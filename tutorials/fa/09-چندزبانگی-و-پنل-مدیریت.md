# ۹. فاز ۴ (بخش دوم) — چندزبانگی و پنل مدیریت

## چندزبانگی (i18n) — مرحله ۴

### چرا از سیستم ترجمه‌ی خود Laravel استفاده نشد؟

Laravel از قبل یک سیستم ترجمه‌ی JSON دارد، ولی آن یک فایل تخت `lang/{locale}.json` با کلید = متن اصلی انتظار دارد. نیاز واقعی پروژه این بود: `lang/{code}/{group}.json` — یعنی چند فایل جدا به‌ازای هر گروه، با کلیدهای مسیر-نقطه‌ای مثل `messages.dashboard.title`. برای همین یک زیرسیستم کوچک و سفارشی (حدود ۴۰ خط) ساخته شد.

اجزای اصلی:

```
Language                          enum: en / fa
TranslationServiceInterface        قرارداد Domain
JsonTranslationLoader              پیاده‌سازی: خواندن فایل‌های JSON
LanguageDetector                   تشخیص زبان درخواست
```

### اولویت تشخیص زبان

```
۱. پارامتر ?lang= در URL
۲. هدر Accept-Language
۳. زبان پیش‌فرض همان Tenant (ستون default_language)
۴. انگلیسی (پیش‌فرض نهایی)
```

برای یک Listener (که Request واقعی HTTP ندارد)، فقط مرحله‌ی ۳ و ۴ استفاده می‌شود (`detectForTenant()`).

### یک نکته‌ی خیلی مهم و تکرارشونده

**کلید ترجمه همیشه باید با نام گروه شروع شود**: `t('messages.dashboard.title')`، نه `t('dashboard.title')`. اگر گروه را جا بیندازید، خطایی داده نمی‌شود — فقط به‌آرامی، خود کلید به‌عنوان متن نمایش داده می‌شود. این دقیقاً همان چیزی بود که در فاز ۴ همه‌ی ۱۷ فایل Blade پنل مدیریت را یک‌جا درگیر کرد و فقط با یک تست که واقعاً متن رندرشده را چک می‌کرد (`assertSee(...)`) کشف شد.

## پنل مدیریت (Admin Dashboard) — مرحله ۵

### چرا این بخش به تعویق افتاد؟

درخواست اولیه، بک‌اند ترجمه را با یک پنل مدیریت ۸-صفحه‌ای همراه کرده بود، ولی هیچ مکانیزم احراز هویت انسانی در پروژه وجود نداشت (هر مسیر هویتی تا آن لحظه فقط توکن Bearer یک Agent بود). به‌جای تصمیم عجولانه، سؤال مطرح شد و کاربر تصمیم گرفت این کار به دو مرحله تقسیم شود: ابتدا فقط بک‌اند ترجمه، بعد در مرحله‌ی بعد پنل مدیریت با معماری احراز هویت مشخص.

### مدل هویت پنل مدیریت — یک بازبینی مهم

اولین تصور این بود که ورود انسانی باید از طریق `OrganizationMember` باشد (چون این مدل از قبل برای عضویت در یک سازمان داخل یک Tenant ساخته شده بود). ولی وقتی لیست واقعی صفحات مشخص شد (مثلاً صفحه‌ی «مدیریت مستأجرها» که باید بین **همه‌ی** Tenant ها CRUD کامل انجام دهد)، مشخص شد این مدل اشتباه است — یک اپراتور پلتفرم عضو یک سازمان خاص نیست، او باید همه‌ی مستأجرها را ببیند.

راه‌حل: یک موجودیت کاملاً جدید و **بدون tenant_id**، به نام `User` — دومین موجودیت هسته که بالاتر از سطح مستأجری قرار دارد (اولی خود `Tenant` بود).

```
User (سطح پلتفرم، بدون tenant_id)
  ├── Email, HashedPassword (بر پایه‌ی password_hash خالص PHP)
  ├── UserRole: Admin / Operator
  └── محافظت‌شده با Guard واقعی Session لاراول (extends Authenticatable)
```

**نکته‌ی حیاتی**: این سیستم کاملاً **مستقل** از سیستم مجوز Role/Permission است که Agent ها استفاده می‌کنند (فایل ۴). دو مکانیزم، دو مسیر، هرگز با هم ترکیب نمی‌شوند — چون سؤالی که هرکدام جواب می‌دهند فرق دارد: «این اپراتور پلتفرم چه دسترسی‌ای دارد» در برابر «این Agent داخل این Tenant چه کاری می‌تواند بکند».

پیش‌فرض ورود اولیه (حتماً قبل از هر Deploy واقعی تغییر دهید):
```
admin@opencommerce.test / password
```

### هشت صفحه‌ی پنل مدیریت

| صفحه | چه کاری می‌کند |
|---|---|
| Home | ۶ کارت KPI، نمودار درآمد/سفارش، ۵ محصول برتر، سفارش‌های اخیر |
| Tenants | CRUD کامل روی مستأجرها |
| Agents | CRUD + تعلیق/فعال‌سازی، فیلتر بر اساس مستأجر |
| Products | فقط-خواندنی، انتخاب مستأجر |
| Orders | لیست/جزئیات/لغو |
| Notifications | لیست فقط-خواندنی |
| Analytics | فرم محاسبه‌ی KPI + خروجی CSV/PDF |
| Settings | فقط مدیریت زبان پیش‌فرض مستأجر |

### قانون طلایی کنترلرهای پنل مدیریت

هر کنترلر پنل مدیریت **همان Action هایی** را صدا می‌زند که Handler قابلیت MCP معادلش صدا می‌زند — هیچ منطق کسب‌وکاری دوباره داخل کنترلر نوشته نمی‌شود. مثلاً صفحه‌ی سفارش‌ها همان `ListOrdersAction`/`GetOrderAction`/`CancelOrderAction` را استفاده می‌کند.

چون Action ها معمولاً به یک Tenant وابسته‌اند و کاربر پنل مدیریت به هیچ Tenant خاصی محدود نیست، هر صفحه‌ی مربوطه یک انتخاب‌گر `?tenant_id=` دارد.

### یک باگ ظریف که چند صفحه را هم‌زمان درگیر کرد

هر شش کنترلر انتخاب‌گر مستأجر، این کد را داشتند:
```php
$tenants[0]->id() ?? null
```
مشکل: وقتی `$tenants` خالی است، خود دسترسی به ایندکس `[0]` قبل از این‌که `?->`/`??` فرصت کنند کاری بکنند، خطا می‌دهد — چون `?->` فقط مرحله‌ی «فراخوانی متد» را محافظت می‌کند، نه مرحله‌ی «دسترسی به آرایه». فرم درست:
```php
($tenants[0] ?? null)?->id()
```
این باگ فقط با یک پایگاه‌داده‌ی کاملاً خالی (بدون هیچ Tenant) بروز می‌کرد و فقط وقتی یک تست دقیقاً همین سناریو را امتحان کرد، پیدا شد. این نمونه‌ی خوبی است از این‌که چرا باید همیشه سناریوی «صفر داده» را هم تست کرد.

## جمع‌بندی این فایل

- سیستم ترجمه‌ی سفارشی، سبک `{group}.{path}` را پیاده‌سازی می‌کند.
- زبان با یک زنجیره‌ی چهار-مرحله‌ای اولویت تشخیص داده می‌شود.
- پنل مدیریت یک لایه‌ی نازک Interfaces است که فقط از Action های موجود استفاده می‌کند.
- احراز هویت انسانی (`User`) کاملاً مستقل از احراز هویت Agent است.

در فایل بعدی، به سراغ Analytics (تحلیل و KPI)، نسخه‌بندی API (v1/v2) و بهینه‌سازی عملکرد می‌رویم — سه مرحله‌ی پایانی فاز ۴.
