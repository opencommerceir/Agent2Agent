# ۱۰. فاز ۴ (بخش سوم) — Analytics، نسخه‌بندی API و بهینه‌سازی عملکرد

سه مرحله‌ی پایانی فاز ۴، هر سه در دسته‌ی زیرساخت میان‌بخشی قرار می‌گیرند.

## Analytics — KPI و داشبورد (مرحله ۶)

### بزرگ‌ترین اصلاح این جلسه‌ی کاری

درخواست اولیه می‌خواست یک ماژول کاملاً جدید بسازد که دوباره از صفر Revenue، Orders و Top Products را از جدول‌های Commerce/Loyalty محاسبه کند. مشکل این‌جاست: **Reporting (فایل ۷) از قبل دقیقاً همین اعداد را محاسبه می‌کند.** ساختن یک راه دوم برای همان محاسبه یعنی دو منبع حقیقت که ممکن است روزی از هم واگرا شوند.

قبل از نوشتن حتی یک خط کد، این موضوع مستقیم با کاربر مطرح شد و تأیید شد: **استفاده‌ی مجدد**. نتیجه:

```
CalculateKPIAction (تنها نقطه‌ی ورودی محاسبه‌ی هر KPI)
   ├── برای KPI هایی که Reporting از قبل می‌داند → مستقیم از Query Builder های Reporting استفاده می‌کند
   └── برای KPI های واقعاً جدید (نرخ تبدیل، نرخ رشد و ...) → ۴ محاسبه‌گر جدید (Domain Calculators)
```

این استثنای Query Builder (که در فایل ۷ برای Reporting دیدیم)، این‌جا برای **دومین بار** با همان استدلال دقیق تکرار می‌شود — نه یک الگوی جدید.

### چهار محاسبه‌گر واقعاً جدید

`RevenueCalculator`، `OrderCalculator`، `CustomerCalculator`، `ConversionRateCalculator` — همه‌ی این‌ها خالص و بدون فریم‌ورک‌اند و فقط اعدادی که از قبل واکشی شده را ترکیب می‌کنند (مثل تمام سرویس‌های Domain دیگر پروژه).

نکته‌ی صادقانه: `CustomerRetentionRate` و `CustomerLifetimeValue` هر دو **ساده‌سازی مستند** هستند، نه یک مدل کوهورت یا پیش‌بینی واقعی — یک تصمیم آگاهانه که در `HANDOFF.md` صریحاً به‌عنوان «واقعی، کارآمد، ولی عمداً ساده‌شده» ثبت شده است.

### دو تصمیم امنیتی مهم

- سه قابلیت (`analytics.dashboard.stats` و ...) در درخواست اولیه یک ورودی `tenant_id` داشتند — این ورودی **عمداً حذف شد**، چون قبول‌کردن `tenant_id` از سمت Agent یعنی هر Agent می‌تواند داده‌ی مالی یک مستأجر دیگر را با تغییر یک عدد ببیند. هر قابلیتی در این کدبیس، فقط از `AuthContext` خودش scope می‌گیرد، نه از ورودی کاربر.
- نتایج تا ۱ ساعت کش می‌شوند؛ فقط در صورت Cache Miss واقعی یک رکورد جدید ذخیره می‌شود.

## نسخه‌بندی API — v1 و v2 (مرحله ۷)

### یک تناقض واقعی در خود درخواست، پیدا و اصلاح شد

اولویت اعلام‌شده برای تشخیص نسخه این بود: URL > Header > Query. ولی مثال تست همان درخواست، دقیقاً برعکس این را نشان می‌داد (یک هدر `Accept` را بر یک URL صریح `v1` غالب می‌کرد). این تناقض قبل از نوشتن کد مطرح شد؛ تصمیم امن‌تر تأیید شد: **یک نسخه‌ی صریح در URL، همیشه برنده است.**

### v1 و v2 یک پلتفرم با دو لباس‌اند

همان‌طور که در فایل ۵ گفتیم — تنها تفاوت واقعی، شکل پاسخ (Envelope) است. برای این‌که این دو نسخه هرگز در مسیر امنیتی (احراز هویت → محدودیت نرخ → مجوز → اجرا) از هم واگرا نشوند، این توالی در یک کلاس پایه‌ی مشترک استخراج شد — هر کنترلر مخصوص نسخه فقط مسئول قالب‌بندی پاسخ خودش است.

## بهینه‌سازی عملکرد (مرحله ۸، آخرین مرحله‌ی فاز ۴)

### ممیزی ایندکس‌های پایگاه‌داده

قبل از نوشتن Migration، لیست درخواستی با شِمای واقعی مقایسه شد: بیشتر ایندکس‌های خواسته‌شده از قبل وجود داشتند، و دو مورد اصلاً به ستون‌هایی اشاره می‌کردند که وجود نداشتند. فقط ۸ ایندکس واقعاً لازم اضافه شد.

### چهار باگ واقعی N+1 پیدا شد

با جست‌وجوی سیستماتیک روی متدهای `toEntity()` که یک رابطه‌ی hasMany را می‌خواندند بدون Eager Loading، چهار باگ واقعی کشف شد — یکی از آن‌ها (`findActiveByEventType()`) روی **هر بار** اجرای یک رویداد دامنه صدا زده می‌شد، نه فقط یک صفحه‌ی گاه‌به‌گاه. هر چهار مورد با یک `->with()` ساده رفع شدند و یک تست رگرسیون تعداد کوئری (نه فقط درستی نتیجه) اضافه شد.

### دو تصمیم که عمداً برخلاف درخواست پیاده‌سازی شدند

1. **فشرده‌سازی Gzip** فقط روی مسیرهای `web` اعمال شد، نه `mcp/*` — چون فشرده‌سازی سراسری، حدود ۶۰۰ تست JSON را می‌شکست و خطر دوبار-فشرده‌سازی داشت اگر تنظیم سرور هم فعال باشد.
2. **اتصال دائمی PDO (Persistent Connection)** به‌جای پیش‌فرض، **اختیاری** شد — چون در یک اپلیکیشن چندمستأجری، اتصال مشترک بین درخواست‌ها می‌تواند داده‌ی یک تراکنش را به‌اشتباه به مستأجر بعدی نشت دهد.

### CacheService

یک سرویس کش جدید، آگاه به تگ (`Cache::tags()`)، فقط روی یک مسیر واقعی (خواندن/به‌روزرسانی/حذف محصول) سیم‌کشی شد — نه همه‌جا یک‌باره. کلید کش شامل `tenantId` است تا محصول یک مستأجر هیچ‌وقت به مستأجر دیگر با همان شناسه‌ی عددی نشت نکند.

## جدول خلاصه

| مرحله | دستاورد کلیدی |
|---|---|
| Analytics (۶) | استفاده‌ی مجدد از Reporting به‌جای دوباره‌سازی + حذف امنیتی `tenant_id` ورودی |
| API Versioning (۷) | URL همیشه برنده؛ منطق امنیتی مشترک بین v1/v2 |
| Performance (۸) | رفع ۴ باگ واقعی N+1، ایندکس‌های واقعی، کش تگ‌دار امن نسبت به Tenant |

با پایان این فایل، **فاز ۴ به‌طور کامل تمام شده** (۶۴۸ تست، صفر Regression). فایل بعدی وارد فاز ۵ می‌شود — جایی که Commerce با پنج قابلیت پیشرفته‌ی جدید گسترش پیدا می‌کند.
