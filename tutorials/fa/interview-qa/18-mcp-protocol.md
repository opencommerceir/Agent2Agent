# ۱۸. پروتکل MCP

ردیابی کامل و گام‌به‌گام یک درخواست MCP (فایل ۰۲، سؤال ۳)، چرا این API کاملاً RESTful نیست (فایل ۰۵، سؤال ۱)، تناقض واقعی نسخه‌بندی v1/v2 که این پروژه گرفت و اصلاح کرد (فایل ۰۵، سؤال ۲)، اعتبارسنجی ورودی از طریق `inputSchema` (فایل ۰۵، سؤال ۳)، MCP Gateway به‌عنوان یک گلوگاه معماری عمدی (فایل ۰۲، سؤال ۱۰)، و جایگاه خودِ MCP Gateway به‌عنوان یک Open Host Service واقعی — با UCP به‌عنوان زبان-منتشرشده‌ی همراهش (فایل ۰۸، سؤال‌های ۵ و ۱۱) — همه از قبل از زاویه‌های دیگر پوشش داده شدند. این فایل جایی است که خودِ پروتکل رفتار مستقیم و مستقل می‌گیرد: MCP واقعاً چیست در برابر چیزی که این پلتفرم واقعاً ساخته، تفکیک Discovery/Execution به‌عنوان یک مرز امنیتی واقعی، تاریخچه‌ی رد-و-دوباره-نام‌گذاری خودِ قانون نام‌گذاری، یک نکته‌ی ظریف ثبت واقعی، و این‌که چطور پنج SDK مستقل و کل یک Orchestrator هوش‌مصنوعی هردو در نهایت روی دقیقاً همان قرارداد عمداً غیرچشمگیر HTTP+JSON تکیه می‌کنند.

### Q1: آیا خودِ MCP Gateway این پلتفرم واقعاً فرمت سیمی رسمی Model Context Protocol را صحبت می‌کند، یا چیز دیگری؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا واقعاً فرق بین «ایده‌ی زیربنایی یک پروتکل را پیاده می‌کند» و «فرمت سیمی تحت‌اللفظی آن پروتکل را صحبت می‌کند» را می‌داند — تمایزی که خیلی‌ها وقتی نام‌گذاری یک پروژه آن را شبیه یک چک‌باکس جلوه می‌دهد قاطی می‌کنند.

✅ **جواب مدل:**
«چیز دیگری، و ارزش دارد دقیق دربارش باشیم به‌جای این‌که بگذاریم اسم حرف بزند. خودِ MCP Gateway این پلتفرم یک API واقعی و معمولی HTTP+JSON است — `POST /mcp/v1/execute` با یک توکن Bearer و یک Body JSON، `GET /mcp/v1/capabilities` که یک لیست JSON برمی‌گرداند — نه فرمت پیام رسمی JSON-RPC 2.0 خودِ Model Context Protocol روی stdio یا Streamable HTTP با مذاکره‌ی نشست. چیزی که این پلتفرم واقعاً دنبال کرد *ایده‌ی زیربنایی* است که MCP به‌عنوان یک مفهوم صنعتی نمایندگی می‌کند: یک قرارداد استاندارد برای این‌که یک AI Agent قابلیت‌ها را **کشف** کند و **اجرا**شان کند بدون دانش قبلی و Hardcode‌شده از این‌که سیستم پشتشان واقعاً چطور کار می‌کند — همان شکل کشف-سپس-اجرا که پروتکل رسمی دورش ساخته شده، فقط روی HTTP+JSON حمل‌شده به‌جای فرمت سیمی رسمی. این یک تناسب معقول و عمدی برای چیزی است که این پلتفرم واقعاً نیاز دارد: یک API بی‌حالت، Multi-Tenant، احراز‌هویت‌شده-با-Bearer-Token که با `curl` بی‌دردسر صدازدنی است، بدون هیچ کتابخانه‌ی کلاینت خاص قابل‌تست است، و در پنج SDK زبان مختلف (سؤال ۷ همین فایل) با صفر ابزار مخصوص-پروتکل در هرکدام قابل‌حمل است.»

🔁 **سوالات تعقیبی احتمالی:**
1. «یعنی خودِ "MCP" این پلتفرم واقعاً فقط یک API REST با یک اسم متفاوته؟» → نه دقیقاً REST هم — فایل ۰۵ (سؤال ۱) از قبل پوشش می‌دهد چرا: یک آدرس اجرای واحد برای هر ۱۲۷ قابلیت، نه یک شکل REST یک-Resource-به‌ازای-هر-آدرس، مشخصاً تا کشف پویا نیازی به یک نقشه‌ی آدرس از‌قبل-شناخته‌شده نداشته باشد.
2. «آیا پذیرفتن فرمت سیمی رسمی تا حالا معنا داشته؟» → اگه این پلتفرم نیاز داشت مستقیم داخل یک کلاینت بومی-MCP وصل شود که دقیقاً همان انتقال را انتظار دارد، بله — امروز، هر مصرف‌کننده‌ی واقعی (پنج SDK، Agent Orchestrator خودِ این پلتفرم) از قبل HTTP+JSON صحبت می‌کند، پس هیچ نیاز واقعی و فعلاً‌حس‌شده‌ای این تغییر را نمی‌راند.

🚩 **پرچم‌های قرمز:**
فرض این‌که «اسمش MCP هست» سؤال این‌که واقعاً کدام فرمت سیمی در کاره را حل می‌کند — جواب جالب و درست نیاز دارد واقعاً بدانی فرمت سیمی پروتکل رسمی چه شکلی است و صادقانه با کاری که مسیرهای واقعی این پلتفرم انجام می‌دهند مقایسه‌اش کنی.

### Q2: `GET /mcp/v1/capabilities` می‌گوید یک قابلیت وجود دارد. یعنی یک فراخوان واقعاً اجازه دارد اجراش کند؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک مرز امنیتی دقیق و واقعی که این پلتفرم مستقیم بیانش می‌کند — Discovery و Execution دو چک مستقل هستند، و قاطی‌کردنشان یک اشتباه واقعی و رایج است.

✅ **جواب مدل:**
«نه، و این پلتفرم صریح دربارش است: Discovery فقط مستندات است، مجوز واقعی همیشه، جدا، در زمان اجرا چک می‌شود. `GET /mcp/v1/capabilities` نام، توضیح، شکل ورودی/خروجی، و مجوز لازم هر قابلیت را برمی‌گرداند — یک کاتالوگ کامل و صادقانه از چیزی که پلتفرم *می‌تواند* انجام دهد — ولی دیدنش آنجا هرگز تضمین نمی‌کند یک فراخوان مشخص واقعاً اجازه‌ی اجراش را دارد. آن چک واقعی منحصراً داخل چرخه‌ی عمر درخواست خودِ `POST /mcp/v1/execute` اتفاق می‌افتد (فایل ۰۲، سؤال ۳)، جایی که `CheckPermissionAction` تأیید می‌کند این Agent مشخص، از طریق یکی از Roleهایش، واقعاً مجوزی که این قابلیت مشخص نیاز دارد را دارد. این دو نگرانی برای یک دلیل واقعی کاملاً جدا هستند: Discovery باید به «اصلاً چی روی این پلتفرم وجود داره» به همان شکل برای هر فراخوان جواب دهد، درحالی‌که Execution باید به «آیا *خودت مشخصاً* می‌تونی این کار رو بکنی» متفاوت برای هر فراخوان جواب دهد — یکی‌کردنشان یا یعنی مخفی‌کردن قابلیت‌های واقعی از فراخوان‌هایی که هنوز نمی‌توانند استفاده‌شان کنند (Discovery را فراخوان-مشخص و گران می‌کند) یا اجازه‌دادن به Discovery بی‌صدا یک تضمین مجوز که هرگز طراحی نشده بدهد را برساند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا `LLMPlanner` یک لیست فیلترشده می‌بیند، فقط قابلیت‌هایی که Agent خودش می‌تواند استفاده کند؟» → نه — همان `DiscoverCapabilitiesAction` را برای لیست کامل قابلیت‌های پلتفرم صدا می‌زند صرف‌نظر از مجوزهای Agent درخواست‌کننده، یعنی یک LLM واقعاً می‌تواند یک مرحله را برنامه‌ریزی کند که اصلاً اجازه‌ی اجرایش را ندارد؛ سؤال ۴ فایل ۱۷ پوشش می‌دهد بعدش چی اتفاق می‌افتد — یک ۴۰۳ واقعی در زمان اجرا، بدون هیچ دور‌زدن خاص.
2. «آیا لیست‌کردن قابلیت‌هایی که یک فراخوان نمی‌تواند استفاده کند یک نشت امنیتی نیست؟» → نه با طراحی خودِ این پلتفرم — نام/توضیح/Schema یک قابلیت قابل‌مشاهده به‌عنوان مستندات عمومی API رفتار می‌شود، نه یک راز؛ مرز واقعاً ارزشمند-حفاظت (آیا واقعاً می‌تونی صداش بزنی) دقیقاً یک‌بار، جایی که واقعاً اهمیت دارد، اجرا می‌شود.

🚩 **پرچم‌های قرمز:**
فرض این‌که یک قابلیت که در Discovery ظاهر می‌شود یعنی یک فراخوان می‌تواند بی‌خطر صدایش بزند بدون انتظار یک ۴۰۳ ممکن — دقیقاً همان تضمین کاذبی که مستندات خودِ این پلتفرم مواظب است هرگز القا نکند.

### Q3: داستان واقعی پشت قانون نام‌گذاری قابلیت «دقیقاً ۳ بخش» را بهم بگو — نه فقط قانون، بلکه اسم‌های واقعی که رد و دوباره‌نوشته شدند.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آشنایی ملموس و به‌خاطرسپرده‌شده با یک محدودیت ساختاری که این پروژه در کد اجرا می‌کند (خودِ `CapabilityName` اعتبارسنجی‌اش می‌کند)، نه فقط یک قانون بازنویسی‌شده.

✅ **جواب مدل:**
«`CapabilityName`/`PermissionKey` هردو دقیقاً سه بخش جداشده‌با-نقطه نیاز دارند — `domain.resource.action` — و این محدودیت Renameهای واقعی و مشخصی در سراسر تاریخچه‌ی پروژه اجبار کرده، نه فقط یک راهنمای فرضی. `crm.ticket.comment.add` (۴ بخش) به `crm.comment.create` تبدیل شد — «Comment» به Resource خودش ارتقا یافت، چون یک Comment واقعاً یک زیر-ویژگی فضای-عمل خودِ یک Ticket نیست. `workflow.create` (۲ بخش) به `workflow.definition.create` تبدیل شد — مفهوم ضمنی «Definition» صریح شد. `commerce.variant.attribute.create` (۴ بخش) به `commerce.attribute.create` تبدیل شد، و `commerce.subscription.plan.create` (۴ بخش) به `commerce.plan.create` تبدیل شد — همان حرکت هردوبار، ارتقای یک کلمه‌ی میانی به Resource درجه‌یک خودش به‌جای اختراع یک شِمای نام‌گذاری عمیق‌تر تودرتو. الگو این‌قدر تکرار می‌شود که یک قانون سرانگشتی نام‌گذاری‌شده است: وقتی یک نام درخواستی روی ۴ بخش فرود می‌آید، تقریباً همیشه یکی از کلمات میانی همانی است که باید ارتقا یابد؛ وقتی روی ۲ بخش فرود می‌آید، مفهوم گم‌شده‌ای که درخواست فقط ضمنی گفته به‌جایش صریح می‌شود.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا کوچکی ماژول کل ساختش را بدون برخورد به این تمام کرده؟» → فقط Loyalty و Reporting، طبق تاریخچه‌ی خودِ این پروژه — WooCommerce، CRM، Finance، Workflows، و Shipping هرکدام حداقل به یک Rename نیاز داشتند، این را به یکی از پایدارترین نکات ظریف نام‌گذاری تکرارشونده در سراسر پلتفرم تبدیل می‌کند.
2. «چرا فقط اجازه‌ی تعداد بخش انعطاف‌پذیر داده نشد؟» → یک شکل ثابت و دقیقاً-۳-بخشی چیزی است که شِمای نام‌گذاری را برای هر مصرف‌کننده، انسان یا LLM، در یک نگاه قابل‌پیش‌بینی و قابل‌Parse می‌کند (`domain.resource.action`) — یک شِمای طول-متغیر آن قابل‌پیش‌بینی‌بودن را با جای‌دادن هرشکلی که یک درخواست اتفاقاً پیشنهاد داده معامله می‌کرد.

🚩 **پرچم‌های قرمز:**
بیان قانون به‌صورت انتزاعی («نام‌ها باید کوتاه باشند») بدون توانایی تولید یک نام واقعی و مشخص رد‌شده و جایگزین واقعی‌اش — تاریخچه‌ی ملموس چیزی است که ثابت می‌کند این یک محدودیت اجراشده است، نه یک ترجیح سبکی.

### Q4: یک قابلیت می‌تواند با «هیچ Handler اجرایی پیدا نشد» شکست بخورد با این‌که مطمئنی داخل ServiceProvider وایر شده. واقعاً چی داره اتفاق می‌افته؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک نکته‌ی ظریف واقعی، خاص، و راحت-برخوردکردنی که مستندات خودِ این پروژه مستقیم نام می‌برد — و دلیل ساختاری واقعی *چرا* وجود دارد، نه فقط «یادت باشه هردو کار رو بکن».

✅ **جواب مدل:**
«ثبت‌کردن **Handler** اجرای واقعی یک قابلیت و ثبت‌کردن **توضیحش** (برای Discovery، و برای Seederای که تغذیه‌اش می‌کند) دو مرحله‌ی کاملاً مستقل هستند، و واقعاً راحت است یکی را انجام دهی و دیگری را فراموش کنی. Handler یک Closure است که داخل خودِ `ServiceProvider::boot()` ماژول مالک ثبت شده — خالص، درون-حافظه، بدون هیچ پایگاه‌داده‌ای درگیر. توضیح یک ردیف پایگاه‌داده است، نوشته‌شده توسط Seeder اختصاصی خودِ آن ماژول (مثل `CommerceCapabilitiesSeeder`)، هرگز مستقیم داخل `boot()` ثبت نمی‌شود. دلیل این‌که نمی‌توانند هردو داخل `boot()` زندگی کنند: `ServiceProvider::boot()` خودِ Laravel *قبل* از این‌که `RefreshDatabase` پایگاه‌داده‌ی تست را Migrate کند اجرا می‌شود، پس چیزی که به یک ردیف واقعی پایگاه‌داده نیاز داشته باشد در آن نقطه از چرخه‌ی عمر یک تست هنوز یکی نخواهد داشت. اگه یک قابلیت با «هیچ Handler اجرایی پیدا نشد» با این‌که به‌نظر درست داخل ServiceProvider وایر شده ۴۰۴ بگیرد، رفع مشکل واقعی تقریباً همیشه چک‌کردن این است که آیا تست واقعاً Capabilities Seeder مطابق را Seed کرده — Handler احتمالاً همیشه درست بوده.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا Discovery تا حالا برای دلیل برعکس شکست می‌خوره — یک توضیح Seed‌شده بدون Handler واقعی پشتش؟» → بله، ساختاری همان‌قدر ممکن برعکس — یک قابلیت می‌تواند در `GET /mcp/v1/capabilities` ظاهر شود ولی با یک خطای Handler-پیدا-نشد در زمان اجرا ۵۰۰ بدهد، دقیقاً چرا این نکته‌ی ظریف به‌عنوان «دو ثبت مستقل» چارچوب‌بندی شده، نه «یک ثبت با دو بخش اختیاری».
2. «چرا خودِ Seeder Handler رو هم ثبت نمی‌کنه، پس یک مرحله باشه؟» → یک Handler PHP خالص بدون هیچ وابستگی پایگاه‌داده است؛ مجبورکردنش از طریق Seeder یعنی مسیر اجرای درون-حافظه حالا وابسته به Migrate‌شدن اول پایگاه‌داده است، خنثی‌کردن دقیقاً همان دلیلی که Handlerها اصلاً داخل `boot()` زندگی می‌کنند.

🚩 **پرچم‌های قرمز:**
فرض این‌که «وایرشده داخل ServiceProvider» یک عمل واحد و اتمی است — از‌دست‌دادن این‌که این پروژه عمداً آن را به دو ثبت مستقل برای یک دلیل واقعی و ساختاری (زمان‌بندی پایگاه‌داده‌ی تست) تقسیم می‌کند، نه تصادفی.

### Q5: منطق تشخیص نسخه اول URL، بعد یک Header به‌نام Accept، بعد یک Query String را چک می‌کند — ولی فقط لایه‌ی URL واقعاً در Production درگیر می‌شود. چرا دو لایه‌ی دیگر اصلاً نگه‌داشته شدند؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا می‌تواند نگه‌داشتن مسیرهای کد کاملاً-ساخته‌شده و کاملاً-تست‌شده که هرگز در عمل فعال نمی‌شوند را دفاع کند — یک تصمیم واقعی و عمدی، نه کد مرده‌ای که تصادفی جا مانده.

✅ **جواب مدل:**
«چون «امروز هرگز درگیر نمی‌شود» و «کد مرده» دو ادعای متفاوت هستند، و این واقعاً اولی است، نه دومی. هر مسیر واقعی این پلتفرم از قبل یک بخش نسخه‌ی صریح حمل می‌کند (`/mcp/v1/...` یا `/mcp/v2/...`)، پس لایه‌ی URL همیشه قبل از این‌که دو لایه‌ی دیگر اصلاً مشورت شوند برنده می‌شود — ولی لایه‌های فال‌بک Header/Query کاملاً پیاده‌سازی‌شده و کاملاً تست‌شده هستند، نگه‌داشته‌شده به‌عنوان سازگاری-با-آینده واقعی و کارکننده برای یک فراخوان که یک‌روزی ممکن به یک مسیر بدون-نسخه برخورد کند، یا یک واسط که URLها را بازنویسی می‌کند ولی Headerها را حفظ می‌کند. این طراحی سه‌لایه هم دقیقاً چیزی است که یک تناقض واقعی و گرفته‌شده در Spec اصلی خودِ این ویژگی را آشکار کرد (فایل ۰۵، سؤال ۲): اولویت بیان‌شده «URL بر Header بر Query» بود، ولی تست مثال خودِ Spec انتظار داشت یک Header به‌نام Accept یک URL v1 از‌قبل-صریح را غلبه کند — دقیقاً همان نوع تغییر-نسخه‌ی پنهان و غافلگیرکننده که یک API قابل‌اعتماد نمی‌تواند اجازه دهد. گرفتن آن یعنی لایه‌های Header/Query امروز دقیقاً همان‌طور که اصلاً مشخص شده وجود دارند، منهای همان یک تناقض، نه حدس تست‌نشده.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا این همان Refactor است که AbstractMCPGatewayController رو تولید کرد؟» → مستقیم مرتبط — قبل از این‌که v2 وجود داشته باشد، فقط یک Controller بود و هیچ ریسک واقعی Drift کردن چهار مرحله‌ی امنیتی-حیاتی (احراز‌هویت/محدودیت‌نرخ/مجوز/اجرا) بین دو نسخه وجود نداشت؛ آمدن v2 دقیقاً چیزی است که «این رو تکرار نکن» را از یک خوب-داشتن به یک الزام واقعی تبدیل کرد، برای همین Extraction دقیقاً در آن لحظه اتفاق افتاد، نه زودتر.
2. «چطور می‌دونی v1 و v2 واقعاً همون داده‌ی زیربنایی رو برمی‌گردونن؟» → یک تست مستقیم ثابتش می‌کند، نه یک فرض — همان قابلیت را از هردو نسخه صدا می‌زند و `v1.data === v2.result` را ادعا می‌کند، دقیقاً همان Payload زیربنایی زیر دو شکل پاکت متفاوت.

🚩 **پرچم‌های قرمز:**
پیشنهاد این‌که لایه‌های Header/Query باید حذف شوند چون «هرگز اجرا نمی‌شوند» — از‌دست‌دادن این‌که تست‌نشده-در-Production و استفاده‌نشده-با-طراحی از خراب یا بی‌فایده متفاوت هستند؛ این مسیرها واقعی، تأییدشده، و کارکننده‌اند، نگه‌داشته‌شده برای یک دلیل واقعی سازگاری-با-آینده.

### Q6: خودِ Agent Orchestrator مسیرهای HTTP اختصاصی خودش را دارد (`POST /api/agents/{agent_type}`، `GET /api/agents/executions/{id}`) *علاوه‌بر* قابلیت‌های MCPاش. این یعنی پلتفرم دو راه رقیب برای همون کار داره؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
تشخیص یک الگوی معماری واقعی و نام‌گذاری‌شده (یک سطح انسان-محور یا تخصصی همیشه Actionهای موجود را دوباره استفاده می‌کند، هرگز منطق کسب‌وکاری را برای یک انتقال جدید دوباره پیاده نمی‌کند) به‌جای دیدن دو مسیر به همان نتیجه به‌عنوان ذاتاً تکراری.

✅ **جواب مدل:**
«دو مسیر، هرگز دو پیاده‌سازی — و آن تمایز دقیقاً کل نکته است. `POST /api/agents/{agent_type}` و `agent.goal.execute` **دقیقاً همان** Action زیربنایی را صدا می‌زنند؛ `GET /api/agents/executions/{id}` و `agent.execution.get` هم همین‌طور. این یک الگوی نام‌گذاری‌شده و تکرارشونده در خودِ معماری این پروژه است: یک سطح تخصصی یا انسان-محور همیشه Actionهایی را دوباره استفاده می‌کند که قابلیت‌های MCP خودِ یک ماژول از قبل صدا می‌زنند، هرگز همان منطق کسب‌وکاری را برای یک انتقال متفاوت دوباره پیاده نمی‌کند — همان انضباطی که Admin Dashboard برای هرکدام از Controllerهای خودش دنبال می‌کند، مستقیم Actionهای خودِ Commerce/CRM را دوباره استفاده می‌کند به‌جای تکرار منطقشان پشت یک UI Session-محور. مسیرهای اختصاصی Orchestrator وجود دارند چون یک بخش URL ساده `/api/agents/{agent_type}` یک شکل طبیعی‌تر و راحت‌تر برای یک مورد استفاده‌ی مشخص و باریک‌تر است تا یک Body عمومی `POST /mcp/v1/execute` — ولی «راحت‌تر برای یک مورد استفاده» هرگز به یک بهانه برای Fork‌کردن منطق واقعی تبدیل نمی‌شود؛ واقعاً همان Action است، رسیده‌شده از یک در دوم.»

🔁 **سوالات تعقیبی احتمالی:**
1. «یعنی هر ماژول در نهایت به سطح HTTP اختصاصی خودش هم نیاز داره؟» → نه — این مخصوص موردی است که یک شکل انتقال باریک‌تر و تخصصی‌تر واقعاً به یک فراخوان واقعی کمک می‌کند؛ اکثر ماژول‌ها هیچ نیاز قابل‌مقایسه‌ای ندارند و کاملاً خوب فقط با سطح عمومی و واحد MCP خدمت‌رسانی می‌شوند.
2. «چطور می‌گرفتیش اگه کسی تصادفی می‌گذاشت دو سطح از هم Drift کنند؟» → همان انضباط Test Suite که فایل ۰۵ (سؤال ۲) از قبل برای اثبات رفتار یکسان v1/v2 استفاده می‌کند — یک تست مستقیم که هم قابلیت MCP و هم مسیر اختصاصی را صدا می‌زند و نتایج یکسان را ادعا می‌کند، نه فقط اعتماد این‌که یک‌بار درست ساخته شدند تا مچ شوند.

🚩 **پرچم‌های قرمز:**
توصیف مسیرهای اختصاصی Orchestrator به‌عنوان «یک پیاده‌سازی دوم» یا «یک راه‌حل موقت» — از‌دست‌دادن این‌که کل نکته‌ی معماری این است که همان Action دو‌طوری رسیده شده، نه منطق رقیبی که اتفاقاً نتایج مشابه تولید می‌کند.

### Q7: پنج SDK رسمی وجود دارند، در پنج زبان مختلف، سه‌تاشان با صفر وابستگی خارجی. این واقعاً به چی درباره‌ی ساخته‌شدن خودِ Gateway بستگی داره؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
وصل‌کردن یک نتیجه‌ی واقعی و بین-زبانی مهندسی به تصمیم مشخص طراحی-پروتکل (سؤال ۱ همین فایل) که آن را ممکن کرد — نه فقط لیست‌کردن SDKها به‌عنوان یک ویژگی.

✅ **جواب مدل:**
«مستقیم به این بستگی دارد که Gateway خالص HTTP+JSON باشد، نه یک پروتکل که به یک کتابخانه‌ی کلاینت تخصصی برای صحبت درست نیاز دارد. SDKهای خودِ Python، Node.js/TypeScript، و Go عمداً با صفر وابستگی خارجی ساخته شدند — هرکدام فقط از کلاینت HTTP کتابخانه‌ی استاندارد زبان خودش استفاده می‌کند (خودِ Python، `fetch`، `net/http`) — چیزی که فقط ممکن است چون صحبت‌کردن با این پلتفرم هرگز به چیزی تخصصی‌تر از «یک Body JSON روی HTTPS با یک Header Bearer بفرست، یک پاسخ JSON را Parse کن» نیاز ندارد. هر پنج SDK، شامل هردو PHP، عمداً دقیقاً همان قرارداد را به اشتراک می‌گذارند: یک شیء پیکربندی، یک Client که سه عملیات را افشا می‌کند (`discoverCapabilities`/`execute`/`getCapability`)، و یک سلسله‌مراتب خطا مطابق کدهای وضعیت HTTP خودِ سرور — چون خودِ پروتکل زیربنایی به‌اندازه‌ی کافی ساده است که SDK خودِ هر زبان می‌تواند یک پوشش نازک و صادقانه باشد به‌جای این‌که به منطق واقعی مخصوص-پروتکل خودش نیاز داشته باشد. و برای هر زبانی بدون هیچ SDK رسمی اصلاً، Fallback مستندشده واقعاً فقط «مستقیم HTTP+JSON صحبت کن» است — یک شکاف زبانی واقعی برای یک فراخوان چند ساعت نوشتن یک Client نازک هزینه دارد، نه هفته‌ها پیاده‌سازی یک پروتکل سیمی ناآشنا از صفر.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا SDK PHP به Guzzle نیاز داره وقتی سه‌تای دیگه به هیچی نیاز ندارن؟» → PHP، برخلاف Python/Node.js/Go، اصلاً هیچ کلاینت HTTP کتابخانه‌ی استاندارد ندارد — Guzzle تنها وابستگی واقعاً لازم است، نه یک ناهماهنگی در فلسفه‌ی صفر-وابستگی سه‌تای دیگر.
2. «آیا SDK Go ساختاری با بقیه یکسانه؟» → ساختاری همان قرارداد سه-عملیاتی، با یک تفاوت اصطلاح-زبانی عمدی — هر متد یک `context.Context` به‌عنوان اولین پارامترش می‌گیرد، اصطلاح استاندارد خودِ Go برای Timeout/لغو، و خطاها از نوع بومی `error` خودِ Go استفاده می‌کنند به‌جای Exception.

🚩 **پرچم‌های قرمز:**
رفتار با پنج SDK به‌عنوان پنج تلاش مهندسی مستقل — از‌دست‌دادن این‌که سادگی مشترکشان یک نتیجه‌ی مستقیم و ساختاری خودِ پروتکل عمداً غیرچشمگیر HTTP+JSON است، نه یک تصادف که پنج تیم جدا اتفاقی همگرا شدند.

### Q8: این پلتفرم دو «سطح» تعامل مستند می‌کند — صدازدن مستقیم یک قابلیت، و دادن یک Goal متن-ساده. یک یکپارچگی واقعی واقعاً کِی یکی را بر دیگری انتخاب می‌کند؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا این‌ها را به‌عنوان دو شکل تعامل واقعاً متفاوت و عمداً هم‌زیست می‌بیند — نه یک راه قدیمی و یک راه جدید، با یکی که سرنوشتش جایگزین‌کردن دیگری است.

✅ **جواب مدل:**
«سطح ۱ صدازدن مستقیم یک قابلیت مشخص و از‌قبل-شناخته‌شده است — `commerce.product.search` با یک Query واقعی — برای یک فراخوان که از قبل دقیقاً می‌داند چی می‌خواهد انجام شود؛ این شکلی است که هر پنج SDK (سؤال ۷ همین فایل) به‌عنوان `execute()` افشا می‌کنند. سطح ۲ دادن یک Goal متن-ساده به `agent.goal.execute` است و گذاشتن شش مرحله‌ی خودِ Orchestrator (فایل ۱۷) بفهمند کدام قابلیت‌ها را صدا بزنند، در چه ترتیبی — برای یک فراخوان که فقط یک نیت کلی دارد، نه یک برنامه‌ی دقیق. هردو همیشه هم‌زمان در دسترس هستند، برای همان پلتفرم، چون فراخوان‌های واقعاً متفاوتی را خدمت می‌کنند: یک اسکریپت یکپارچگی ساده که فقط «این محصول رو جستجو کن» نیاز دارد هیچ دلیلی برای پرداخت هزینه‌ی واقعی (تأخیر، یک Call LLM، سربار برنامه‌ریزی) سطح ۲ برای چیزی که از قبل می‌داند چطور مستقیم بخواهد ندارد؛ یک فراخوان مستقل‌تر — خودش یک سیستم AI، یا یک انسان که یک درخواست مبهم در یک Chat Box تایپ می‌کند — اصلاً راهی برای بیان «کدام توالی دقیق قابلیت» ندارد، دقیقاً شکافی که سطح ۲ برای بستنش وجود دارد. هیچ سطحی نسبت به دیگری به‌عنوان «واقعی» یا «پیشرفته» موضع‌گیری نشده؛ آن‌ها دو شکل متفاوت همان سطح زیربنایی قابلیت هستند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا یک Goal سطح ۲ تا حالا می‌تونه به یک توالی ثابت سطح ۱ دوباره‌نوشته بشه؟» → اغلب، بله، برای یک Goal که در نهایت روتین از‌آب‌درمی‌آید — این دقیقاً چیزی است که `ExecutionPattern`/حافظه‌ی اجرا (فایل ۱۷، سؤال ۵) برایش وجود دارد: یک Goal تکراری روزافزون توسط یک Plan یادگرفته‌شده و دوباره‌استفاده‌شده خدمت می‌شود به‌جای برنامه‌ریزی تازه‌ی سطح-۲ هر بار، بی‌آن‌که خط را در عمل هرگز کاملاً حذف کند.
2. «آیا سطح ۱ همون‌طور که یک مرحله‌ی برنامه‌ریزی‌شده-توسط-LLM سطح ۲ ممکنه، مجوز رو رد می‌کنه؟» → نه — هردو سطح در نهایت از طریق دقیقاً همان مسیر `CapabilityExecutionService` اجرا می‌شوند (فایل ۱۷، سؤال ۴)، پس یک شکاف مجوز همان ۴۰۳ واقعی را تولید می‌کند صرف‌نظر از این‌که Call از کدام سطح شروع شده.

🚩 **پرچم‌های قرمز:**
توصیف سطح ۲ به‌عنوان یک ارتقای قطعی روی سطح ۱، یا سطح ۱ به‌عنوان یک مسیر قدیمی که دارد کنار گذاشته می‌شود — از‌دست‌دادن این‌که این پلتفرم عمداً هردو را به‌عنوان شکل‌های تعامل دائماً معتبر و متفاوت-مناسب برای فراخوان‌های واقعاً متفاوت نگه می‌دارد.

### Q9: من رو از دقیقاً کجا «این قابلیت وجود دارد» و «این فراخوان واقعاً می‌تواند اجراش کند» به‌شکل مکانیکی در کد چک می‌شوند عبور بده.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک جواب دقیق و مکانیکی که روی سؤال ۲ همین فایل می‌سازد — آیا کاندیدا می‌تواند کلاس‌های واقعی درگیر را نام ببرد، نه فقط اصل امنیتی Discovery/Execution را انتزاعی دوباره بیان کند.

✅ **جواب مدل:**
«`GET /mcp/v1/capabilities` پشتش `DiscoverCapabilitiesAction` است — کاتالوگ کامل و واقعی قابلیت پلتفرم را برمی‌گرداند، و قابل‌توجه، این همان Actionی است که خودِ `LLMPlanner` هم داخلی صدا می‌زند وقتی به «هر قابلیتی که پلتفرم دارد» برای برنامه‌ریزی روی آن نیاز دارد، بدون هیچ فیلتر مبتنی‌بر-مجوز اعمال‌شده در آن نقطه برای هیچ‌کدام فراخوان. مرز واقعی مجوز کاملاً داخل چرخه‌ی عمر درخواست خودِ `POST /mcp/v1/execute` است (فایل ۰۲، سؤال ۳): بعد از احراز‌هویت و محدودیت‌نرخ، `CheckPermissionAction` Roleهای خودِ Agent حل‌شده را در برابر مجوز مشخصی که قابلیت هدف اعلام می‌کند نیاز دارد چک می‌کند — فقط بعد از آن چک است که `CapabilityExecutionService` اصلاً واقعاً Handler را اجرا می‌کند. این یعنی دقیقاً همان پاسخ Discovery به هر فراخوان و هر فرآیند برنامه‌ریزی صرف‌نظر از این‌که هرکدام مشخصاً اجازه‌ی چی را دارند داده می‌شود، و تنها دروازه‌ی واحدی که واقعاً اهمیت دارد بعداً، در Execution می‌نشیند — هرگز تکرارنشده، هرگز به‌ازای هر نوع فراخوان دوباره‌پیاده‌سازی‌نشده، و هرگز برای یک Call که از یک Goal برنامه‌ریزی‌شده-توسط-LLM سرچشمه گرفته به‌جای یک Call مستقیم MCP رد‌نشده.»

🔁 **سوالات تعقیبی احتمالی:**
1. «یعنی یک فراخوان می‌تونه Discovery رو کاوش کنه تا درباره‌ی قابلیت‌هایی که مجوزشون رو نداره یاد بگیره؟» → بله، و این به‌عنوان یک تبادل قابل‌قبول و عمدی رفتار می‌شود — نام‌ها/Schemaهای قابلیت مستندات عمومی API هستند، نه راز؛ چیز واقعاً ارزش-محافظت (Execution واقعی) در تنها جایی که اهمیت دارد محافظت می‌شود.
2. «چرا خودِ DiscoverCapabilitiesAction یک AuthContext نمی‌گیره و از قبل فیلتر نمی‌کنه؟» → می‌تواند، ولی این یعنی هر Call Discovery هزینه‌ی واقعی چک‌کردن مجوز برای قابلیت‌هایی که فراخوان شاید هرگز حتی امتحان نکند می‌پردازد — طراحی فعلی Discovery را ارزان و همگانی نگه می‌دارد، پذیرفتن این‌که یک ۴۰۳ واقعی بعدی در زمان اجرا یک راه خوب و صادقانه برای اعلام «واقعاً نمی‌تونی این کار رو بکنی» است.

🚩 **پرچم‌های قرمز:**
فرض این‌که `DiscoverCapabilitiesAction` خروجی خودش را با مجوزهای فراخوان فیلتر می‌کند — از‌دست‌دادن این‌که این پلتفرم عمداً چک‌های مجوز Discovery و Execution را کاملاً جدا نگه می‌دارد، نه لایه‌بندی‌شده.

### Q10: چرا خودِ MCP Gateway صفر منطق کسب‌وکاری دارد — حتی چیزی به کوچکی «آیا این تخفیف مجازه»؟ اگه داشت واقعاً چی اشتباه می‌رفت؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک هزینه‌ی واقعی و ملموس نقض قانون طلایی بیان‌شده‌ی خودِ Gateway — نه فقط تکرار «Gateway نباید منطق کسب‌وکاری داشته باشه» به‌عنوان یک شعار.

✅ **جواب مدل:**
«چون کل ارزش Gateway بودن آن یک گلوگاه یکسان (فایل ۰۲، سؤال ۱۰) است که هر قابلیت از میانش عبور می‌کند — احراز‌هویت، محدودیت‌نرخ، مجوز، اجرا، قالب‌بندی پاسخ — و هیچی دیگر. لحظه‌ای که یک تصمیم واقعی کسب‌وکاری (حتی چیزی به‌باریکی «آیا این تخفیف مشخص مجاز است») داخل خودِ Gateway زندگی می‌کرد، آن تصمیم به هر قابلیتی که اتفاقاً از میانش عبور می‌کند Coupled می‌شد، به‌جای این‌که مالکش تنها ماژولی باشد که واقعاً می‌فهمدش. ملموس، این یعنی Gateway حالا باید قوانین تخفیف خودِ Commerce را برای گرفتن آن تصمیم درست بشناسد — یک وابستگی خاص-دامنه داخل تنها کلاسی که هر ماژول، کسب‌وکاری یا نه، از میانش می‌گذرد، دقیقاً همان نوع Couplingای که کل انضباط استقلال-ماژول این پلتفرم (فایل‌های ۰۲، ۰۸، ۱۴-۱۶) برای جلوگیریش ساخته شده. منطق کسب‌وکاری داخل خودِ Action ماژول مربوطه زندگی می‌کند، که Gateway فقط از طریق `CapabilityExecutionService` صدایش می‌زند بدون نیاز به فهمیدن چی واقعاً تصمیم گرفت — کار Gateway در رسیدن یک Call درست-احراز‌هویت‌شده، مجوز-داده‌شده، اعتبارسنجی‌شده به Handler درست متوقف می‌شود، هرگز در قضاوت این‌که آن Handler باید چه‌کاری بکند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا خودِ اعتبارسنجی ورودی نوعی منطق کسب‌وکاری نیست که داخل Gateway زندگی می‌کنه؟» → یک نوع عمداً کم‌عمق و عمومی — `MCPRequestValidationService` فقط چک می‌کند یک فیلد وجود دارد و با یک نوع اولیه‌ی اعلام‌شده مچ می‌شود (فایل ۰۵، سؤال ۳)، هرگز یک قانون واقعی دامنه مثل «آیا این درصد تخفیف واقعاً برای این Coupon معتبره»؛ آن چک عمیق‌تر هنوز کاملاً داخل خودِ Action ماژول مالک زندگی می‌کند.
2. «آیا این قانون تا حالا خم شده همون‌طور که قانون مرز-ماژول خم شده (استثنای Conformist خودِ Reporting، فایل ۰۸ سؤال ۹)؟» → هیچ‌جا مستندشده به‌عنوان خم‌شده — برخلاف استثنای Reporting، که یک انحراف محدوده‌شده و نام‌گذاری‌شده از یک قانون مشخص است، «بدون منطق کسب‌وکاری در Gateway» تا الان به‌عنوان یک مطلق در سراسر هر ماژول ساخته‌شده روی این پلتفرم برقرار مانده.

🚩 **پرچم‌های قرمز:**
رفتار با «منطق کسب‌وکاری رو از Gateway دور نگه‌دار» به‌عنوان یک ترجیح سبکی به‌جای یک الزام ساختاری — از‌دست‌دادن هزینه‌ی واقعی و ملموس Couplingای (Gateway که نیاز به دانش خاص-دامنه درباره‌ی هر ماژولی که از میانش می‌گذرد دارد) که از نقضش حتی یک‌بار دنبال می‌شد.

### Q11: هم UCP و هم MCP در این پلتفرم به‌عنوان «پروتکل» توصیف می‌شوند. تفاوت واقعی در چیزی که هرکدام استاندارد می‌کنند چیه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک تلفیق کوتاه و دقیق از دو الگوی استراتژیک مرتبط که از‌قبل جدا پوشش داده شدند (فایل ۰۸، سؤال‌های ۵ و ۱۱) — آیا کاندیدا می‌تواند تفاوت واقعی و مکمل را مختصر بیان کند، بدون قاطی‌کردنشان.

✅ **جواب مدل:**
«آن‌ها دو چیز متفاوت را استاندارد می‌کنند، و نام‌ها راحت این را قاطی می‌کنند. MCP (یک Open Host Service، فایل ۰۸ سؤال ۱۱) **مکانیزم دسترسی** را استاندارد می‌کند — چطور هر فراخوان، صرف‌نظر از این‌که چی می‌خواهد انجام دهد، از طریق یک Gateway مشترک یک قابلیت را کشف و اجرا می‌کند، به‌جای این‌که هر مصرف‌کننده به یک یکپارچگی خاص و یک‌باره نیاز داشته باشد. UCP (یک زبان-منتشرشده، فایل ۰۸ سؤال ۵) **شکل داده**ای را که از میان آن مکانیزم جریان می‌یابد استاندارد می‌کند — `UCPProduct` و خواهرانش تنها مدل نرمال‌شده‌ی Commerce هستند که هم داده‌ی بومی خودِ این پلتفرم و هم داده‌ی یک سیستم خارجی (WooCommerce، سؤال ۴ فایل ۰۸) بهش ترجمه می‌شوند، پس هیچ‌چیز پایین‌دستی هرگز لازم نیست بداند یا اهمیت دهد یک Product مشخص واقعاً از کجا آمده. باهم: MCP این است که چطور اصلاً یک قابلیت را *برسی*؛ UCP این است که *داده* وقتی وارد یکی که اتفاقاً با مفاهیم Commerce سروکار دارد می‌شوی چه شکلی است. یک قابلیت مثل `commerce.product.search` به هردو نیاز دارد — MCP یک فراخوان را اصلاً بهش می‌رساند، UCP تضمین می‌کند `Product`ای که برمی‌گرداند صرف‌نظر از منشأ واقعیش همان معنا را دارد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا هر قابلیت روی پلتفرم UCP رو درگیر می‌کنه؟» → نه — UCP مشخصاً یک نگرانی داده-Commerce است؛ یک قابلیت مثل `agent.reasoning.explain` (فایل ۱۷، سؤال ۱۱) نتیجه‌ی خاص-دامنه‌ی خودش را بدون هیچ درگیری UCP برمی‌گرداند، چون اصلاً هیچ سؤال بیرونی-در-برابر-داخلی داده-Commerد برای نرمال‌سازی آنجا نیست.
2. «آیا یک دامنه‌ی آینده تا حالا می‌تونه زبان-منتشرشده‌ی خودش رو مثل UCP خودِ Commerce نیاز داشته باشه؟» → واقعاً ممکن، و همان استدلال اعمال می‌شود — یک زبان-منتشرشده فقط وقتی ارزش هزینه‌ی طراحی را دارد که یک مفهوم Domain واقعی نیاز داشته باشد صرف‌نظر از این‌که واقعاً از کدام چندین منبع واقعی آمده یکسان به‌نظر برسد، که کل دلیل وجود خودِ UCP از اول است.

🚩 **پرچم‌های قرمز:**
رفتار با UCP و MCP به‌عنوان دو نام برای تقریباً یک ایده — از‌دست‌دادن این‌که یکی درباره‌ی *رسیدن* به یک قابلیت است و دیگری درباره‌ی *شکل داده*ای است که یک قابلیت مرتبط-با-Commerce اتفاقاً برمی‌گرداند.

### Q12: فایل‌های ۱۷ و ۱۸ باهم Orchestrator و Gateway را پوشش می‌دهند. با نگاه به هردو، آن یک چیزی که واقعاً فاز ۶ را بدون این‌که هرگز نه Gateway نه Core را لمس کند ممکن کرد چیه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک تلفیق بسته و در-سراسر-Part-F — کشیدن استدلال بسته‌ی خودِ فایل ۱۷ (فاز ۶ به صفر تغییر Core نیاز داشت) کنار جزئیات سطح-پروتکل همین فایل به یک توضیح مشخص و مکانیکی از *چطور* این واقعاً ممکن بود، نه فقط این‌که اتفاق افتاد.

✅ **جواب مدل:**
«خودِ مدل قابلیت که یک Registry واقعاً باز و قابل-آدرس‌دهی-با-نام است به‌جای یک لیست ثابت و Hardcode‌شده مکانیزم واقعی زیر ادعای بسته‌ی خودِ فایل ۱۷ است. هر قابلیت — چه `commerce.product.search`، وایرشده در فاز ۲، یا `agent.goal.execute`، وایرشده در فاز ۶ — دقیقاً به همان `CapabilityHandlerRegistry` می‌رسد، دقیقاً همان رفتار احراز‌هویت → محدودیت‌نرخ → مجوز → اجرا را داخل `AbstractMCPGatewayController` می‌گیرد، و در دقیقاً همان شکل پاسخ `GET /mcp/v1/capabilities` ظاهر می‌شود. Gateway هرگز لازم نبود یاد بگیرد اصلاً یک «Agent Orchestrator» چیست تا قابلیت‌هایش را درست خدمت کند — از دید خودِ Gateway، `agent.goal.execute` ساختاری از هر قابلیت Commerce که چهار فاز زودتر ثبت شده غیرقابل‌تشخیص است. این دقیقاً چیزی است که الگوی سطح-دوگانه‌ی خودِ سؤال ۶ همین فایل بهش بستگی دارد، و دقیقاً چیزی است که فایل ۱۷ (سؤال ۹) با وابستگی Orchestrator به مکانیزم‌های عمومی خودِ Core به‌جای هرچیزی که خاص-Core برایش ساخته شده باشد منظورش است: خودِ پروتکل از قبل، از فاز ۱ به بعد، به‌اندازه‌ی کافی عمومی بود که یک *نوع* کاملاً جدید ماژول — یکی که برنامه‌ریزی و اجرا می‌کند به‌جای مالکیت یک دامنه‌ی کسب‌وکاری — بتواند به‌عنوان فقط یک قابلیت نام‌گذاری‌شده‌ی دیگر ثبت شود، استفاده از زیرساختی که هیچ ایده‌ای نداشت، و لازم نبود داشته باشد، که هماهنگی AI روزی می‌آید.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا محدودیتی برای این‌که این باز-بودن مبتنی‌بر-Registry چه نوع ماژولی رو می‌تونه جای بده هست؟» → چیزی که تاریخچه‌ی خودِ این پلتفرم تا حالا بهش برخورده باشد نه — همان شکل ثبت باز که ۱۰ ماژول کسب‌وکاری و یک لایه‌ی هماهنگی اساساً متفاوت را با صفر تغییر Gateway جذب کرد هیچ دلیل ساختاری برای انتظار این‌که یک ماژول آینده و به‌طور مادی متفاوت به یکی نیاز داشته باشد نمی‌دهد.
2. «آیا این یعنی خودِ کد Gateway با گذر زمان برای جای‌دادن انواع بیشتری از قابلیت پیچیده‌تر شده؟» → نه، و این دقیقاً نکته‌ی واقعی است — خطِ‌لوله‌ی پنج-مرحله‌ای خودِ `AbstractMCPGatewayController` امروز دقیقاً همانی است که قبل از شروع فاز ۶ بود؛ رشد کاملاً در تعداد قابلیت‌های ثبت‌شده اتفاق افتاد، هرگز در مکانیزم ثبت و خدمت‌رسانی‌شان.

🚩 **پرچم‌های قرمز:**
جواب‌دادن با «برنامه‌ریزی خوب» یا «معماری محکم» به‌صورت انتزاعی — جواب قوی مکانیزم واقعی (یک Registry قابلیت قابل-آدرس‌دهی-با-نام که Gateway یکسان باهاش رفتار می‌کند) که ادعای انتزاعی را ملموس درست کرد را نام می‌برد، نه فقط دوباره بیان می‌کند که درست بود.
