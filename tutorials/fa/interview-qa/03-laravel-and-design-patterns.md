# ۰۳. Laravel و الگوهای طراحی

اگر [پیش‌آموزش](../pre-tutorial/05-الگوهای-طراحی-رایج.md) تعریف هر الگو را داده، این فایل یک لایه عمیق‌تر می‌رود: این الگوها در کد واقعی این پروژه دقیقاً چه شکلی هستند، و — مهم‌تر — کجا یک انتخاب ظریف Laravel-محور (مثل `bind()` در برابر `singleton()`) باعث یک باگ واقعی یا یک تصمیم آگاهانه شده.

---

### Q1: Service Container و Dependency Injection رو در این پروژه توضیح بده — یک مثال واقعی از یک Interface که چند Binding داره.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک عملی از Container، نه فقط تعریف کتابی «DI یعنی تزریق وابستگی».

✅ **جواب مدل:**
«بهترین مثال واقعی، `LLMClientInterface` در ماژول Agent Orchestrator است. سه پیاده‌سازی واقعی دارد — `OpenAIClient`، `ClaudeClient`، `OpenRouterClient` — و `AgentOrchestratorServiceProvider::register()` بر اساس مقدار `config('agent-orchestrator.llm.provider')` تصمیم می‌گیرد کدام‌یک تزریق شود:
```php
$this->app->bind(LLMClientInterface::class, function ($app) {
    return match (config('agent-orchestrator.llm.provider')) {
        'openai' => new OpenAIClient(...),
        'claude' => new ClaudeClient(...),
        'openrouter' => new OpenRouterClient(...),
        default => throw new InvalidArgumentException(...),
    };
});
```
هر کلاسی که `LLMClientInterface` را در سازنده‌ی خودش بخواهد (مثلاً `LLMPlanner`)، بدون این‌که بداند کدام Provider واقعی پشتش است، آن را می‌گیرد. این دقیقاً پایه‌ی Dependency Inversion در سطح Container است.»

🔁 **سوالات تعقیبی احتمالی:**
1. «اگه یک Provider جدید (مثلاً یک مدل محلی) اضافه کنی چی تغییر می‌کنه؟» → فقط یک `case` جدید در همین `match`؛ هیچ کلاس مصرف‌کننده‌ای تغییر نمی‌کند.
2. «اگه Interface بایند نشده باشه چی می‌شه؟» → Laravel سعی می‌کند خودش Interface را نمونه‌سازی کند، که چون Interface است شکست می‌خورد — یک خطای واضح در توسعه، نه یک باگ خاموش.

🚩 **پرچم‌های قرمز:**
تعریف Container فقط به‌عنوان «جایی که Laravel کلاس‌ها رو می‌سازه» بدون مثال واقعی از چرایی این الگو در این پروژه.

### Q2: فرق `bind()` و `singleton()` چیه؟ کجای این پروژه عمداً از `bind()` به‌جای `singleton()` استفاده شده، و چرا مهمه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
این یک سؤال ظریف و واقعی سطح Senior است — خیلی‌ها فرق سطحی را می‌دانند ولی پیامد عملی‌اش را در تست تجربه نکرده‌اند.

✅ **جواب مدل:**
«`singleton()` یعنی اولین باری که Interface خواسته شود، یک نمونه ساخته می‌شود و همان نمونه برای همیشه (در طول یک درخواست) برگردانده می‌شود. `bind()` یعنی هر بار Interface خواسته شود، Closure دوباره اجرا می‌شود — یک نمونه‌ی تازه، با آخرین مقدار `config()`. در `AgentOrchestratorServiceProvider`، `PlannerInterface`، `ReasoningEngineInterface`، و `LLMClientInterface` هرسه عمداً با `bind()` ثبت شده‌اند، نه `singleton()` — چون تست‌ها نیاز دارند وسط اجرا `config(['agent-orchestrator.planner.type' => 'llm'])` را عوض کنند و بلافاصله پیاده‌سازی متفاوت را ببینند. اگر این‌ها `singleton()` بودند، اولین Resolve همیشه برنده می‌ماند و تغییر Config بعدی هیچ اثری نمی‌داشت — دقیقاً همان گیر واقعی که `ConnectorRegistry` دارد (سؤال ۶ همین فایل).»

🔁 **سوالات تعقیبی احتمالی:**
1. «پس چرا همه‌چیز رو singleton نمی‌کنید که سریع‌تر باشه؟» → چون سرعت تفاوتش در این مقیاس (یک بار در هر درخواست) قابل‌اندازه‌گیری نیست، ولی هزینه‌ی تست‌ناپذیری بسیار واقعی است.
2. «توی Production این تفاوت اهمیت داره؟» → کمتر، چون Config در یک درخواست واقعی معمولاً وسط راه عوض نمی‌شود؛ ولی همین انعطاف، همان چیزی است که Showcase demo's own «Use real AI» toggle را ممکن می‌کند (بازبینی Config در وسط یک درخواست واقعی HTTP، نه فقط تست).

🚩 **پرچم‌های قرمز:**
نگفتن این‌که این یک تصمیم *آگاهانه* بوده — گفتن «فرقی نداره کدوم رو استفاده کنی» نشان می‌دهد فرد هیچ‌وقت به این گیر برنخورده.

### Q3: الگوی Repository در این پروژه دقیقاً چطور پیاده‌سازی شده؟ یک مثال کامل بزن.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا فقط اسم الگو را می‌دانید، یا واقعاً شکل کامل Interface → Eloquent Model → `toEntity()` را دیده‌اید؟

✅ **جواب مدل:**
«سه تکه‌ی ثابت: یک Interface در `Domain/Repositories` (مثلاً `ProductRepositoryInterface` با متدهایی مثل `findById()`, `save()`)، یک Eloquent Model در `Infrastructure/Models` که فقط ساختار جدول را نشان می‌دهد، و یک پیاده‌سازی در `Infrastructure/Repositories` (`EloquentProductRepository`) که این دو دنیا را به هم وصل می‌کند. نکته‌ی کلیدی، متد `toEntity()` است — هر Repository این متد را دارد که یک ردیف Eloquent را مستقیم به یک Entity خالص Domain تبدیل می‌کند، **بدون** عبور از متدهای عمومی تغییر وضعیت خودِ Entity (مثل `cancel()`)؛ چون Entity از پایگاه‌داده «بازسازی» می‌شود، نه «از نو ساخته». این تمایز مهم است — یک Entity تازه‌ساخته باید همه‌ی قوانین اعتبارسنجی سازنده را رد کند، ولی یک Entity که از یک ردیف معتبر پایگاه‌داده بازسازی می‌شود، نیازی به عبور دوباره از آن قوانین ندارد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا Model و Entity دو کلاس جدان، نه یک کلاس واحد؟» → چون Model باید Eloquent را بشناسد (فریم‌ورک‌وابسته)، Entity نباید — این دقیقاً همان مرز Clean Architecture است.
2. «Repository کِی write می‌کنه، کِی read؟» → هردو در همان Interface — `save()` هم برای Create هم Update استفاده می‌شود (Upsert)، تصمیمی که خودِ Repository بر اساس وجود `id` می‌گیرد.

🚩 **پرچم‌های قرمز:**
فکرکردن به این‌که Repository فقط «یک Wrapper دور Eloquent» است بدون تبدیل واقعی به یک Entity مستقل.

### Q4: الگوی Factory کجای این پروژه واقعاً استفاده شده؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک مثال واقعی، نه یک تعریف عمومی «Factory یعنی کلاسی که آبجکت می‌سازه».

✅ **جواب مدل:**
«دو مثال واقعی و متفاوت. اول، `Inventory::stock()` — یک متد استاتیک که یک نمونه‌ی تازه از `Inventory` با موجودی صفر می‌سازد؛ به‌جای این‌که هر Action مستقیم سازنده‌ی کلاس را با مقادیر پیش‌فرض صدا بزند. دوم، `MCPConfig::forVersion()` — یک Factory سبک‌تر که `baseUrl` را از `host` + `version` می‌سازد (`{host}/mcp/{version}`)، تا مهاجرت از v1 به v2 یک تغییر یک‌آرگومانی باشد، نه ویرایش دستی یک رشته‌ی URL. هردو مثال یک ویژگی مشترک Factory واقعی دارند: منطق ساخت آن‌قدر غیرپیش‌پاافتاده است (یا چند پارامتر پیش‌فرض، یا یک قاعده‌ی ترکیبی) که تکرارش در هر Call Site خطر تناقض دارد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا این‌ها static factory method هستن، نه یک کلاس Factory جدا؟» → چون منطق ساده‌تر از آن است که یک کلاس مستقل توجیه کند — یک قاعده‌ی کلی این پروژه: پیچیدگی معماری باید متناسب با پیچیدگی واقعی مسئله باشد.
2. «کجا از الگوی Factory استفاده نشده با این‌که می‌شد؟» → یک جواب صادق: خیلی از Entityهای ساده (مثل `Category`) فقط سازنده‌ی عمومی خودشان را دارند، چون هیچ منطق ساخت غیرپیش‌پاافتاده‌ای وجود ندارد که توجیه‌کننده‌ی یک Factory جدا باشد.

🚩 **پرچم‌های قرمز:**
اسم‌بردن از یک الگوی عمومی PHP (مثل Factory Method کتاب GoF) بدون توانایی اشاره به یک متد واقعی در این کد.

### Q5: الگوی Strategy/Connector — کجا و چند بار تکرار شده؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا شما یک الگو را فقط یک‌بار دیده‌اید، یا می‌فهمید یک الگوی خوب چرا در یک کدبیس واقعی تکرار می‌شود.

✅ **جواب مدل:**
«الگوی Connector — یک Interface مشترک + چند پیاده‌سازی قابل‌تعویض — دقیقاً **چهار بار** در این پلتفرم تکرار شده، هر بار برای یک نیاز کاملاً متفاوت: اتصال به فروشگاه‌های خارجی (`ProductConnectorInterface`، پیاده‌سازی واقعی `WooCommerceProductConnector`)، درگاه‌های ارسال (`ShippingProviderInterface`)، کانال‌های اطلاع‌رسانی (`ChannelSenderInterface` — ایمیل/پیامک/Webhook/درون‌برنامه‌ای)، و درگاه‌های پرداخت واقعی (`RedirectPaymentGatewayInterface` — Zibal/Stripe). هر چهارتا دقیقاً همان سه‌تکه را دارند: Interface، یک Registry برای انتخاب پیاده‌سازی با نام (سؤال بعدی)، و حداقل یک پیاده‌سازی ساختگی (Mock) برای تست بدون تماس واقعی شبکه. این تکرار نشان می‌دهد که این یک الگوی خاص یک بار حل‌شده نیست — بلکه یک قالب اثبات‌شده است که هر بار «چطور با یک سیستم بیرونی جایگزین‌پذیر ارتباط بگیریم» پیش آمده، همان قالب دوباره استفاده شده.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا هر بار الگو رو از صفر بازطراحی نکردید؟» → دقیقاً برعکس — هر بار همان الگوی قبلی کپی و تطبیق داده شد، چون قبلاً اثبات شده بود که کار می‌کند؛ این خودش یک نشانه‌ی معماری خوب است.
2. «کدوم پیاده‌سازی این الگو فقط Mock داره، پیاده‌سازی واقعی نداره؟» → درگاه‌های ارسال واقعی (USPS/FedEx/DHL) — چون اعتبارنامه‌ی واقعی برای تست صادقانه در دسترس نبود، مستند شده به‌عنوان یک هدف آینده، نه یک ادعای دروغین.

🚩 **پرچم‌های قرمز:**
دانستن فقط یک نمونه از این الگو (معمولاً WooCommerce) و نتوانستن گفتن که سه‌بار دیگر هم تکرار شده — نشان می‌دهد آشنایی سطحی و نه عمیق با کدبیس دارید.

### Q6: الگوی Registry چطور با Strategy فرق داره، و چرا جدا لازم بود؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
تمایز ظریف بین دو الگویی که معمولاً با هم اشتباه گرفته می‌شوند.

✅ **جواب مدل:**
«Strategy می‌گوید «چند راه برای انجام یک کار وجود دارد، همه با یک Interface». Registry جواب یک سؤال جدا می‌دهد: «در زمان اجرا، از روی یک رشته‌ی متنی (مثلاً `'zibal'`)، کدام پیاده‌سازی را انتخاب کنم؟» — یعنی Registry یک دفترچه‌ی نگاشت نام-به-پیاده‌سازی است که روی Strategy سوار می‌شود. `PaymentGatewayRegistry` دقیقاً همین کار را می‌کند: `register('zibal', $zibalGateway)` در `CommerceServiceProvider::boot()`، و بعد `PaymentGatewayRegistry::get('zibal')` هر جا لازم شد. یک نکته‌ی واقعی و مهم درباره‌ی Registry: چون معمولاً به‌شکل `singleton()` بایند می‌شود (یک نمونه‌ی واحد که همه‌ی پیاده‌سازی‌ها از قبل درونش ثبت شده‌اند)، نمی‌توانید مثل یک `bind()` ساده در وسط یک تست آن را جایگزین کنید — این یک گیر واقعی و مستندشده در `HANDOFF.md` است که برای اولین بار در تست‌های `ConnectorRegistry` کشف شد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چطور این گیر رو تو تست حل می‌کنید؟» → با ثبت مستقیم یک پیاده‌سازی Mock در همان نمونه‌ی Registry، به‌جای تلاش برای rebind کردن کل Registry.
2. «Registry همیشه singleton هست؟» → معمولاً بله، چون خودِ نگاشت (کدام نام به کدام پیاده‌سازی) در طول یک درخواست ثابت است — برخلاف `LLMClientInterface` (سؤال ۲) که خودِ پیاده‌سازی انتخاب‌شده ممکن است وسط تست عوض شود.

🚩 **پرچم‌های قرمز:**
یکی‌دانستن Registry و Strategy — این دو الگو مکمل هم‌اند، نه مترادف.

### Q7: الگوی Observer/Event Listener — رویدادهای دامنه Sync اجرا می‌شن یا Queued؟ چطور تصمیم گرفتید؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک واقعی تبادل بین سادگی (Sync) و مقیاس‌پذیری (Async) — نه فقط تکرار «رویدادها باید Async باشن چون بهتره».

✅ **جواب مدل:**
«همه‌ی Listenerهای این پروژه امروز Sync اجرا می‌شوند — یعنی همان درخواست HTTP که رویداد را پخش می‌کند، منتظر اجرای کامل هر Listener هم می‌ماند. این یک انتخاب آگاهانه، نه یک محدودیت فراموش‌شده است: `SendNotificationAction` (که به چند رویداد گوش می‌دهد) خودش منطق تلاش‌مجدد و Backoff دارد، ولی هنوز داخل همان چرخه‌ی درخواست اجرا می‌شود — چون هیچ Job‌ای برایش هنوز ساخته نشده. مستندات خودِ این کلاس صریحاً می‌گوید: تبدیل به Async فقط نیاز به پیچیدن همین فراخوانی در یک Job دارد، نه یک تغییر ساختاری. تصمیم به ماندن در Sync، هزینه‌ی واقعی دارد — اگر یک Listener کند باشد (مثلاً یک تماس شبکه‌ای که Backoff می‌کند)، کل پاسخ HTTP اصلی هم کند می‌شود؛ ولی برای مقیاس فعلی، سادگی دیباگ (کل زنجیره در یک Stack Trace واحد) بر این هزینه غالب شد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «کدوم Listener بیشترین ریسک کندشدن رو داره؟» → `WebhookSender` (از طریق `ChannelSenderRegistry`) چون به یک سرور بیرونی واقعی وصل می‌شود؛ اولین کاندید واقعی برای تبدیل به Job.
2. «چرا از اول Async نساختید اگه هزینه‌ی واقعی داره؟» → چون `QUEUE_CONNECTION=sync` از فاز ۱ در `phpunit.xml` تنظیم شده و هیچ Job‌ای تا فاز ۵ (Bulk Operations) وجود نداشت — زیرساخت Queue واقعی، وقتی واقعاً لازم شد، اضافه شد، نه پیش‌دستانه.

🚩 **پرچم‌های قرمز:**
«همه‌چیز باید همیشه Async باشه» بدون درک این‌که Async هزینه‌ی عملیاتی (Worker، صف، Observability) دارد که باید توجیه شود.

### Q8: Facade (الگوی Laravel) با Facade (الگوی طراحی) چه فرقی داره؟ در این پروژه کجا استفاده شده؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک تله‌ی رایج اصطلاحی — خیلی از توسعه‌دهندگان Laravel این دو را قاطی می‌کنند.

✅ **جواب مدل:**
«Facade در الگوی طراحی کلاسیک یعنی «یک نمای ساده جلوی یک زیرسیستم پیچیده» — که خودِ MCP Gateway در سطح کلان دقیقاً همین است. Facade در Laravel یک مکانیزم فنی خاص‌تر است: یک کلاس استاتیک که در پس‌زمینه یک نمونه‌ی واقعی از Container Resolve می‌کند (مثل `Cache::remember()`). این پروژه Facade نوع دوم را کم استفاده می‌کند و ترجیح می‌دهد Dependency Injection صریح باشد — به‌جز یک استثنای عمدی و مستند: SDK مخصوص Laravel (`packages/opencommerce-sdk-laravel`) یک Facade واقعی به نام `OpenCommerce` ارائه می‌دهد (`OpenCommerce::execute(...)`)، چون مخاطب این SDK توسعه‌دهنده‌ی بیرونی است که راحتیِ فراخوانی استاتیک‌گونه را به تزریق صریح ترجیح می‌دهد — درست برعکس فلسفه‌ی داخلی خودِ پلتفرم.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا داخل خودِ پلتفرم از Facade استفاده نمی‌کنید ولی توی SDK چرا؟» → چون داخل پلتفرم، تست‌پذیری صریح (Mock‌کردن یک وابستگی تزریق‌شده) اولویت دارد؛ در SDK، سرعت و راحتی توسعه‌دهنده‌ی نهایی اولویت دارد.
2. «Facade در Laravel چطور کار می‌کنه از پشت پرده؟» → از طریق `__callStatic()`، که فراخوانی استاتیک را به `Facade::getFacadeRoot()` (یک نمونه‌ی واقعی از Container) هدایت می‌کند.

🚩 **پرچم‌های قرمز:**
یکی‌دانستن این دو مفهوم کاملاً متفاوت با یک اسم مشترک — یک اشتباه رایج که بلافاصله سطح دانش را لو می‌دهد.

### Q9: Middleware در این پروژه کجا استفاده شده، و کجا عمداً استفاده *نشده*؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک این‌که هر ابزار (Middleware در برابر یک فراخوانی صریح Action) یک محدوده‌ی مناسب دارد، نه این‌که همیشه یک انتخاب «درست» جهانی وجود داشته باشد.

✅ **جواب مدل:**
«`ApiVersioning` یک Middleware واقعی است که روی `routes/mcp.php` می‌نشیند — چون فقط به خودِ Request خام (مسیر URL، هدر `Accept`) نیاز دارد، چیزی که قبل از رسیدن به Controller هم در دسترس است. در مقابل، نرخ‌محدودسازی عمداً یک Middleware **نیست** — یک فراخوانی صریح `EnforceRateLimitAction` داخل خودِ Controller، بعد از احراز هویت. دلیل: نرخ‌محدودسازی به `id` واقعی Agent نیاز دارد، که تا وقتی `AgentAuthenticationService` توکن را اعتبارسنجی نکرده، اصلاً شناخته‌شده نیست — یک Middleware که قبل از Controller اجرا می‌شود، این اطلاعات را ندارد. این یک قانون کلی این پروژه است: یک دغدغه‌ی مشترک بین چند مسیر، اگر فقط به خودِ Request نیاز دارد، Middleware می‌شود؛ اگر به چیزی نیاز دارد که فقط داخل Controller (بعد از احراز هویت) شناخته می‌شود، یک Action صریح می‌ماند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «می‌شد Middleware رو بعد از یک Middleware احراز هویت جدا گذاشت؟» → از نظر فنی شدنی بود، ولی این پروژه از ابتدا احراز هویت را داخل خودِ Controller (`AgentAuthenticationService`) نگه داشته، نه یک Guard/Middleware Laravel — پس این ترتیب طبیعی‌تر بود.
2. «کجای دیگه همین قانون دیده می‌شه؟» → پنل مدیریت انسانی برعکس این را نشان می‌دهد — چون از Session/Guard واقعی Laravel استفاده می‌کند، `auth`/`admin` Middleware استاندارد کاملاً منطقی است، چون احراز هویت آنجا واقعاً قبل از Controller اتفاق می‌افتد.

🚩 **پرچم‌های قرمز:**
«همه‌چیز باید Middleware باشه چون تمیزتره» — بدون توجه به این‌که Middleware به چه اطلاعاتی در چه لحظه‌ای دسترسی دارد.

### Q10: چرا هر Entity یک DTO مجزا داره؟ چرا مستقیم خودِ Entity رو برنمی‌گردونید؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک مرز بین یک شیء داخلی (که می‌تواند تغییر کند) و یک قرارداد بیرونی (که نباید بی‌هشدار تغییر کند).

✅ **جواب مدل:**
«اگر یک Entity مستقیم به‌عنوان پاسخ JSON برگردانده شود، هر تغییر داخلی روی آن Entity (مثلاً افزودن یک متد جدید، یا تغییر یک نام فیلد داخلی برای خوانایی بهتر) خودکار قرارداد بیرونی MCP را هم می‌شکند — چیزی که هیچ کلاینتی (مخصوصاً یک ایجنت هوش مصنوعی که خودش کد را نمی‌خواند) نباید غافلگیرش کند. هر Entity یک `*Data` مخصوص خودش دارد (مثلاً `ProductData`) که Actionها آن را می‌سازند و برمی‌گردانند — یک لایه‌ی میانی صریح که شکل «بیرونی» را از شکل «داخلی» جدا نگه می‌دارد. حتی جالب‌تر: DTOهای این پروژه معمولاً `toArray()` با کلیدهای `snake_case` دارند (قرارداد سیم، نه قرارداد PHP)، درحالی‌که خودِ کلاس‌های PHP از `camelCase` استفاده می‌کنند — یعنی این لایه، تبدیل قرارداد کدنویسی به قرارداد سیم را هم انجام می‌دهد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این باعث تکرار کد نمی‌شه؟» → کمی، ولی این تکرار عمدی و ارزان است در مقابل ریسک نشت جزئیات داخلی به یک قرارداد عمومی.
2. «همیشه یک DTO دقیقاً معادل یک Entity هست؟» → نه لزوماً — بعضی DTOها (مثل `ExecutionResultData`) چند فیلد اختیاری اضافه دارند که هیچ Entity معادلی ندارند، دقیقاً برای همین منظور طراحی شده‌اند.

🚩 **پرچم‌های قرمز:**
«چون همیشه همینطوری Laravel یاد می‌ده» — بدون توضیح دلیل معماری واقعی.

### Q11: یک باگ واقعی که به‌خاطر یک الگوی طراحی اشتباه استفاده‌شده به وجود اومد، و چطور پیداش کردی؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
این سؤال کلاسیک «داستان دیباگ واقعی» است — جواب باید یک داستان کامل با یک نتیجه‌ی مشخص باشد، نه یک جمله‌ی کلی.

✅ **جواب مدل:**
«دقیقاً همان گیر Registry-در-برابر-bind که در سؤال ۶ اشاره کردم — ولی داستان کاملش این است: یک تست می‌خواست وسط اجرا یک پیاده‌سازی Mock را جایگزین یک Connector واقعی درون `ConnectorRegistry` کند، به همان روشی که برای Interfaceهای عادی (`bind()` مجدد در تست) کار می‌کرد. ولی چون `ConnectorRegistry` خودش یک Singleton بود که همه‌ی پیاده‌سازی‌های واقعی از قبل، در `boot()`، درونش ثبت شده بودند، rebind‌کردن خودِ Interface کمکی نمی‌کرد — نمونه‌ی از قبل ساخته‌شده‌ی Registry، پیاده‌سازی قدیمی را همچنان نگه می‌داشت. این باعث شد یک تست به‌جای Mock، واقعاً به یک پیاده‌سازی نزدیک به شبکه برخورد کند. راه‌حل، نه تغییر معماری Registry (که برای دلایل دیگر درست بود)، بلکه ثبت مستقیم Mock در همان نمونه‌ی Registry قبل از اجرای تست بود. این را در `HANDOFF.md` به‌عنوان یک «گوچا»ی مستند برای هر توسعه‌دهنده‌ی آینده ثبت کردیم، تا دوباره کسی وقتش را برای همین گیر تلف نکند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا Registry رو خودش قابل rebind نکردید؟» → چون Singleton‌بودنش برای رفتار Production درست بود (نگاشت نام-به-پیاده‌سازی نباید وسط یک درخواست عوض شود)؛ مشکل فقط در تست بود، نه در طراحی خودِ الگو.
2. «این باگ رو چطور برای همیشه جلوگیری کردید؟» → با مستندسازی صریح این گوچا، نه با یک راه‌حل خودکار — یک تصمیم آگاهانه که سادگی معماری را به قیمت یک نکته‌ی مستندشده حفظ کرد.

🚩 **پرچم‌های قرمز:**
نداشتن هیچ داستان واقعی برای این سؤال — یک نشانه‌ی قوی که فرد هرگز عمیقاً با تست‌نویسی این کدبیس درگیر نشده.

### Q12: چرا `MCPExceptionHandler` از یک‌جایی به بعد باید Container-Resolved بشه، نه `new` بشه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک مثال دقیق و واقعی از این‌که چطور یک نیاز جدید، یک تصمیم قدیمی و به‌ظاهر بی‌ضرر را می‌شکند.

✅ **جواب مدل:**
«در `bootstrap/app.php`، بخش `$exceptions->render()` در ابتدا مستقیم `new MCPExceptionHandler()` صدا می‌زد — کاملاً بی‌ضرر، چون این کلاس هیچ وابستگی سازنده‌ای نداشت. وقتی چندزبانگی اضافه شد، این کلاس برای اولین بار نیاز واقعی به وابستگی (`LanguageDetector`، `TranslationServiceInterface`) پیدا کرد تا بتواند `error.localized_message` را در پاسخ خطا بگنجاند. `new MCPExceptionHandler()` دیگر کار نمی‌کرد — یا باید این دو وابستگی را دستی می‌ساختیم (که یعنی تکرار همان منطقی که Container قرار بود انجام دهد)، یا از `app(MCPExceptionHandler::class)` استفاده می‌کردیم تا Container خودش این‌ها را Resolve کند. این تغییر یک‌خطی، دقیقاً همان لحظه‌ای بود که فهمیدیم `new`کردن دستی یک کلاس، یک تصمیم قابل‌برگشت نیست — هر لحظه ممکن است آن کلاس یک وابستگی جدید نیاز پیدا کند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این یعنی همیشه باید همه‌چیز رو Container-Resolved کنیم؟» → نه لزوماً — Value Objectها و Entityهای Domain عمداً همیشه با `new` ساخته می‌شوند، چون آن‌ها هیچ وابستگی بیرونی ندارند و نباید هم داشته باشند؛ این قانون فقط برای کلاس‌هایی صادق است که وابستگی واقعی می‌گیرند.
2. «چطور فهمیدید این تغییر لازمه؟» → همان لحظه که کلاس `LanguageDetector` را به سازنده‌ی `MCPExceptionHandler` اضافه کردیم، هر جای کد که `new MCPExceptionHandler()` صدا می‌زد، بلافاصله در تست خطای «آرگومان اجباری داده نشده» می‌داد — خودِ سیستم نوع‌ها این مشکل را فوراً لو داد.

🚩 **پرچم‌های قرمز:**
ندانستن فرق `new` کردن دستی و Container-Resolve کردن، یا فکرکردن که این دو همیشه معادل‌اند.
