# ۱۲. امنیت

نرخ‌محدودسازی (فایل‌های ۰۲، ۰۳، ۰۵، ۱۱)، نگاشت استثنا-به-کد-HTTP با Marker Interface (فایل ۰۵)، و چطور امضای HMAC یک Webhook تست می‌شود (فایل ۰۶) از قبل از زاویه‌های دیگر پوشش داده شدند. این فایل جایی است که آن‌ها، و هرچیزی که هنوز پوشش داده نشده، مشخصاً از زاویه‌ی امنیت بررسی می‌شوند: دو مکانیزم کاملاً جدای احراز هویت این پلتفرم، دسته‌بندی‌های واقعی OWASP روی کد واقعی، مدیریت راز (Secrets)، و چند نکته‌ی صادقانه‌ ناتمام که این پروژه به‌جای پنهان‌کردن، نام‌گذاری می‌کند.

---

### Q1: این پلتفرم دو نوع فراخوان کاملاً متفاوت رو احراز هویت می‌کنه — یک Agent هوش مصنوعی و یک User انسانی پنل مدیریت. هردو مکانیزم رو توضیح بده و بگو چرا هرگز با هم ادغام نشدن.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا «احراز هویت» را یک مفهوم عمومی واحد می‌داند، یا واقعاً می‌داند این پلتفرم دو مکانیزم ساختاراً متفاوت و عمداً جدا اجرا می‌کند.

✅ **جواب مدل:**
«یک Agent روی هر درخواست بدون‌حالت (Stateless) با یک توکن Bearer احراز هویت می‌شود — `AgentAuthenticationService` آن را می‌خواند، هش می‌کند، و Agent مالک را با آن هش در `agent_tokens` پیدا می‌کند (فایل ۰۲، سؤال ۳). یک `User` پنل مدیریت با یک ورود ایمیل/رمز عبور احراز هویت می‌شود که یک نشست واقعی و مبتنی‌بر Cookie راه‌اندازی می‌کند — `AuthenticateUserAction` رمز عبور را تأیید می‌کند، بعد `LoginController` واقعاً `Auth::loginUsingId()` را صدا می‌زند تا نشست شروع شود. این دو هرگز ادغام نشدند، به یک دلیل ساختاری، نه فقط سلیقه‌ای: یک کلاینت MCP یک فراخوان API بدون‌حالت است، بدون مرورگر، بدون سبد Cookie، و بدون هیچ مفهومی از «لاگین‌مانده»؛ یک نشست برایش بی‌معنا خواهد بود. یک اپراتور انسانی، در مقابل، واقعاً می‌خواهد بین بارگذاری‌های صفحه لاگین‌مانده بماند. مجبورکردن یک مکانیزم برای سرویس‌دهی به هردو، یا یعنی Agentها را مجبور به حمل Cookie کنی (بی‌فایده برای یک API بدون‌حالت) یا یک انسان را مجبور کنی روی هر کلیک دوباره اطلاعات هویتی بفرستد (یک تجربه‌ی کاربری افتضاح) — دو انتقال کاملاً متفاوت برای دو نوع کاملاً متفاوت فراخوان.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این یعنی پنل مدیریت به محافظت CSRF نیاز داره ولی دروازه‌ی MCP نه؟» → دقیقاً — CSRF حمله‌ای است که روی اطلاعات هویتی محیطی (Ambient) که یک مرورگر خودکار می‌فرستد سوار می‌شود (Cookie)؛ یک درخواست با توکن Bearer هیچ اطلاعات هویتی محیطی‌ای ندارد که یک صفحه‌ی مخرب بتواند مرورگر را گول بزند بفرستد، پس `routes/mcp.php` اصلاً به توکن CSRF نیازی ندارد، درحالی‌که `/dashboard/*` و `/showcase` (هردو مبتنی‌بر نشست) دقیقاً برای گرفتن آن، داخل گروه Middleware استاندارد `web` قرار می‌گیرند.
2. «آیا ممکنه یک آدم واقعی، هم `User` باشه هم یک Agent رو کنترل کنه؟» → بله، از قضا — ولی پلتفرم هیچ مفهومی که این دو را به‌هم وصل کند ندارد؛ دو هویت کاملاً مستقل که اتفاقاً توسط همان انسان اجرا می‌شوند.

🚩 **پرچم‌های قرمز:**
پیشنهاد «فقط از یک سیستم Auth یکپارچه برای هردو استفاده کن» — این دلیل واقعی وجود دو سیستم را از دست می‌دهد: آن‌ها دو مسئله‌ی متفاوت را حل می‌کنند (یک فراخوان API بدون‌حالت در برابر یک نشست انسانی با‌حالت)، نه یک مسئله که تصادفاً دوبار حل شده.

### Q2: توکن‌های Bearer یک Agent در پایگاه‌داده به‌صورت متن ساده ذخیره می‌شن؟ ویژگی امنیتی واقعی اینجا چیه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا فرض یک طراحی ساده‌لوحانه‌ی «توکن رو ذخیره کن، رشته‌ها رو مقایسه کن» را دارد، یا واقعاً الگوی هش-بعد-جستجو و چرایی اهمیتش را می‌فهمد.

✅ **جواب مدل:**
«نه — `AgentAuthenticationService` توکن Bearer دریافتی را هش می‌کند و آن را با آن هش جستجو می‌کند، هرگز خودِ مقدار خام توکن را ذخیره یا مقایسه نمی‌کند (فایل ۰۲، سؤال ۳). این یعنی یک Dump دزدیده‌شده از پایگاه‌داده مستقیم توکن‌های قابل‌استفاده تحویل نمی‌دهد، آن‌طور که یک جدول توکن-متن-ساده می‌داد — همان اصلی که Hash رمز عبور را محافظت می‌کند، اینجا روی یک اطلاعات هویتی API به‌جای یک رمز عبور ورود اعمال شده. یک تفاوت عمدی از `HashedPassword` (سؤال ۴ همین فایل): یک رمز عبور ورود به‌ندرت چک می‌شود (یک‌بار به‌ازای هر نشست)، پس درست است از `bcrypt` استفاده شود، الگوریتمی که عمداً کند است تا در برابر Brute-Force مقاومت کند. یک توکن Agent روی **هر تک درخواست API** چک می‌شود — استفاده از یک الگوریتم عمداً کند آنجا تأخیر واقعی و انباشته‌شونده به هر درخواستی که این پلتفرم سرویس می‌دهد اضافه می‌کرد، پس یک Hash رمزنگاری سریع ابزار درست برای دقیقاً این کار است، نه همان Hash کند رمزهای عبور.»

🔁 **سوالات تعقیبی احتمالی:**
1. «پس اطلاعات هویتی مختلف این سیستم استراتژی‌های Hashing متفاوت استفاده می‌کنن؟» → بله، عمداً — استراتژی Hashing درست به این بستگی دارد که مقدار چقدر مکرر تأیید می‌شود، نه یک قانون یکسان-برای-همه.
2. «اگه یک توکن لو بره چی میشه؟» → هیچ UI ابطال-توکن مشخصی در محدوده‌ی این کتابچه پوشش داده نشده، ولی توکن دقیقاً متعلق به یک ردیف Agent است، پس غیرفعال‌کردن/چرخاندن توکن همان Agent مسیر واقعی کاهش ریسک است.

🚩 **پرچم‌های قرمز:**
فرض این‌که یک توکن Bearer فقط به‌عنوان یک رشته‌ی ساده در برابر یک ستون ذخیره‌شده مقایسه می‌شود — دقیقاً همان طراحی ساده‌لوحانه‌ای است که این الگوی هش-بعد-جستجو از آن دوری می‌کند.

### Q3: ورود `User` پنل مدیریت رو از سر تا ته ردیابی کن. مرز دقیق بین «تأیید این‌که واقعاً خودشه» و «شروع یک نشست واقعی» کجاست، و چرا اونجا جدا شده؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا می‌فهمد *چرا* تأیید اطلاعات هویتی و راه‌اندازی نشست دو قدم جدا هستند، نه فقط این‌که هستند.

✅ **جواب مدل:**
«`AuthenticateUserAction` (لایه‌ی Application) خودِ چک اطلاعات هویتی را انجام می‌دهد — `User` را با ایمیل بارگذاری می‌کند و `HashedPassword::verifyPassword()` را روی رمز عبور ارسالی صدا می‌زند، و فقط در صورت موفقیت `UserData` برمی‌گرداند، وگرنه `InvalidCredentialsException` پرتاب می‌کند. `LoginController` (لایه‌ی HTTP) فقط *بعد* از موفقیت آن Action، خودِ `Auth::loginUsingId()`ی Laravel — چیزی که واقعاً Cookie نشست احراز‌هویت‌شده را می‌نویسد — را صدا می‌زند. این دقیقاً همان جدایی «اول هویت رو تأیید کن، بعد جداگانه به این انتقال خاص وفقش بده» است که `AgentAuthenticationService` از قبل برای MCP برقرار کرده بود (سؤال ۱ همین فایل)، یک لایه بالاتر اعمال‌شده. دلیل این‌که مشخصاً برای امنیت اهمیت دارد: تأیید رمز عبور منطق کسب‌وکاری واقعی است که سزاوار تست‌شدن کاملاً مستقل از ماشین‌آلات نشست Laravel است — و، به‌همان‌اندازه مهم، هیچ‌وقت یک نشست واقعی و مبتنی‌بر Cookie روی چکی از اطلاعات هویتی که هنوز کاملاً موفق نشده شروع نمی‌شود.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا `AuthenticateUserAction` می‌تونه خودش تصادفاً یک نشست شروع کنه؟» → نه — هیچ وابستگی به `Auth`/`Session` اصلاً ندارد؛ یک کلاس ساده‌ی لایه‌ی Application است که فقط داده برمی‌گرداند یا پرتاب می‌کند، همان استقلال از فریم‌ورک که هر Action دیگری در این کدبیس دارد.
2. «یک ورود نامعتبر واقعاً برای فراخوان چه شکلیه؟» → یک پیام خطای ترجمه‌شده و عمومی (`InvalidCredentialsException`) که عمداً «ایمیل غلط» را از «رمز عبور غلط» تشخیص نمی‌دهد — همان اصل حداقل‌سازی اطلاعات که سؤال ۵ همین فایل برای جستجوهای بین-Tenant پوشش می‌دهد.

🚩 **پرچم‌های قرمز:**
توصیف ورود به‌عنوان «فقط `Auth::attempt()` رو صدا بزن» بدون تشخیص این‌که این پروژه عمداً منطق واقعی تأیید اطلاعات هویتی را ابتدا در یک Action مستقل از فریم‌ورک نگه می‌دارد — یک تمایز معماری ظریف ولی واقعی.

### Q4: چرا `HashedPassword` مستقیم `password_hash()`/`password_verify()`ی خودِ PHP را صدا می‌زنه، به‌جای Facade `Hash`ی Laravel؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا می‌تونه یک تصمیم امنیتی رو به انضباط معماری خودِ این پروژه وصل کنه، به‌جای این‌که آن را یک انتخاب دلخواه در نظر بگیرد.

✅ **جواب مدل:**
«هر کلاس Domain در این کدبیس عمداً مستقل از فریم‌ورک است — با PHPUnit خالص قابل‌تست، بدون نیاز به Container Laravel (`PricingService`، `WorkflowEvaluator`، و هر Domain Service دیگری از قبل همین را رعایت می‌کنند). `HashedPassword` اولین Value Objectی بود که واقعاً به Hashing رمزنگاری نیاز داشت، و استفاده از Facade `Hash`ی Laravel آن را اولین استثنای لایه‌ی Domain به این قانون می‌کرد — بدون هیچ فایده‌ی واقعی، چون کتابخانه‌ی استاندارد خودِ PHP (`password_hash()`/`password_verify()`، که زیرش از bcrypt استفاده می‌کند) از قبل دقیقاً همان چیزی که لازم است را انجام می‌دهد، با صفر وابستگی به فریم‌ورک. این کار `HashedPassword` را کاملاً مستقل و قابل‌تست واحد نگه می‌دارد، دقیقاً مثل هر Value Object دیگری در این پروژه، درحالی‌که هنوز از یک الگوریتم Hashing واقعی، استاندارد صنعتی، و تطبیقی زیرش استفاده می‌کند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «پیاده‌سازی bcryptی `password_hash()` واقعاً به‌اندازه‌ی Facade `Hash`ی Laravel امن هست؟» → بله — خودِ Facade `Hash`ی Laravel چیزی نیست جز یک لفاف نازک روی دقیقاً همان توابع PHP؛ هیچ تفاوت امنیتی واقعی نیست، فقط یک تفاوت وابستگی به فریم‌ورک.
2. «این تصمیم برای یک Value Object با نیاز واقعاً Laravel-only تغییر می‌کرد؟» → نه — قانون پروژه «مستقل از فریم‌ورک بمان مگر واقعاً معادلی نباشد» است، و این VO دقیقاً همان موردی است که یک معادل مستقل از فریم‌ورک از قبل وجود داشت.

🚩 **پرچم‌های قرمز:**
ادعای این‌که `password_hash()` «کمتر امن» از یک Facade فریم‌ورک است — یک سوءتفاهم واقعی درباره‌ی این‌که خودِ Facade واقعاً چه چیزی را لفاف می‌کند.

### Q5: دو مکانیزم واقعی و مشخص تو این کدبیس بگو که در برابر دسته‌ی «Broken Access Control» OWASP دفاع می‌کنن.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا دانش OWASP روی همین کدبیس خاص پایه‌گذاری شده، نه به‌شکل انتزاعی حفظ‌شده.

✅ **جواب مدل:**
«اول، الگوی ۴۰۴-نه-۴۰۳ روی هر جستجوی بین-Tenant با id (فایل ۱۱، سؤال ۵) — یک Agent که یک id واقعی متعلق به یک Tenant دیگر را حدس می‌زند، دقیقاً همان پاسخی را می‌گیرد که انگار آن id اصلاً هرگز وجود نداشته، پس هیچ پاسخی هرگز تأیید نمی‌کند «این منبع واقعیه، فقط ازش منع شدی». دوم، ترتیب عمدی داخل خودِ خط لوله‌ی واقعی درخواست MCP (فایل ۰۲، سؤال ۳): احراز هویت، بعد نرخ‌محدودسازی، بعد اختیارسنجی (`CheckPermissionAction`) — و فقط *بعد* از موفقیت آن، اعتبارسنجی ورودی اصلاً اجرا می‌شود. آن ترتیب یک تصمیم واقعی کنترل دسترسی است، نه یک توالی دلخواه: یک Agent که مجوز یک قابلیت را ندارد، هرگز هیچ‌چیزی درباره‌ی این‌که ورودی‌اش معتبر بود یا نه یاد نمی‌گیرد، چون اعتبارسنجی هرگز برای درخواستی که از همان اول مجوز نداشته اجرا نمی‌شود. هردو مکانیزم یک اصل مشترک دارند — هرگز اجازه نده یک فراخوان بدون‌مجوز بیشتر از «نه» درباره‌ی یک منبع یا یک درخواست بفهمد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «اختیارسنجی یک‌بار به‌ازای هر درخواست چک می‌شه یا به‌ازای هر قابلیت؟» → به‌ازای هر قابلیت، هربار — `CheckPermissionAction` مشخصاً `requiredPermissions` قابلیتِ *فراخوانی‌شده* را چک می‌کند، نه یک دروازه‌ی کلی «آیا این Agent اصلاً لاگین کرده».
2. «این ترتیب هیچ‌وقت تو مسیر خوشحال هزینه‌ای داره؟» → نه — اعتبارسنجی ورودی یک درخواستی که آخرش بدون‌مجوز درمی‌آید، هرحال کاری هدررفته بود؛ چک‌کردن اختیارسنجی اول، هم امن‌تر و هم ارزان‌تر است.

🚩 **پرچم‌های قرمز:**
فقط گفتن «ما مجوزها رو چک می‌کنیم» بدون جزئیات مشخص ۴۰۴-در-برابر-۴۰۳ و ترتیب — یک جواب عمومی که درک واقعی و خاص کدبیس را نشان نمی‌دهد.

### Q6: چند مثال واقعی از درست‌عمل‌کردن این پروژه در دسته‌ی «Cryptographic Failures» OWASP بزن — و یک جا که هنوز صادقانه ناتمامه.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
تعادل — آیا کاندیدا می‌تواند برنده‌های واقعی را نام ببرد بدون این‌که وانمود کند پروژه بی‌عیب است.

✅ **جواب مدل:**
«سه برنده‌ی واقعی و مشخص: bcrypt برای هر رمز عبور `User` پنل مدیریت (سؤال ۴)، توکن‌های Bearer هش‌شده — هرگز متن‌ساده — Agent (سؤال ۲)، و `hash_equals()` که برای هر مقایسه‌ی رشته‌ی حساس-به-زمان‌بندی که این کدبیس واقعاً انجام می‌دهد استفاده می‌شود — هم گیت رمزعبور نمایشی Showcase و هم چک امضای HMAC خودِ `StripeWebhookVerifier` مشخصاً از آن استفاده می‌کنند تا از نشت حمله‌ی زمان‌بندی از یک مقایسه‌ی ساده‌ی `===` جلوگیری کنند، که می‌تواند از طریق تفاوت زمان پاسخ، تعداد کاراکترهای ابتدایی مطابق را فاش کند. نکته‌ی صادقانه‌ی ناتمام: اطلاعات ورود کانکتورهای بیرونی (WooCommerce، و به همان شکل درگاه‌های پرداخت) یک‌بار در مقادیر خام `.env` به‌ازای هر Deployment زندگی می‌کنند، نه رمزنگاری‌شده-در-حالت-سکون در یک جدول اطلاعات ورود Tenant-محور — فایل ۱۱ (سؤال ۱۰) این شکاف را کامل به‌عنوان یک محدودیت چندمستأجری پوشش می‌دهد، و این دقیقاً همان شکاف است از زاویه‌ی خالص مدیریت راز: امروز، خواندن آن فایل `.env` یعنی خواندن اطلاعات ورود همه‌ی Tenantهای وصل‌شده با هم.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا مشخصاً `hash_equals()` به‌جای `===`؟» → `===` روی رشته‌ها در اولین بایت نامطابق کوتاه‌مدار می‌شود، پس زمان اجرایش فاش می‌کند حدس مهاجم چند کاراکتر ابتدایی درست داشته — `hash_equals()` صرف‌نظر از این‌که نامطابقت کجاست، در زمان ثابت اجرا می‌شود و این کانال جانبی را می‌بندد.
2. «bcrypt امروز هنوز به‌اندازه‌ی کافی قوی در نظر گرفته می‌شه؟» → بله، با یک فاکتور هزینه‌ی به‌درستی تنظیم‌شده — یک انتخاب استاندارد و پذیرفته‌شده باقی می‌ماند؛ ریسک واقعی در این حوزه بیشتر یک `hash_equals()` گم‌شده جایی است تا ضعف خودِ bcrypt.

🚩 **پرچم‌های قرمز:**
ندانستن این‌که چرا اصلاً `hash_equals()` وجود دارد، یا ادعای این‌که این پروژه *هیچ* شکاف رمزنگاری‌ای ندارد — هم یک جزئیات فنی از‌دست‌رفته و هم یک مشکل اعتبار در برابر مصاحبه‌کننده‌ای که از قبل می‌داند کدبیس محدودیت‌های صادقانه‌مستندشده دارد.

### Q7: `StripeWebhookVerifier` یک تحمل زمانی چک می‌کنه، نه فقط این‌که امضای HMAC مطابقت داره. این دقیقاً در برابر چه حمله‌ای دفاع می‌کنه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک حمله‌های Replay مشخصاً — یک امضا به‌تنهایی کافی نیست، و دانستن دقیقاً چرا.

✅ **جواب مدل:**
«یک امضای HMAC معتبر، به‌تنهایی، فقط ثابت می‌کند یک Payload واقعاً یک‌جایی توسط Stripe امضا شده — چیزی درباره‌ی *کِی* نمی‌گوید. بدون چک زمانی، مهاجمی که یک‌بار یک درخواست Webhook امضاشده‌ی قانونی را گرفته باشد (یک لاگ شبکه، یک Proxy مختل‌شده) می‌تواند همان درخواست را تا ابد دوباره بفرستد، و امضا هربار از نظر ریاضی درست چک خواهد شد — یک حمله‌ی کلاسیک Replay. `StripeWebhookVerifier` Payload امضاشده را به‌شکل `"{timestamp}.{raw_body}"` می‌سازد و هرچیزی قدیمی‌تر از یک پنجره‌ی تحمل ۳۰۰-ثانیه‌ای را رد می‌کند، پس حتی یک Replay کاملاً معتبر و درست‌امضاشده از یک درخواست قدیمی، فقط بر اساس کهنه‌بودن رد می‌شود. دو جزئیات دیگر که ارزش دانستن دارند: هر مطابقتی با **هرکدام** از امضاهای `v1`ی که Stripe شامل می‌کند را قبول می‌کند (Stripe چندتا را در طول پنجره‌ی چرخش راز خودش می‌فرستد، پس فقط نیازداشتن به مطابقت یکی، چرخش را امن نگه می‌دارد)، و عمداً یک امضای `v0` را کاملاً نادیده می‌گیرد — یک طعمه‌ی مستندشده‌ی حمله‌ی Downgrade که مستندات خودِ Stripe توصیف می‌کنند، چون قبول‌کردن یک طرح ضعیف‌تر و قدیمی‌تر وقتی یک طرح قوی‌تر در همان Payload موجود است، دقیقاً همان‌طور که یک حمله‌ی Downgrade کار می‌کند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این واقعاً بدون یک حساب واقعی Stripe چطور تست میشه؟» → فایل ۰۶ (سؤال ۱۲) مستقیم این را پوشش می‌دهد — یک Payload تست خودامضاشده‌ی واقعی با همان فرمول دقیق، شامل یک مورد که اثبات می‌کند یک امضای دست‌کاری‌شده رد می‌شود.
2. «چرا مشخصاً ۳۰۰ ثانیه؟» → توصیه‌ی مستندشده‌ی خودِ Stripe — به‌اندازه‌ی کافی طولانی که کج‌شدگی معمول شبکه/ساعت را تحمل کند، به‌اندازه‌ی کافی کوتاه که یک درخواست گرفته‌شده برای Replay خیلی زود بی‌فایده شود.

🚩 **پرچم‌های قرمز:**
گفتن «فقط چک امضا کافیه» — از‌دست‌دادن این‌که یک امضا اصالت را ثابت می‌کند، نه تازگی را، که دقیقاً همان شکافی است که چک زمانی می‌بندد.

### Q8: مسیرهای عمومی Callback و Webhookی پرداخت از یک جستجوی Tenant-*نامحدود* عمدی (`findByIdUnscoped()`) استفاده می‌کنن. این با هرچیزی که فایل ۱۱ درباره‌ی ایزوله‌سازی Tenant تثبیت کرد، تناقض نداره؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا می‌تواند درباره‌ی یک استثنای واقعی و عمدی به قانونی که تازه یاد گرفته استدلال کند، نه این‌که کورکورانه از آن دفاع یا آن را رد کند.

✅ **جواب مدل:**
«اول به‌نظر یک تناقض می‌رسد، ولی نیست، چون این دو مسیر از نظر ساختاری اصلاً نمی‌توانند یک `AuthContext` حمل کنند — Redirect مرورگر خودِ یک درگاه پرداخت یا یک Webhook سرور-به-سرور هیچ توکن Bearerی از یک Agent برای ارائه ندارد، پس از همان اول هیچ Tenant احراز‌هویت‌شده‌ای برای Scope‌کردن یک جستجو وجود ندارد. امنیت اینجا از یک مکانیزم کاملاً متفاوت از Scope کردن Tenant می‌آید: `ConfirmRedirectPaymentAction` هرگز چیزی که فراخوان درباره‌ی موفقیت یک پرداخت ادعا می‌کند را باور نمی‌کند — همیشه سرور-به-سرور، در برابر خودِ API `verify()`ی درگاه واقعی، دوباره تأیید می‌کند. `findByIdUnscoped()` فقط تعیین می‌کند فراخوان *کدام* `PaymentSession` را منظور دارد؛ در بدترین حالت، یک id حدس‌زده‌شده یا اشتباه، فقط یک فراخوانی واقعی `verify()` را روی نشستی که مال خودِ فراخوان نیست هدر می‌دهد — هرگز نمی‌تواند یک پرداخت را از طرف کس دیگری تکمیل‌شده علامت بزند، چون تکمیل‌شدن توسط پاسخ معتبر خودِ درگاه تعیین می‌شود، هرگز فقط با وجود یک id مطابق.»

🔁 **سوالات تعقیبی احتمالی:**

🚩 **پرچم‌های قرمز:**
مستقیم گفتن «یک جستجوی Repository نامحدود همیشه یک باگ امنیتی است» — از‌دست‌دادن این‌که تضمین واقعی اینجا از یک مکانیزم دیگر و قوی‌تر (تأیید مجدد سمت سرور) می‌آید، نه اصلاً از Scope کردن.

### Q9: این پروژه چطور مطمئن می‌شه یک اطلاعات هویتی واقعی — یک کلید API، یک راز Webhook — هرگز داخل Git کامیت نشه، یا داخل یک کلاس Domain مدفون نشه؟

آیا مدیریت راز یک انضباط ساختاری واقعی در این کدبیس است، یا فقط «ما هم مثل بقیه از `.env` استفاده می‌کنیم».

2. «آیا یک اطلاعات هویتی واقعی تا حالا تو تاریخچه‌ی این پروژه واقعاً نشت کرده؟» → هیچ حادثه‌ی شناخته‌شده‌ای نیست — این یک انضباط پیشگیرانه است، نه یک رفع بعد از حادثه.

🚩 **پرچم‌های قرمز:**
«ما فقط فایل `.env` رو کامیت نمی‌کنیم» به‌عنوان کل جواب — از‌دست‌دادن انضباط عمیق‌تر و مهم‌تر: هرگز نگذاشتن یک اطلاعات هویتی از همان اول داخل درون یک کلاس نشت کند.

قضاوت دقیق — تشخیص «یک ناتمامی مستندشده و شناخته‌شده» از «یک باگ امنیتی واقعی»، که این دو یکی نیستند.

✅ **جواب مدل:**
«یک شکاف تدریجی قابل‌قبول، نه یک آسیب‌پذیری — و این تمایز اهمیت دارد. یک آسیب‌پذیری این بود که `Operator` *قول* دسترسی محدودتر بدهد (یک UI که «فقط-مشاهده» را القا می‌کند) درحالی‌که بی‌صدا اجازه‌ی نوشتن‌های کامل سطح-`Admin` را زیرش بدهد — آن یک ناهماهنگی واقعی و خطرناک بین رفتار بیان‌شده و رفتار واقعی می‌بود. آنچه واقعاً وجود دارد صادقانه‌تر است: `UserRole::Operator` یک مورد Enum واقعی و مدل‌شده است، ولی هر مسیر پنل مدیریتی که این کدبیس تا الان ساخته با همان یک Middleware `admin` محافظت می‌شود، بدون هیچ چک محدودتری روی آن لایه‌بندی‌شده — مستقیم در لیست بدهی فنی خودِ `HANDOFF.md` به‌عنوان ساخته‌نشده مستند شده، نه بی‌صدا خراب. هیچ‌چیز درباره‌ی رفتار امروز چیزی که قول داده شده را نقض نمی‌کند؛ شکاف این است که یک نقش واقعاً محدودتر «مشاهده ولی ویرایش نکن» هنوز به‌عنوان یک تمایز واقعی و اجراشده وجود ندارد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چطور تمایز واقعی رو می‌ساختی؟» → یک Middleware Alias دوم و محدودتر (یا یک چک مجوز شبیه-قابلیت روی خودِ `UserRole`) که مسیرهای نوشتنی خاص به آن نیاز دارند و مسیرهای `operator` نه — همان شکلی که `CheckPermissionAction` از قبل به Agentهای Tenant-محور می‌دهد، یک لایه بالاتر برای Userهای پلتفرم.
2. «این رو قبل از شکاف اطلاعات هویتی کاشته‌شده (سؤال ۱۰) اولویت می‌دادی؟» → نه — سؤال ۱۲ همین فایل دقیقاً همین اولویت‌بندی را باز می‌کند، و اطلاعات هویتی کاشته‌شده ریسک ارزان‌تر و نزدیک‌ترمدت است.

🚩 **پرچم‌های قرمز:**
نامیدن این به «یک آسیب‌پذیری بحرانی» بدون تشخیص آن از یک ناهماهنگی واقعی قول-در-برابر-رفتار — یک بازبینی امنیتی واقعی به این دقت نیاز دارد، نه فقط یک واکنش خودکار «هر شکافی بحرانیه».

### Q12: اگه باید یک بازبینی امنیتی واقعی از این پلتفرم قبل از اولین مشتری چندمستأجری پرداختی اجرا می‌کردی، لیست اولویت‌بندی‌شده‌ات چیه — با ترکیب این فایل و فایل ۱۱؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک جواب بسته و ترکیبی روی مواد دو فایل — آیا کاندیدا می‌تواند ریسک‌های واقعی را در برابر هم بسنجد، نه فقط آن‌ها را به ترتیب فایل بازگو کند.

✅ **جواب مدل:**
«به‌ترتیب: اول، چرخاندن یا حذف اطلاعات هویتی پیش‌فرض کاشته‌شده‌ی ادمین و گذاشتن یک جریان واقعی بازیابی رمز عبور پشتش (سؤالات ۱۰ و ۱۱ همین فایل) — ارزان، از قبل علامت‌گذاری‌شده، و هیچ‌چیز دیگری را مسدود نمی‌کند، پس هیچ دلیلی نیست که اول نباشد. دوم، اطلاعات ورود کانکتور Tenant-محور (فایل ۱۱، سؤال ۱۰) — این همان چیزی است که واقعاً *مشتری واقعی بعدی* را مسدود می‌کند، دقیقاً همان لحظه‌ای که یک Tenant دوم می‌خواهد فروشگاه WooCommerce خودش یا حساب درگاه پرداخت خودش را وصل کند. سوم، یک تمایز واقعی دسترسی `Operator` در برابر `Admin` (سؤال ۱۱) — واقعاً مفید، ولی فقط زمانی اهمیت پیدا می‌کند که واقعاً بیش از یک نوع کاربر پنل مدیریت در عمل وجود داشته باشد. آخر، انصاف نرخ‌محدودسازی در سطح Tenant (فایل ۱۱، سؤال ۹) — یک نگرانی واقعی ولی مرحله‌ی-بعدی که فقط وقتی گاز می‌گیرد که یک Tenant تنها از قبل به‌اندازه‌ی کافی Agent تأمین کرده که به‌طور معنادار Tenant دیگری را کنار بزند. اصل اولویت‌بندی همانی است که این پروژه از قبل در سراسر لیست بدهی فنی خودش اعمال می‌کند: اولویت‌بندی با چیزی که ارزان-و-از-قبل-شناخته‌شده است، بعد چیزی که مشتری واقعی بعدی را مسدود می‌کند، بعد چیزی که فقط در مقیاس چندمستأجری واقعی اهمیت دارد — نه با این‌که کدام رفع از نظر معماری چشمگیرتر به‌نظر می‌رسد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چیزی که تو هیچ‌کدوم از این دو فایل پوشش داده نشده اضافه می‌کردی؟» → یک ممیزی وابستگی/CVE روی `composer.lock`/`package-lock.json` — اصلاً در این کتابچه پوشش داده نشده، و یک قدم استاندارد و واقعی پیش-راه‌اندازی برای هر استقرار Production.
2. «چی باعث می‌شد این لیست رو دوباره مرتب کنی؟» → یک حادثه‌ی واقعی یا یک نیاز انطباق مشخص (مثلاً یک Tenant که به ایزوله‌سازی فیزیکی داده نیاز دارد) بلافاصله سؤال پایگاه‌داده-به‌ازای-هر-Tenant فایل ۱۱ را بالای این لیست می‌آورد.

🚩 **پرچم‌های قرمز:**
مرتب‌کردن این لیست بر اساس «جالبی فنی» (مثلاً شروع با پایگاه‌داده-به‌ازای-هر-Tenant) به‌جای تأثیر واقعی و نزدیک‌مدت — دقیقاً همان اشتباهی که سؤال بسته‌ی خودِ فایل ۱۱ قبلاً، یک فایل زودتر، درباره‌اش هشدار داد.
