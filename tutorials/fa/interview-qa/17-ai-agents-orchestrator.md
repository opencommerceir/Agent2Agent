# ۱۷. ایجنت‌های AI و Orchestrator

Dependency Inversion سطح-Container خودِ سه-تأمین‌کننده‌ی `LLMClientInterface` (فایل ۰۳، سؤال ۱) و چرا عمداً با `bind()` Bind می‌شود، هرگز `singleton()` (فایل ۰۳، سؤال ۲)، جایگاه خودِ Agent Orchestrator به‌عنوان یک Bounded Context غیر-کسب‌وکاری با زبانی درباره‌ی «چطور کار انجام می‌شه»، نه «چه کاری انجام می‌شه» (فایل ۰۸، سؤال ۸)، تبادل Payload سبک-در-برابر-سنگین خودِ Eventهای `AgentMessage`/Delegation (فایل ۰۹، سؤال ۵)، تاریخچه‌ی `Execution` به‌شکل Ledger خودِ `ExecutionMemoryRepositoryInterface` (فایل ۱۰، سؤال ۳)، باگ واقعی `base_uri` خودِ `OpenRouterClient` که فقط تست زنده گرفتش (فایل ۰۶، سؤال ۸)، باگ مسیریابی ۴۰۴-در-برابر-۵۰۰ خودِ `/api/agents/{agentType}` که هنگام ساخت همین ماژول پیدا شد (فایل ۰۵، سؤال ۴)، انضباط جداسازی-Credential که هر Client LLM از قبل دنبال می‌کند (فایل ۱۲، سؤال ۹)، هزینه‌ی واقعی و اندازه‌گیری‌شده‌ی خودِ Prompt در `LLMPlanner` (فایل ۰۱، سؤال ۹)، اصلاح Persona-نیست-هویت-واقعی از Multi-Agent Collaboration (فایل ۰۱، سؤال‌های ۲ و ۱۱)، و استثنای مستندشده‌ی خودِ Agent Orchestrator برای وابستگی مستقیم به Actionهای Core (فایل ۰۲، سؤال ۹) همه از قبل از زاویه‌های دیگر پوشش داده شدند. این فایل جایی است که خودِ فاز ۶ — ساخت شش‌مرحله‌ای که یک Core مستقل-از-دامنه را به چیزی تبدیل کرد که واقعاً می‌تواند برنامه‌ریزی کند، اجرا کند، به‌خاطر بسپارد، تفویض کند، و بازتاب دهد — مرحله‌به‌مرحله مستقیم بررسی می‌شود.

### Q1: من رو از یک Goal واقعی، سر تا ته، از هر شش مرحله‌ی Orchestrator عبور بده. هر مرحله واقعاً کجا وصل میشه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا می‌تواند یک خط‌لوله‌ی واقعی و چند-مرحله‌ای را سر تا ته ردیابی کند — همان نوع سؤال ردیابی-کامل که فایل ۰۲ (سؤال ۳) از قبل برای یک درخواست ساده‌ی MCP می‌طلبد، یک لایه بالاتر.

✅ **جواب مدل:**
«`ExecuteGoalAction` یک متن ساده‌ی Goal می‌گیرد — مثلاً «اگه هر محصولی موجودیش کم شد بهم اطلاع بده» — و شش مرحله از آنجا به بعد را می‌گیرند. **مرحله‌ی ۱/۲، برنامه‌ریزی**: `PlannerInterface` آن متن را به یک `Plan` واقعی تبدیل می‌کند، یک توالی از مراحل که هرکدام یک قابلیت واقعی MCP را هدف می‌گیرند؛ کدام پیاده‌سازی مشخص اجرا می‌شود با `bind()` روی `config('agent-orchestrator.planner.type')` حل می‌شود (فایل ۰۳، سؤال ۲) — یک Planner سریع، رایگان، و قطعی مبتنی‌بر مچ‌کردن کلیدواژه برای هدف‌های ساده، یا `LLMPlanner`، که `LLMClientInterface` را برای موارد واقعاً مبهم صدا می‌زند. **مرحله‌ی ۳، Tool Calling**: `PlanExecutor` مراحل خودِ `Plan` را طی می‌کند، و برای هرکدام، `CapabilityToolInvoker` واقعاً آن قابلیت را از طریق دقیقاً همان `CapabilityExecutionService`ای صدا می‌زند که یک صدازدن مستقیم MCP خودِ یک Agent واقعی استفاده می‌کرد (سؤال ۴ همین فایل) — Orchestrator هرگز یک مسیر میان‌بر که چک‌های واقعی مجوز رویش اعمال نشه نمی‌گیرد. **مرحله‌ی ۴، حافظه‌ی اجرا**: نتیجه‌ی واقعی هر مرحله به تاریخچه‌ی خودِ `Execution` آن Goal از طریق `ExecutionMemoryRepositoryInterface` ضمیمه می‌شود (فایل ۱۰، سؤال ۳)، برای مچ‌کردن الگو در آینده. **مرحله‌ی ۵، همکاری چند-Agent**: اگه یک مرحله مشخصاً چون Agent فعلی یک مجوز لازم را ندارد شکست بخورد، یک `DelegationRequest` می‌تواند آن یک مرحله را به یک Agent واقعی دیگر با مجوز درست بفرستد — هرگز با تظاهر به یک Persona دیگر (سؤال ۶ همین فایل). **مرحله‌ی ۶، بازتاب-خود**: وقتی Goal تمام می‌شود (یا تسلیم می‌شود)، `ReasoningEngineInterface` یک توضیح واقعی و قابل‌خواندن-برای-انسان از این‌که چی اتفاق افتاد و چرا تولید می‌کند — امروز، خالص توضیحی (سؤال ۸ همین فایل).»

🔁 **سوالات تعقیبی احتمالی:**
1. «کدوم مرحله از نظر محاسباتی گران‌تره؟» → مرحله‌ی ۲، وقتی `LLMPlanner` پیاده‌سازی فعال است — یک Round-Trip شبکه‌ای واقعی به یک تأمین‌کننده‌ی LLM که کل لیست قابلیت‌ها را حمل می‌کند (سؤال ۲ همین فایل)، کاملاً برخلاف مچ کلیدواژه‌ی محلی و آنی مرحله‌ی ۱.
2. «هر Goal واقعاً هر شش مرحله رو لمس می‌کنه؟» → نه — مرحله‌ی ۵ (تفویض) فقط روی یک شکست واقعی مجوز درگیر می‌شود، و مرحله‌ی ۶ همیشه اجرا می‌شود ولی می‌تواند واقعاً برای یک Goal که دقیقاً همان‌طور که برنامه‌ریزی شده بود موفق شد چیز جالبی برای گفتن نداشته باشد.

🚩 **پرچم‌های قرمز:**
توصیف «Orchestrator» به‌عنوان یک کلاس یکپارچه — از‌دست‌دادن این‌که شش مرحله‌ی واقعاً جداشدنی است، هرکدام مستقل قابل‌تعویض، همان انضباط ماژولار که این پروژه روی هر ماژول دیگر اعمال می‌کند.

### Q2: چرا این پروژه *دو* پیاده‌سازی Planner دارد — یکی قطعی و یکی مبتنی‌بر LLM — به‌جای این‌که فقط از اول یکی LLM بسازد؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک تبادل واقعی و صادقانه‌ی هزینه/فایده بین یک خط‌مبنای ارزان و قابل‌پیش‌بینی و یک ارتقای انعطاف‌پذیر ولی گران — نه «LLMها مطلقاً بهترن».

✅ **جواب مدل:**
«Planner قطعی متن خودِ Goal را در برابر مجموعه‌ای ثابت از قوانین کلیدواژه/الگو مچ می‌کند و مستقیم به یک توالی قابلیت شناخته‌شده نگاشت می‌کند — صفر صدازدن شبکه، صفر هزینه، کاملاً قابل‌پیش‌بینی، و هر Test Suite در این کدبیس به‌طور پیش‌فرض `PLANNER_TYPE=deterministic` را ثابت می‌کند مشخصاً تا اجرای تست یک Clone تازه هرگز به یک Credential واقعی نیاز نداشته باشد (فایل ۱۲، سؤال ۹). محدودیت واقعی‌اش واقعی است: فقط می‌تواند یک Goal که به‌اندازه‌ی کافی نزدیک به یکی از الگوهای شناخته‌شده‌ی خودش شکل گرفته باشد را مدیریت کند — یک Goal واقعاً مبهم و چند-مرحله‌ای مثل «وضعیت موجودی کند-فروش ما رو بهتر کن» هیچ الگوی ثابتی برای مچ‌شدن ندارد. `LLMPlanner` دقیقاً برای این شکاف وجود دارد — درک واقعی زبان، به هزینه‌ی واقعی یک Round-Trip شبکه‌ای، یک قیمت واقعی به‌ازای هر Call، و کل لیست ۱۲۷ قابلیت (حدود ۲۰٬۷۰۰ کاراکتر، فایل ۰۱ سؤال ۹) که در هر Prompt واحد جاسازی می‌شود تا مدل واقعاً بداند با چی اجازه‌ی برنامه‌ریزی دارد. نگه‌داشتن هردو، انتخاب‌شده از طریق `config()` با `bind()` به‌جای جایگزینی یکی با دیگری، یعنی یک Deploy که واقعاً به انعطاف LLM برای Goalهای معمول خودش نیازی ندارد هرگز مجبور به پرداخت آن هزینه نیست.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا Planner قطعی می‌تونه واقعاً اشتباه باشه، نه فقط محدود؟» → می‌تواند Under-Match کند (یک الگو پیدا نکند) ولی نمی‌تواند یک قابلیت غیرواقعی توهم کند همان‌طور که یک پاسخ LLM بی‌ریشه به‌طور نظری می‌تواند — خودِ خروجی `LLMPlanner` هم قبل از اجرا در برابر Registry واقعی قابلیت‌ها اعتبارسنجی می‌شود، هرگز کورکورانه اعتماد نمی‌شود.
2. «تعویض Planner یک تصمیم Runtime هست یا زمان-Deploy؟» → پیکربندی‌محور، پس عملاً زمان-Deploy در Production — ولی حل‌کردن به‌ازای هر درخواست خودِ `bind()` (فایل ۰۳، سؤال ۲) دقیقاً چیزی است که به یک Test Suite واحد اجازه می‌دهد بین هردو داخل همان اجرا جابه‌جا شود.

🚩 **پرچم‌های قرمز:**
فرض این‌که Planner قطعی کد قدیمی است که دارد کنار گذاشته می‌شود — یک پیاده‌سازی واقعی و همیشه-مفید برای دقیقاً همان Goalهایی است که از قبل می‌تواند مدیریت کند، نه یک پله‌ی موقت که دارد جایگزین می‌شود.

### Q3: درباره‌ی باگ واقعی base_uri خودِ `OpenRouterClient` بهم بگو. واقعاً چی رو درباره‌ی استراتژی Mock این پروژه آشکار کرد؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک داستان جنگی ملموس و از‌قبل-اشاره‌شده که از زاویه‌ی یکپارچگی-LLM دوباره بررسی می‌شود — آیا کاندیدا می‌تواند مکانیک واقعی RFC را توضیح دهد، نه فقط به‌خاطر بیاورد «یه‌بار یه باگی بود».

✅ **جواب مدل:**
«اولین‌باری که `OpenRouterClient` واقعاً با یک Credential واقعی به‌جای `MockHandler` صدا زده شد (فایل ۰۶، سؤال ۸)، Call با یک `403` واقعی شکست خورد. علت: Guzzle، طبق RFC 3986، مسیر خودِ `base_uri` را *جایگزین* می‌کند به‌جای ضمیمه‌کردنش هروقت مسیر درخواست با `/` شروع شود — پس `https://openrouter.ai/api/v1` به‌عنوان Base، ترکیب‌شده با یک مسیر درخواست `/chat/completions`، بی‌صدا `https://openrouter.ai/chat/completions` تولید می‌کرد، `/api/v1` را کاملاً بی‌صدا حذف می‌کرد. هیچ‌کدام از ۷ تست واحد موجود این را نگرفت، چون هرکدام مستقیم یک Client Guzzle از‌قبل-کاملاً-ساخته‌شده تزریق می‌کردند (دقیقاً همان الگوی تزریق-وابستگی که خودِ `LLMClientInterface` استفاده می‌کند، سؤال ۱ همین فایل)، هرگز شاخه‌ی واقعی Constructor که `base_uri` را از Config می‌سازد را تمرین نمی‌کردند. رفع مشکل پذیرفتن قرارداد استاندارد Guzzle بود (`base_uri` که با `/` تمام می‌شود، مسیرهای درخواست هرگز با یکی شروع نمی‌شوند) به‌همراه یک تست Regression جدید که دقیقاً همان شاخه را از طریق Reflection تمرین می‌کند — اثبات رفع مشکل بدون نیاز دوباره به یک Call شبکه‌ای واقعی. همان رفع مشکل بعداً پیشگیرانه روی `ZibalPaymentGateway`/`StripePaymentGateway` (فایل ۱۳، سؤال ۱۰) اعمال شد قبل از این‌که آن‌ها اصلاً فرصت برخورد با همان باگ دقیق را داشته باشند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا `ClaudeClient`/`OpenAIClient` هم به این برخورد نکردند؟» → می‌توانستند، ساختاری — رفع مشکل روی هر سه به‌عنوان یک قرارداد مشترک اعمال شد مشخصاً برای بستن آن ریسک هرجا `LLMClientInterface` یک پیاده‌سازی واقعی دارد، نه فقط جایی که باگ اتفاقاً اول کشف شد.
2. «درس واقعی درباره‌ی Mocking اینجا چیه؟» → همانی که فایل ۰۶ (سؤال ۸) از قبل مستقیم نام می‌برد: Mocking کامل ثابت می‌کند کد شما یک پاسخ *داده‌شده* را درست مدیریت می‌کند، ولی هرگز نمی‌تواند ثابت کند کد شما اصلاً درست به یک سرور واقعی *می‌رسد* — این‌ها دو ادعای واقعاً متفاوت‌اند.

🚩 **پرچم‌های قرمز:**
توصیف این به‌عنوان «فقط یه غلط‌تایپی تو یک URL» — از‌دست‌دادن مکانیک واقعی و عمومی RFC 3986 (جایگزینی-مسیر، نه ضمیمه‌کردن-مسیر) که باعث می‌شود این دسته‌ی دقیق باگ هرجا یک `base_uri` با مسیر خودش بی‌احتیاط با یک مسیر درخواست مطلق ترکیب شود تکرار شود.

### Q4: «Tool Calling» واقعاً اینجا چطور کار می‌کند؟ وقتی یک LLM تصمیم می‌گیرد یک قابلیت را صدا بزند، دسترسی بیشتری از یک Agent واقعی که مستقیم MCP را صدا می‌زند می‌گیرد؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا Tool Calling را به‌عنوان یک مسیر اجرای واقعی و مجوز-چک‌شده می‌فهمد — نه یک میان‌بر ممتاز که مدل امنیتی خودِ پلتفرم را دور می‌زند.

✅ **جواب مدل:**
«اصلاً دسترسی بیشتری نمی‌گیرد — این کل نکته‌ی ساخته‌شدن `CapabilityToolInvoker` است. همان ۱۲۷ قابلیتی که یک Agent مستقیم از طریق MCP Gateway کشف و اجرا می‌کند (فایل ۰۲، سؤال ۳) دقیقاً همان مجموعه‌ای است که یک LLM به‌عنوان «ابزار»های خودش در دسترس در طول برنامه‌ریزی می‌بیند — هیچی تکرار نمی‌شود، هیچی یک تعریف دومِ فقط-LLM نمی‌گیرد. وقتی `PlanExecutor` واقعاً یک مرحله را صدا می‌زند، `CapabilityToolInvoker` آن را از طریق دقیقاً همان `CapabilityExecutionService`ای مسیریابی می‌کند که یک صدازدن مستقیم MCP استفاده می‌کرد — یعنی همان چک مجوز (`CheckPermissionAction`)، همان محدوده‌ی Tenant، همان اعتبارسنجی InputSchema، همه هر بار اجرا می‌شوند. برای همین `CapabilityToolInvokerTest` یک تست Feature واقعی است، نه یک تست واحد بدون-Framework (فایل ۰۶، سؤال ۷) — واقعاً به سیستم مجوز واقعی و Boot-شده نیاز دارد تا این ادعا را ثابت کند، نه فقط تأییدش کند. اگه خودِ Agentی که یک Goal را می‌راند `commerce.products.write` را نداشته باشد، هیچ برنامه‌ریزی زیرکانه‌ی LLM اجازه نمی‌دهد یک مرحله که آن قابلیت را لمس می‌کند واقعاً موفق شود — دقیقاً با همان `403`ای که یک Call مستقیم می‌گرفت شکست می‌خورد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «پس آیا یک LLM می‌تونه یک مرحله رو برنامه‌ریزی کنه که اجازه‌ی اجراش رو نداره؟» → بله، واقعاً — `PlannerInterface` هنگام ساختن یک `Plan` بر اساس مجوز از قبل فیلتر نمی‌کند؛ اجرای واقعی در زمان اجرا اتفاق می‌افتد، در مرحله‌ی ۳، که دقیقاً همان درزی است که مکانیزم تفویض مرحله‌ی ۵ برای مدیریتش وجود دارد (سؤال ۶ همین فایل).
2. «آیا Schema ابزاری که به LLM داده می‌شود همان InputSchema خودِ قابلیت است؟» → بله — همان JSON Schema که از قبل برای کشف واقعی MCP منتشر شده (فایل ۰۲، سؤال ۳) مستقیم به‌عنوان تعریف ابزار دوباره‌استفاده می‌شود، همان غریزه‌ی «مکانیزم موجود رو دوباره استفاده کن به‌جای ساختن یک موازی» که فایل ۱۴ (سؤال ۱۲) از قبل به‌عنوان تکرارشونده‌ترین حرکت این پروژه نام می‌برد.

🚩 **پرچم‌های قرمز:**
فرض این‌که «صدازدن یک ابزار» توسط یک LLM معماری‌طور با یک Agent که مستقیم MCP را صدا می‌زند متفاوت است — کل هدف طراحی اینجا این بود که مطمئن شوند این دقیقاً همان مسیر است، چک‌های مجوز شامل، نه یک مسیر جدا و بالقوه ضعیف‌تر.

### Q5: `Execution` واقعاً چی ثبت می‌کند، و چرا Pattern-Matching خودش امروز «یک چک Substring ساده» است، نه چیزی هوشمندتر؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
تشخیص شکل Ledger خودِ `Execution` به‌عنوان همان الگویی که این کتابچه جای دیگر پوشش داده، به‌همراه خوانش صادقانه‌ای از یک محدودیت واقعی و نام‌گذاری‌شده به‌جای یک ادعای اغراق‌شده.

✅ **جواب مدل:**
«`Execution` تاریخچه‌ی کامل و فقط-پیوست هر مرحله از یک اجرای واقعی Goal است — هر مرحله‌ی Plan، نتیجه‌ی واقعی‌اش، و هر تفویض یا بازتابی که بهش گره خورده — از طریق `ExecutionMemoryRepositoryInterface` پایدارشده و هرگز رونویسی‌نشده، همان شکل «تعریف/نتیجه‌ی یک اجرا، تاریخچه‌ی کامل حفظ‌شده» که فایل ۱۰ (سؤال ۳) از قبل برای `Report`/`ReportResult` پوشش می‌دهد. ### Q6: من رو از اصلاح واقعی که Multi-Agent Collaboration را شکل داد عبور بده — چرا یک شکاف مجوز نمی‌تواند فقط با تفویض به یک Persona دیگر Agent دور زده شود؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک داستان اصلاح معماری ملموس که از‌قبل جای دیگر این کتابچه اشاره شده (فایل ۰۱، سؤال‌های ۲ و ۱۱) — آیا کاندیدا می‌تواند یک لایه عمیق‌تر به استدلال واقعی مدل-هویت برود، نه فقط به‌خاطر بیاورد که یک اصلاح اتفاق افتاد.

✅ **جواب مدل:**
«طراحی اصلی برای مرحله‌ی ۵ فرض کرد `ExecuteGoalAction` می‌تواند با «تعویض» به یک Persona دیگر Agent — مثلاً از یک Persona «فروش» به یک Persona «مدیر» — وسط یک Goal یک مجوز گم‌شده را دور بزند. آن طراحی با مدل هویت واقعی خودِ این پلتفرم زنده نماند: یک Persona فقط یک دسته‌بندی زمان-برنامه‌ریزی است که یک Agent زیرش عمل می‌کند، هرگز یک هویت مجزا و دارای-مجوز خودش. دقیقاً همان Agent احراز-هویت‌شده، با دقیقاً همان مجموعه Role/مجوز واقعی، پشت هر Personaای که ممکن است استفاده کند می‌نشیند — پس «تعویض Persona» هیچی درباره‌ی چیزی که `CheckPermissionAction` واقعاً می‌بیند تغییر نمی‌دهد. رفع مشکل واقعی **تفویض مبتنی‌بر-قابلیت** بود به‌جایش: یک `DelegationRequest` یک Agent واقعاً متفاوت و واقعی را هدف می‌گیرد که واقعاً مجوز گم‌شده را دارد، با ماشین‌حالت پذیرش/رد صریح خودش (فایل ۰۷، سؤال ۸) — همان شکلی که `WarehouseTransfer`/`Subscription` از قبل دارند، فقط مدل‌سازی یک تحویل مجوز بین دو هویت واقعی به‌جای یک حرکت فیزیکی موجودی یا یک چرخه‌ی صورت‌حساب.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این قبل از نوشتن کد واقعی گرفته شد یا بعدش؟» → قبلش — فایل ۰۱ (سؤال ۱۱) از قبل این را به‌عنوان موردی پوشش می‌دهد که صریح به‌عنوان یک سؤال معماری اول مطرح شد، دقیقاً چون هزینه‌ی ساختن مدل هویت اشتباه و کشف بعدی‌اش خیلی بیشتر می‌بود.
2. «آیا یک DelegationRequest هرگز خودکار تأیید می‌شود؟» → معماری‌طور فرض نشده — تصمیم پذیرش/رد خودِ Agent دریافت‌کننده یک مرحله‌ی واقعی و مدل‌شده است، هرگز فقط چون Goal درخواست‌کننده عجله دارد دور زده نمی‌شود.

🚩 **پرچم‌های قرمز:**
توصیف Personaها به‌عنوان «اساساً کاربرهای متفاوت» — دقیقاً همان تصور غلطی که طراحی اصلی و رد‌شده داشت، و دقیقاً چیزی که این اصلاح برای رد‌کردنش وجود دارد.

### Q7: Eventهای `AgentMessage`/Delegation یک تبادل واقعی Payload سبک-در-برابر-سنگین حمل می‌کنند. این واقعاً اینجا چه شکلی است؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک نمونه‌ی ملموس از قانون عمومی Payload-Event خودِ فایل ۰۹ (سؤال ۵)، اعمال‌شده روی Eventهای واقعی خودِ این فایل — نه فقط تکرار قانون به‌صورت انتزاعی.

✅ **جواب مدل:**
«قانونی که فایل ۰۹ (سؤال ۵) از قبل به‌طور عمومی بیان می‌کند — Entity کامل وقتی Listenerهای شناخته‌شده به جزئیات آنی نیاز دارند، Payload فقط-شناسه وقتی یک Event سبک‌تر و جداتر امن‌تر است — اینجا مشخص اجرا می‌شود. یک `AgentMessage` معمولی (یک مرحله از پیشرفت عادی Goal، مکرر Log می‌شود) فقط شناسه حمل می‌کند — `executionId`، `agentId` — عمداً سبک، چون این‌ها زیاد فعال می‌شوند و اکثر Listenerها فقط اهمیت می‌دهند که *چیزی* اتفاق افتاد، نه محتوای کاملش، این Event مکرر را ارزان نگه می‌دارد. یک Event Delegation، در مقابل، جزئیات کامل‌تری حمل می‌کند — شکاف مجوز واقعی، قابلیت مشخصی که شکست خورد، زمینه‌ی خودِ Agent درخواست‌کننده — چون به‌ندرت فعال می‌شود، و یک Listenerای که اهمیت دارد (Agent که تصمیم می‌گیرد بپذیرد) واقعاً به آن جزئیات آنی نیاز دارد، بدون یک Fetch اضافی Round-Trip. این دقیقاً همان شکلی است که خودِ فایل ۰۹ (سؤال ۵) در سوال تعقیبی خودش مستقیم نام می‌برد: Eventهای سبک برای چیزی که مکرر اتفاق می‌افتد، Eventهای سنگین‌تر برای چیزی که به‌ندرت اتفاق می‌افتد ولی به جزئیات آنی نیاز دارد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا Payload سبک خودِ یک AgentMessage معمولی می‌تونه تا حالا مشکل ایجاد کنه؟» → فقط اگه یک Listener آینده واقعاً بیشتر از یک شناسه نیاز داشته باشد — در آن نقطه، همان الگوی دوباره-Fetch-از-Repository که `InventoryLowListener` از قبل استفاده می‌کند (فایل ۰۹، سؤال ۱۱) رفع مشکل است، نه ارتقای پیشگیرانه‌ی هر `AgentMessage` برای حمل جزئیات کامل.
2. «آیا یک Event Delegation یک Domain Event به همان معنای OrderWasPlaced است؟» → بله، ساختاری یکسان — بعد از یک تغییر وضعیت واقعی ارسال‌شده (یک `DelegationRequest` واقعاً ساخته‌شده)، توسط یک Listener کاملاً جدا مصرف‌شده، همان قرارداد ناشر-هرگز-مصرف‌کنندگانش-را-نمی‌داند که فایل ۰۹ (سؤال ۱) در سراسر پلتفرم برقرار می‌کند.

🚩 **پرچم‌های قرمز:**
رفتار با «سبک در برابر سنگین» به‌عنوان یک شیر یا خط تصادفی به‌ازای هر Event — از‌دست‌دادن این‌که همان یک قانون عمومی (فراوانی و نیاز Listener) به‌طور یکسان اعمال شده، نه یک تصمیم جدا که از صفر برای هر نوع Event گرفته شده.

### Q8: خودِ بازتاب-خود (`ReasoningEngineInterface`) واقعاً امروز چی تولید می‌کند؟ آیا Orchestrator را با گذر زمان باهوش‌تر می‌کند؟

### Q9: چرا Agent Orchestrator مستقیم به خودِ Actionهای Core — `DiscoverCapabilitiesAction`، `CheckPermissionAction` — وابسته است به‌جای رابط Repository یک ماژول دیگر، همان‌طور که هر ماژول کسب‌وکاری این کار را می‌کند؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
تشخیص این به‌عنوان یک استثنای معماری واقعی، مستندشده، و عمدی — نه یک ناهماهنگی که کاندیدا باید یا از‌دستش بدهد یا بابتش عذرخواهی کند.

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا این حذف یا جایگزین‌کردن Orchestrator رو سخت‌تر از یک ماژول کسب‌وکاری می‌کنه؟» → نه — اگه چیزی، آسان‌تر: چون هیچ داده‌ی کسب‌وکاری پایدار خودش (فراتر از `Execution`/`Goal`/`DelegationRequest`، Entityهای زبان-هماهنگی خودش) را مالک نیست، حذف کامل آن هیچ داده‌ی هیچ ماژول دیگری را دست‌نخورده باقی می‌گذارد.
2. «آیا یک ماژول کسب‌وکاری آینده می‌تونه همین استثنا رو بگیره؟» → فقط اگه واقعاً هم یک لایه‌ی هماهنگی باشد، نه یک دامنه‌ی واقعی — فایل ۰۸ (سؤال ۸) صریح است که این استثنا *چون* Orchestrator چه نوع Contextی هست وجود دارد، نه به‌عنوان یک سابقه که هر ماژولی می‌تونه ادعاش کنه.

🚩 **پرچم‌های قرمز:**
نامیدن این «نقض قانون مرز ماژول» بدون درگیرشدن با *چرا* اینجا واقعاً درست است — از‌دست‌دادن تمایز واقعی بین یک Context کسب‌وکاری (که به مرز رابط-Repository نیاز دارد) و یک لایه‌ی هماهنگی که بالای هر Context می‌نشیند (که داده‌ی قابل‌مقایسه‌ای برای محافظت اصلاً ندارد).

### Q10: دو چیز واقعی مشخصاً هنگام ساخت این ماژول ظاهر شدند — یک باگ مسیریابی و یک انضباط مدیریت-Credential. من رو از هردو عبور بده.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا کاندیدا می‌تواند دو واقعیت از‌قبل-اشاره‌شده (فایل ۰۵، سؤال ۴؛ فایل ۱۲، سؤال ۹) را به این ماژول مشخص به‌عنوان مبدأ واقعی‌شان وصل کند — نشان‌دادن آشنایی واقعی با این‌که هرکدام واقعاً از کجای تاریخچه‌ی خودِ پروژه آمده.

✅ **جواب مدل:**
«اول، یک باگ واقعی مسیریابی: `MCPExceptionHandler` (فایل ۰۵، سؤال ۴)، قبل از یک رفع، فقط دو Marker Interface خودِ استثنای Domain (`NotFoundExceptionInterface` و یکی مربوط به تعارض) را چک می‌کرد — هرگز اصلاً `HttpExceptionInterface` سطح-مسیریابی خودِ Symfony را چک نمی‌کرد. یک بخش `agentType` نامعتبر که به `/api/agents/{agentType}` می‌خورد — یک مسیر که این ماژول معرفی کرد — باید یک `404` تمیز می‌بود، ولی به‌جایش به یک `500` عمومی صاف شد، چون استثنایی که Router خودِ Laravel برای یک مسیر واقعاً غیرموجود پرتاب می‌کند هرگز هیچ‌کدام از Marker Interfaceهای خودِ `MCPExceptionHandler` را پیاده نمی‌کرد. پیدا و رفع‌شده هنگام وایرکردن مسیرهای خودِ همین ماژول، نه کشف‌شده بعداً. دوم، یک انضباط که ماهیت Credential-سنگین خودِ همین ماژول درست‌گرفتنش را از همان اول اجتناب‌ناپذیر کرد: هیچ‌کدام از `OpenAIClient`/`ClaudeClient`/`OpenRouterClient` هرگز مستقیم `config()`/`env()` را صدا نمی‌زنند (فایل ۱۲، سؤال ۹) — هر کلید API واقعی دقیقاً یک‌بار حل می‌شود، داخل `AgentOrchestratorServiceProvider::register()`، سپس از طریق Constructor داده می‌شود، با هر Test Suite که مقادیر پیش‌فرض امن و بدون-کلید (`PLANNER_TYPE=deterministic`، `REASONING_TYPE=simple`) را ثابت می‌کند تا اجرای تست یک Clone تازه هرگز ریسک یک Call شبکه‌ای واقعی نداشته باشد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا این دو چیز مرتبط بودند، یا فقط تصادفی همزمان پیدا شدند؟» → واقعاً بی‌ربط — یکی باگ مسیریابی/نگاشت-استثنا است، دیگری یک انضباط پیشگیرانه‌ی مدیریت-Secret — فقط اتفاقاً همان مبدأ واقعی (ساختن همین ماژول) را به‌عنوان لحظه‌ی کشف یا برقراری‌شان به اشتراک می‌گذارند.
2. «آیا رفع HttpExceptionInterface از آن‌موقع جای دیگه‌ای لازم بوده؟» → چیزی که مستندات خودِ این پروژه ثبت کرده باشد نه — یک رفع یک‌باره و ساختاری برای خودِ `MCPExceptionHandler` بود، پس هر مسیری که از آن‌موقع اضافه شده (شامل هر مسیر در ماژول‌های خودِ فایل‌های ۱۴-۱۶) از قبل پوشش داده شده.

🚩 **پرچم‌های قرمز:**
رفتار با هرکدام از این‌ها به‌عنوان «فقط یه باگ که رفع شد» بدون اشاره به *چرا* دقیقاً این ماژول آن‌ها را آشکار کرد — یک ماژول جدید که مسیرهای جدید و Credentialهای خارجی جدید را برای اولین‌بار وایر می‌کند دقیقاً جایی است که یک شکاف از‌قبل-موجود در نگاشت استثنا یا یک انضباط گم‌شده واقعاً به احتمال زیاد تمرین می‌شود.

### Q11: آیا خودِ Agent Orchestrator به‌ازای هر شش مرحله‌اش قابلیت MCP منتشر می‌کند، یا فقط برای مرحله‌ی اصلی اجرای Goal؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک نقش دوگانه‌ی Orchestrator — بزرگ‌ترین *مصرف‌کننده*ی قابلیت پلتفرم، ولی همچنین یک *منتشرکننده*ی قابلیت واقعاً غنی — و تشخیص تنها قانون واقعی که تصمیم می‌گیرد کدام مراحل قابلیت خودشان را می‌گیرند و کدام مرحله عمداً هیچی نمی‌گیرد.

✅ **جواب مدل:**
«هردو، و سمت منتشرکننده از آن‌چه اول به‌نظر می‌رسد غنی‌تر است — ۱۱ قابلیت واقعی، تقریباً هر مرحله را پوشش می‌دهد: مرحله‌ی ۱ `agent.goal.execute`/`agent.execution.get`/`agent.execution.list` می‌گیرد؛ مرحله‌ی ۲ (پروفایل‌های Persona) `agent.profile.get`/`agent.profile.list` می‌گیرد؛ مرحله‌ی ۴ (حافظه‌ی اجرا) `agent.memory.insights`/`agent.memory.suggest` می‌گیرد؛ مرحله‌ی ۵ (همکاری چند-Agent) `agent.collaboration.delegate`/`agent.collaboration.messages` می‌گیرد؛ مرحله‌ی ۶ (بازتاب-خود) `agent.reasoning.trace`/`agent.reasoning.explain` می‌گیرد. تنها مرحله‌ای که واقعاً صفر قابلیت خودش دارد مرحله‌ی ۳، Tool Calling است — و این یک سهو نیست، قانون واقعی است که این سؤال دارد تستش می‌کند: یک مرحله وقتی قابلیت می‌گیرد که چیزی تولید کند که یک صدازننده‌ی بیرونی بتواند معنادار نامش ببرد و بعداً دربارش بپرسد — پیکربندی خودِ یک Persona، یک الگوی یادگرفته‌شده، یک تفویض، یک اثر بازتاب — هرگز برای مرحله‌ای که خالص یک مکانیزم اجرای داخلی است بدون هیچ مفهوم خودش برای افشا. Tool Calling دقیقاً همین است: سؤال ۴ همین فایل از قبل پوشش می‌دهد چرا دقیقاً همان مسیر `CapabilityExecutionService`ای را که یک Call مستقیم MCP از قبل دارد دوباره‌استفاده می‌کند، به‌جای این‌که یک چیز مجزا و قابل‌نام‌بردن باشد که یک صدازننده هرگز مستقل دربارش بپرسد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا `agent.collaboration.delegate` به یک صدازننده اجازه می‌دهد مستقیم یک تفویض بسازد، دور زدن یک مرحله‌ی Goal شکست‌خورده؟» → این یک قابلیت واقعی و صدازدنی است، نه فقط-داخلی — ولی خودِ `ExecuteGoalAction` *بدون‌تغییر* را برای یک Persona متفاوت زیر `AuthContext` واقعی خودِ صدازننده دوباره‌فراخوانی می‌کند، پس تفویض هنوز هرگز یک مجوز جدید که صدازننده از قبل نداشت اعطا نمی‌کند؛ `DelegationRequest.status` موفقیت یا شکست خودِ مکانیزم را ردیابی می‌کند، نه نتیجه‌ی کسب‌وکاری خودِ Goal تودرتو.
2. «چرا مرحله‌ی ۴ دو قابلیت می‌گیرد — insights و suggest — به‌جای یکی؟» → دو سؤال واقعاً متفاوت: `.insights` به «این Persona کلی چطور عمل کرده» جواب می‌دهد (آمار تجمعی روی Executionهای اخیر خودش)، `.suggest` به «`ExecuteGoalAction` واقعاً چی رو الان بی‌صدا برای این Goal دقیق ترجیح می‌داد» جواب می‌دهد (پیش‌نمایش یک Plan یادگرفته‌شده‌ی مشخص) — سؤال‌های به‌اندازه‌ی کافی متفاوت که فشرده‌کردنشان در یک قابلیت یک شکل ورودی ناخوشایند و اضافه‌بار می‌ساخت.

🚩 **پرچم‌های قرمز:**
فرض این‌که سطح عمومی خودِ Orchestrator یا باید «فقط یک قابلیت کلی» باشد یا «یک به‌ازای هر مرحله‌ی داخلی» — از‌دست‌دادن قانون واقعی و دقیق‌تر: یک (یا دو) قابلیت به‌ازای هر مرحله‌ای که چیزی از-بیرون-قابل‌نام‌بردن تولید می‌کند، صفر برای تنها مرحله‌ای که خالص لوله‌کشی اجرای داخلی است.

### Q12: فاز ۱ یک Core ساخت که هیچی درباره‌ی AI نمی‌دانست. فاز ۶ یک کل لایه‌ی هماهنگی مبتنی‌بر LLM بالایش ساخت، پنج فاز بعد. این واقعاً چی درباره‌ی شرط‌بندی معماری مرکزی این پروژه ثابت می‌کند؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک تلفیق بسته و در-سراسر-پروژه — وصل‌کردن این فایل به اصل اول بیان‌شده‌ی خودِ پلتفرم (فایل ۰۱، سؤال ۱؛ «Infrastructure First, Domains Second»ی خودِ CLAUDE.md) با شواهد ملموس و مشخص، نه فقط تکرار شعار.

✅ **جواب مدل:**
«قوی‌ترین شاهد واقعی این پلتفرم است که «Infrastructure First, Domains Second» فقط یک شعار افتتاحیه نبود — یک ادعا بود که واقعاً زیر یک آزمون فشار واقعی و برنامه‌ریزی‌نشده دوام آورد. هیچ‌کس هنگام طراحی Core در فاز ۱ — هویت، Tenancy، مجوزها، MCP Gateway — برای «یک LLM یه‌روزی Goalهای چند-مرحله‌ای در برابر این برنامه‌ریزی می‌کنه» طراحی نمی‌کرد. و با این‌حال فاز ۶ دقیقاً صفر تغییر در خودِ Core نیاز داشت: `CheckPermissionAction` به یک نسخه‌ی آگاه-از-AI نیاز نداشت: Orchestrator فقط همان یکی که هر Call مستقیم MCP خودِ Agent واقعی از قبل استفاده می‌کرد را صدا می‌زند (سؤال ۹ همین فایل). لیست قابلیت خودِ MCP Gateway به یک فرمت موازی «Tool-LLM» اختراع‌شده برایش نیاز نداشت: همان `inputSchema` منتشرشده برای کشف معمولی مستقیم تعریف ابزار شد (سؤال ۴ همین فایل). حتی تنها استثنای معماری واقعی که این فاز نیاز داشت — وابستگی مستقیم به Actionهای Core به‌جای یک رابط Repository — یک تنظیم عمدی، محدود، و مستندشده بود (سؤال ۹)، نه یک بازنویسی Core. شش مرحله‌ای که این فایل عبورشان کرد شاهدی هستند، در کد، دقیقاً برای شرط‌بندی بنیادگذار خودِ پلتفرم: لایه‌ی زیرساخت را به‌اندازه‌ی کافی مستقل-از-دامنه و قابلیت-محور بساز، و حتی یک Use Case به‌اندازه‌ی «بذار یک LLM Goalهای کسب‌وکاری چند-مرحله‌ای رو برنامه‌ریزی و اجرا کنه» متفاوت از «محصول بفروش»، معلوم می‌شود چیزی است که پلتفرم می‌تواند میزبانیش کند، نه چیزی که مجبور باشد دورش بازطراحی شود.»

🔁 **سوالات تعقیبی احتمالی:**
1. «آیا هیچ‌وقت لحظه‌ای بود که این شرط‌بندی نزدیک بود شکست بخورد — جایی که Core واقعاً نیاز به تغییر داشت برای فاز ۶؟» → سؤال Persona/هویت (سؤال ۶ همین فایل) نزدیک‌ترین بود — ولی حل‌شدن واقعی مدل هویت موجود Core را دوباره تأیید کرد به‌جای نیاز به تغییر در آن، که خودش شاهد بیشتری برای همان نکته است، نه یک مثال‌نقض.
2. «آیا این یعنی هر قابلیت AI آینده هم اتوماتیک صفر تغییر Core نیاز داره؟» → نه اتوماتیک — یعنی همان انضباط (چک‌کردن در برابر مدل واقعی و موجود قبل از فرض این‌که یک مکانیزم جدید لازمه) باید هر بار تازه اعمال شود؛ فاز ۶ شاهدی است که انضباط کار می‌کند، نه تضمینی که هر مورد آینده به همان شکل حل می‌شود.

🚩 **پرچم‌های قرمز:**
رفتار با فاز ۶ به‌عنوان «بخش AI، پیچ‌شده روی پلتفرم واقعی» — از‌دست‌دادن این‌که اهمیت واقعی کل این فصل دقیقاً برعکس است: شاهدی است که Core هرگز نیاز به یک سوراخ ویژه به‌شکل-AI بریده‌شده در خودش نداشت، از همان اول.
