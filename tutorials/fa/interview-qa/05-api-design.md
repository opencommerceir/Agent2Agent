# ۰۵. طراحی API

این فایل روی تصمیم‌های طراحی API — قراردادهای REST، نسخه‌بندی، اعتبارسنجی، مدیریت خطا — تمرکز دارد؛ جایی که خیلی از توسعه‌دهنده‌ها فقط «قوانین عمومی REST» را حفظ کرده‌اند بدون این‌که بدانند کِی باید از آن‌ها آگاهانه عبور کرد.

---

### Q1: چرا این API کاملاً RESTful نیست؟ فقط یک Endpoint واحد برای اجرای همه‌ی قابلیت‌ها؟ این خلاف بهترین شیوه‌های REST نیست؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا شما REST را یک قانون مقدس می‌دانید، یا می‌فهمید REST یک ابزار برای یک مخاطب خاص است، نه یک هدف فی‌نفسه؟

✅ **جواب مدل:**
«عمداً RESTful کامل نیست، و این یک تصمیم آگاهانه است، نه یک محدودیت. REST کلاسیک فرض می‌کند مصرف‌کننده از قبل می‌داند چه منابعی وجود دارند و آدرس هرکدام چیست (`GET /products/5`) — این برای یک توسعه‌دهنده‌ی انسانی که مستندات را خوانده منطقی است. مخاطب اصلی این API یک ایجنت هوش مصنوعی است که باید بتواند **پویا** قابلیت‌ها را کشف کند، بدون این‌که از قبل یک نقشه‌ی ثابت از آدرس‌ها داشته باشد. `GET /mcp/v1/capabilities` این کشف را انجام می‌دهد؛ `POST /mcp/v1/execute` اجرا را — یک آدرس واحد برای هر ۱۲۷ قابلیت، چون تعداد و نام قابلیت‌ها با گذشت زمان رشد می‌کند و یک ایجنت باید بتواند این رشد را بدون تغییر کد خودش دنبال کند. این یعنی REST را رد نکرده‌ایم — یک لایه‌ی دیگر رویش گذاشته‌ایم که برای این مخاطب خاص بهتر کار می‌کند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «پس هیچ‌جای این پروژه REST واقعی نیست؟» → پنل مدیریت انسانی (Dashboard) دقیقاً برعکس است — چون مخاطبش انسان با مرورگر است، از مسیرهای REST-گونه‌ی معمولی Laravel استفاده می‌کند؛ انتخاب سبک API همیشه بر اساس مخاطب است.
2. «این یعنی GraphQL بهتر نبود؟» → یک جواب صادق و متعادل: GraphQL مشکل «کشف پویا» را با یک مکانیزم دیگر (Introspection) حل می‌کند، ولی MCP یک استاندارد صنعتی نوظهور مشخص برای ارتباط عامل-محور است که این پلتفرم عمداً دنبالش کرده، نه یک انتخاب اختصاصی.

🚩 **پرچم‌های قرمز:**
«REST همیشه بهترین انتخابه» بدون توجه به این‌که مخاطب API چه کسی است.

### Q2: نسخه‌بندی API (v1/v2) چطور طراحی شده؟ چرا URL باید همیشه بر هدر برنده باشه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک مثال واقعی از این‌که یک تصمیم طراحی API چطور از تناقض در خودِ Spec درخواستی کشف و اصلاح شد.

✅ **جواب مدل:**
«`/mcp/v1/*` و `/mcp/v2/*` هم‌زمان و کاملاً مستقل وجود دارند — همان قابلیت‌ها، همان مجوزها، فقط پوشش پاسخ فرق می‌کند (`data`/`meta` در برابر `result`/`metadata`). تشخیص نسخه سه‌لایه است: آدرس URL، بعد هدر `Accept`، بعد Query String. نکته‌ی جالب این است که مشخصات اولیه‌ی این ویژگی، یک تناقض داخلی داشت — ترتیب اولویت گفته‌شده «URL > Header > Query» بود، ولی یک تست نمونه‌ی همان مشخصات، انتظار داشت یک هدر `Accept` روی یک آدرس صریح v1 غلبه کند. اگر این را همان‌طور که نوشته شده بود پیاده می‌کردیم، یک یکپارچه‌سازی v1 می‌توانست بدون هیچ تغییری در کدش، فقط چون یک واسطه‌ی شبکه (مثلاً یک Proxy) یک هدر `Accept` پیش‌فرض اضافه کرده، ناگهان شکل پاسخش عوض شود — دقیقاً همان نوع رفتار پنهان و غافلگیرکننده‌ای که یک API قابل‌اعتماد نباید داشته باشد. تصمیم نهایی (تأییدشده، نه فرض‌شده): آدرس صریح URL همیشه برنده است، بدون استثنا.»

🔁 **سوالات تعقیبی احتمالی:**
1. «تشخیص با هدر/Query پس اصلاً استفاده می‌شه؟» → کاملاً پیاده‌سازی و تست شده، ولی امروز هیچ‌وقت واقعاً اجرا نمی‌شود چون هر Route واقعی از قبل یک بخش نسخه‌ی صریح در آدرسش دارد.
2. «چطور مطمئنید v1 و v2 دقیقاً همون داده رو برمی‌گردونن؟» → یک تست صریح همین را ثابت می‌کند: همان قابلیت را هم از v1 هم از v2 صدا می‌زند و مطمئن می‌شود `v1.data === v2.result`.

🚩 **پرچم‌های قرمز:**
ندانستن این‌که این یک تناقض واقعی در Spec بود که کشف شد — پذیرفتن یک مشخصات با یک تست نمونه‌ی متناقض بدون سؤال‌کردن، دقیقاً همان چیزی است که یک مهندس ارشد باید تشخیص دهد.

### Q3: اعتبارسنجی ورودی چطور کار می‌کنه؟ Input Schema دقیقاً چیه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک مثال ملموس از یک لایه‌ی اعتبارسنجی متمرکز، نه پراکنده در هر Controller.

✅ **جواب مدل:**
«هر قابلیت یک `inputSchema` دارد — یک آرایه‌ی ساده از نام فیلد به نوع (مثلاً `['query' => 'string', 'limit' => 'integer']`)، که همراه با تعریف خودِ قابلیت در `*Capabilities.php` هر ماژول ثبت می‌شود. `MCPRequestValidationService` قبل از این‌که Handler واقعی صدا زده شود، ورودی خام JSON را در برابر همین Schema چک می‌کند — یک ورودی گم‌شده یا از نوع اشتباه، همان‌جا با `422 VALIDATION_ERROR` رد می‌شود، قبل از این‌که حتی یک خط منطق کسب‌وکاری اجرا شود. یک محدودیت واقعی و مستندشده این سیستم: امروز فقط «فیلد اجباری با یک نوع» را می‌فهمد، مفهوم «اختیاری ولی تایپ‌شده» ندارد — به همین دلیل فیلدهای اختیاری (مثل `notes` روی `commerce.order.place`) عمداً از `inputSchema` کلاً حذف می‌شوند و به‌شکل تدافعی (`$input['notes'] ?? null`) خوانده می‌شوند، به‌جای این‌که به‌اشتباه اجباری علامت بخورند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا این محدودیت رو رفع نکردید؟» → یک بدهی فنی صادقانه و مستند — رفعش نیاز به یک زبان Schema غنی‌تر دارد (شبیه JSON Schema واقعی) که تا امروز ارزشش از پیچیدگی‌اش بیشتر نبوده.
2. «اعتبارسنجی خروجی هم انجام می‌شه؟» → `outputSchema` مستند می‌شود (برای کشف/مستندسازی) ولی امروز به‌شکل خودکار اجرا نمی‌شود — یک تفاوت آگاهانه بین «چه چیزی قول می‌دهیم» و «چه چیزی واقعاً اجباری چک می‌کنیم».

🚩 **پرچم‌های قرمز:**
گفتن «همه‌چیز رو Laravel Form Request اعتبارسنجی می‌کنه» — این پروژه عمداً یک لایه‌ی اعتبارسنجی مستقل و متمرکز برای MCP دارد، جدا از Form Requestهای پنل مدیریت.

### Q4: مدیریت خطا چطور کار می‌کنه؟ یک Exception چطور به یک کد HTTP درست ترجمه می‌شه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک یک لایه‌ی مدیریت خطای متمرکز به‌جای try/catch پراکنده در هر Controller.

✅ **جواب مدل:**
«`MCPExceptionHandler` تنها جایی است که هر خطای MCP فرمت می‌شود. به‌جای این‌که هر Controller بداند کدام Exception به کدام کد HTTP نگاشت می‌شود، این کلاس دو Marker Interface را چک می‌کند: `NotFoundExceptionInterface` (→ `404`) و یک Interface دیگر برای تناقض/تکرار (→ `409`) — هر Exception دامنه‌ای که یکی از این دو را پیاده‌سازی کند، خودکار درست نگاشت می‌شود، بدون این‌که `MCPExceptionHandler` اصلاً اسم آن کلاس Exception را بشناسد. یک Exception که هیچ‌کدام را پیاده‌سازی نکند (مثل `WooCommerceApiException`) به `500 INTERNAL_ERROR` می‌افتد — یک تصمیم آگاهانه، چون یک خطای واقعی سرویس بیرونی، از نظر معنایی، همان چیزی نیست که کلاینت باید مثل یک خطای ۴xx با آن رفتار کند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا دو Marker Interface جدا به‌جای یک enum یا کد عددی؟» → چون یک Interface اجازه می‌دهد یک Exception، بدون تغییر `MCPExceptionHandler`، فقط با `implements`کردن آن، رفتار درست را بگیرد — باز برای گسترش (اصل Open/Closed، فایل ۰۲ همین کتابچه).
2. «یک باگ واقعی که این مکانیزم پیدا کرد رو بگو.» → یک Route ناموجود (مثل یک `agentType` نامعتبر در `/api/agents/{agentType}`) قبلاً به‌اشتباه به `500` تخت می‌شد، به‌جای `404` واقعی خودش — چون `MCPExceptionHandler` قبل از یک اصلاح، `HttpExceptionInterface` (استثنای سطح‌روتینگ Symfony) را اصلاً چک نمی‌کرد؛ این باگ حین اضافه‌کردن ماژول Agent Orchestrator کشف و رفع شد.

🚩 **پرچم‌های قرمز:**
پیشنهاد try/catch جداگانه در هر Controller برای نگاشت خطا — دقیقاً همان چیزی که این لایه‌ی متمرکز جلویش را می‌گیرد.

### Q5: چرا یک Exception عمداً از هیچ Marker Interface‌ای استفاده نمی‌کنه؟ یک مثال واقعی بزن.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک این‌که «۵۰۰ پیش‌فرض» گاهی خودش انتخاب درست است، نه یک شکست در پیاده‌سازی.

✅ **جواب مدل:**
«`RateLimitExceededException` عمداً هیچ‌کدام از دو Marker Interface را پیاده نمی‌کند. دلیل: این خطا نه «چیزی پیدا نشد» است، نه «یک تناقض داده‌ای» — یک وضعیت کاملاً جداست که مستحق کد HTTP خودش (`429`) است، و `MCPExceptionHandler` یک شاخه‌ی `match` اختصاصی برای همین یک Exception دارد. همین الگو برای `WooCommerceApiException` و `ShippingProviderException` هم تکرار شده — هر دو یک شکست واقعی سرویس بیرونی را نشان می‌دهند که معنایش با یک ۴۰۴/۴۰۹ که کلاینت «باید» رفتارش را عوض کند، فرق دارد؛ اینجا کلاینت فقط باید بداند «الان کار نکرد»، نه این‌که «درخواستت اشتباه بود».»

🔁 **سوالات تعقیبی احتمالی:**
1. «چطور تصمیم می‌گیرید یک Exception جدید کدام دسته‌س؟» → یک سؤال ساده: آیا کلاینت باید *رفتارش* را عوض کند (۴xx واقعی)، یا فقط باید بداند «الان جواب نگرفتی، شاید بعداً دوباره امتحان کن» (۵xx یا یک کد اختصاصی)؟
2. «این تصمیم‌ها کجا مستند می‌شن؟» → مستقیم در docblock خودِ کلاس Exception — «implements neither marker interface, same reasoning WooCommerceApiException gives» یک عبارت تکرارشونده‌ی واقعی در این کدبیس است.

🚩 **پرچم‌های قرمز:**
فکرکردن به این‌که «هر Exception باید یک کد ۴xx مشخص داشته باشه» — بعضی خطاها واقعاً باید ۵xx بمانند.

### Q6: قرارداد نام‌گذاری قابلیت‌ها چیه؟ چرا باید دقیقاً ۳ بخش نقطه‌جدا باشه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک قانون کوچک ولی به‌شدت تکرارشونده — سؤال می‌سنجد آیا واقعاً با فرآیند واقعی ساخت این پروژه آشنایید.

✅ **جواب مدل:**
«هر اسم قابلیت باید دقیقاً سه بخش نقطه‌جدا باشد: `دامنه.منبع.فعل` — مثل `commerce.product.search`. این محدودیت در `CapabilityName` (یک Value Object) اجرا می‌شود. جالب این‌جاست: تقریباً **هر مرحله‌ی این پروژه** حداقل یک مورد به این محدودیت برخورده — یک درخواست طبیعی می‌خواست `commerce.warehouse.transfer.request` بنویسد (۴ بخش)، که رد شده و به `commerce.transfer.request` تغییر نام گرفته (با «Transfer» به‌عنوان یک منبع مستقل، نه یک زیرمجموعه‌ی «Warehouse»). این آن‌قدر تکرار شده که در `HANDOFF.md` یک الگوی رسمی و شماره‌گذاری‌شده است (Pattern #13) — راه‌حل استاندارد همیشه یکی از این دو است: یک فعل عمومی مثل «find»/«get» را حذف کن، یا یکی از اسم‌ها را به‌عنوان یک منبع مستقل ترفیع بده.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا اصلاً این محدودیت ۳-بخشی رو گذاشتید؟» → یک قرارداد ثابت و قابل‌پیش‌بینی برای یک ایجنت که این اسم‌ها را می‌خواند/کشف می‌کند، مهم‌تر از انعطاف نام‌گذاری دلخواه است.
2. «یک مثال دیگه از این تصحیح بزن.» → `commerce.bulk.import.products` (۴ بخش) به `commerce.bulk.import_products` تبدیل شد — با ادغام فعل+منبع در یک بخش با زیرخط، به‌جای حذف یک کلمه.

🚩 **پرچم‌های قرمز:**
ندانستن این قانون یا نتوانستن یک مثال واقعی از تغییر نام بر اثر آن ارائه دادن — این یکی از پرتکرارترین جزئیات واقعی این کدبیس است.

### Q7: چرا فیلدهای اختیاری از `inputSchema` عمداً حذف می‌شن به‌جای این‌که Nullable علامت بخورن؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک یک محدودیت واقعی سیستم و چطور دورش با یک قرارداد ساده و ثابت مدیریت شده.

✅ **جواب مدل:**
«چون `MCPRequestValidationService` امروز مفهوم «اختیاری» ندارد — هر کلید در `inputSchema` را «اجباری» می‌بیند. اگر یک فیلد اختیاری (مثل `notes` در ثبت سفارش) در Schema می‌ماند، هر تماسی که آن را نمی‌فرستاد، به‌اشتباه با `422` رد می‌شد. راه‌حل، نه یک تغییر در موتور اعتبارسنجی (که پیچیدگی بیشتری اضافه می‌کرد)، بلکه یک قرارداد ساده و مستند: یک فیلد واقعاً اختیاری، از `inputSchema` کلاً حذف می‌شود و در کدِ Action با `$input['field'] ?? default` خوانده می‌شود. این یک تبادل آگاهانه است — مستندسازی خودکار (فایل `docs/api-reference.md`) این فیلدهای اختیاری را نشان نمی‌دهد، ولی رفتار Runtime همیشه درست است.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این یعنی یک کلاینت نمی‌تونه بفهمه یه فیلد اختیاری وجود داره؟» → دقیقاً همان محدودیت مستند — تنها راه، خواندن مستندات دستی یا خودِ کد است؛ یک بهبود آینده‌ی واقعی، مستندشده در `HANDOFF.md`.
2. «چرا موتور اعتبارسنجی رو گسترش ندادید؟» → چون تا امروز، این محدودیت هرگز واقعاً جلوی یک قابلیت را نگرفته — فقط یک قرارداد ساده لازم داشت، نه یک بازنویسی.

🚩 **پرچم‌های قرمز:**
پیشنهاد «فقط nullable علامتش بزن» بدون دانستن این‌که خودِ موتور اعتبارسنجی اصلاً این مفهوم را نمی‌فهمد.

### Q8: Idempotency در سطح API چطور مدیریت می‌شه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک یک اصل واقعی طراحی API قابل‌اعتماد، فراتر از تعریف خشک (سؤال کامل‌تر Idempotency پرداختی در فایل ۱۳ همین کتابچه باز می‌شود؛ این‌جا سطح عمومی‌تر API).

✅ **جواب مدل:**
«بهترین نمونه، `ConfirmRedirectPaymentAction` است — چون هم مرورگر خریدار می‌تواند برگردد و هم Webhook درگاه پرداخت می‌تواند مستقل برسد، این Action ممکن است دقیقاً برای همان `PaymentSession` بیش از یک‌بار صدا زده شود. به‌جای پردازش دوباره (که یعنی سفارش دوم، کسر دوم موجودی)، اولین کاری که این Action می‌کند چک‌کردن وضعیت فعلی Session است — اگر از قبل `Completed` است، همان نتیجه‌ی قبلی (بدون هیچ نوشتن جدیدی) دوباره برگردانده می‌شود. این الگو، Idempotency به‌معنای واقعی است: نتیجه‌ی فراخوانی دوم دقیقاً همان فراخوانی اول است، نه فقط «خطا نمی‌ده».»

🔁 **سوالات تعقیبی احتمالی:**
1. «همه‌ی قابلیت‌های Nnrite Idempotent هستن؟» → نه، صادقانه — فقط جایی که یک سناریوی واقعی تکرار (مثل Webhook دوبار ارسال‌شده) وجود دارد، این الگو عمداً اضافه شده؛ یک `commerce.coupon.create` دوباره صدا زدن، یک کوپن دوم واقعی می‌سازد.
2. «چرا Idempotency Key واقعی (مثل استاندارد Stripe) استفاده نکردید؟» → چون منبع Idempotency در این مورد خاص، خودِ `tracking_reference` (شناسه‌ی PaymentSession) از قبل موجود بود — یک کلید جدا اضافه‌کردن، تکرار همان چیزی می‌بود که از قبل داشتیم.

🚩 **پرچم‌های قرمز:**
فکرکردن که Idempotency یعنی «فقط دوباره همون خطا رو نده» — Idempotency واقعی یعنی همان نتیجه، نه فقط عدم‌شکست.

### Q9: چطور یک قابلیت جدید MCP رو از صفر اضافه می‌کنید؟ قدم‌به‌قدم بگو.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک جواب عملی و کامل، نه یک توضیح انتزاعی از معماری.

✅ **جواب مدل:**
«فرض کنید می‌خواهیم `commerce.product.archive` اضافه کنیم. اول، یک Action در `Application/Actions` که منطق واقعی را هماهنگ می‌کند (خواندن محصول از Repository، صدازدن یک متد Domain مثل `Product::archive()`، ذخیره). دوم، یک ورودی جدید در `CommerceCapabilities::definitions()` — نام (که باید قرارداد ۳-بخشی را رعایت کند، سؤال ۶)، توضیح، `inputSchema`، `outputSchema`، و `requiredPermissions`. سوم، یک Handler Closure در `CommerceServiceProvider::boot()` که این نام را به همان Action وصل می‌کند، از طریق `CapabilityHandlerRegistry`. چهارم، اگر مجوز جدیدی لازم است، آن مجوز باید به Seeder مربوطه اضافه شود تا واقعاً قابل‌اعطا باشد. آخرین قدم، یک تست Feature کامل که کل مسیر واقعی MCP (نه فقط خودِ Action) را، شامل تست مجوز و ایزوله‌سازی چندمستأجری، پوشش دهد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا نیاز به Migration ندارید اگه ستون جدیدی لازم نیست؟» → دقیقاً همین — این قدم‌ها فقط برای قابلیتی است که از داده‌ی موجود استفاده می‌کند؛ اگر یک Entity/جدول جدید لازم باشد، الگوی هفت‌مرحله‌ای کامل (فایل ۰۲، سؤال ۹ همین کتابچه) اجرا می‌شود.
2. «تست ایزوله‌سازی چندمستأجری دقیقاً چیه؟» → یک تست که مستقیم ثابت می‌کند یک Agent از Tenant دیگر، این قابلیت را برای داده‌ی خودش می‌بیند، نه داده‌ی Tenant صدازننده — یک تست الگوی تکرارشونده در تقریباً هر فایل تست Feature این پروژه.

🚩 **پرچم‌های قرمز:**
فراموش‌کردن قدم ثبت مجوز در Seeder — یک اشتباه واقعی و رایج که باعث می‌شود قابلیت وجود داشته باشد ولی هیچ Agentای واقعاً نتواند آن را صدا بزند.

### Q10: تفاوت بین DTO ورودی و DTO خروجی چیه؟ از یک کلاس مشترک استفاده می‌کنید؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک این‌که چرا حتی یک تفاوت به‌ظاهر کوچک (ورودی در برابر خروجی) نباید یک کلاس مشترک داشته باشد.

✅ **جواب مدل:**
«نه، عمداً جدا. ورودی خام از طریق آرایه‌ی ساده‌ی `$input` وارد یک Action می‌شود (که خودِ Action مقادیر لازم را از آن استخراج می‌کند، معمولاً بدون یک کلاس DTO اختصاصی برای ورودی)؛ خروجی همیشه از طریق یک `*Data` مشخص (مثل `ProductData`) برمی‌گردد. دلیل عدم اشتراک: یک DTO ورودی باید همیشه اختیاری/جزئی باشد (چون کلاینت شاید فقط بخشی از فیلدها را بفرستد)، درحالی‌که یک DTO خروجی باید همیشه کامل باشد (چون کلاینت انتظار یک شکل قطعی دارد). ترکیب این دو در یک کلاس یعنی یا باید همه‌چیز در ورودی nullable شود (که هیچ اعتبارسنجی واقعی نمی‌دهد)، یا خروجی مجبور شود فیلدهای اختیاری بی‌معنی داشته باشد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «پس ورودی هیچ‌وقت type-safe نیست؟» → درست پس از عبور از `MCPRequestValidationService` (سؤال ۳)، نوع هر فیلد تضمین شده است؛ فقط ساختار PHP آن یک آرایه است، نه یک کلاس.
2. «چرا خروجی DTO دارد ولی ورودی نه؟» → چون خروجی یک قرارداد بلندمدت و پایدار با کلاینت‌های بیرونی است (نیاز به ثبات دارد)؛ ورودی هر بار تازه اعتبارسنجی می‌شود، پس نیازی به یک لایه‌ی اضافه‌ی نوع ندارد.

🚩 **پرچم‌های قرمز:**
پیشنهاد «یک DTO مشترک برای هردو بسازیم که تمیزتره» — نشان می‌دهد تفاوت واقعی نیازهای ورودی/خروجی درک نشده.

### Q11: چطور مطمئن می‌شید یک تغییر در یک قابلیت، مشتری‌های موجود رو نمی‌شکنه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک واقعی سازگاری با نسخه‌ی قبل (Backward Compatibility) در سطح API، نه فقط شعار «همیشه سازگار بمون».

✅ **جواب مدل:**
«الگوی ثابت این پروژه: هر فیلد جدید روی یک ورودی/خروجی موجود، همیشه **اختیاری و در انتهای پارامترها** اضافه می‌شود، هرگز اجباری و هرگز وسط لیست. این الگو آن‌قدر تکرار شده که در `HANDOFF.md` یک الگوی رسمی است (Pattern #6). مثال واقعی: وقتی تنوع محصول اضافه شد، `AddToCartAction::execute()` یک پارامتر اختیاری جدید `?int $variantId = null` گرفت — هر تماس قدیمی که این پارامتر را نمی‌فرستاد، رفتارش کاملاً بدون تغییر ماند، که با اجرای کامل مجموعه‌ی تست از قبل موجود، بدون تغییر یک خط از آن تست‌ها، تأیید شد. این خودِ تست‌های قدیمی، سند زنده‌ی «هیچ‌چیز نشکسته» هستند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «اگه واقعاً باید یک تغییر شکننده انجام بدید چی؟» → دقیقاً همان جایی که سیستم نسخه‌بندی (سؤال ۲) وارد می‌شود — یک تغییر شکننده‌ی واقعی، نسخه‌ی جدید API می‌شود، نه یک ویرایش خاموش روی نسخه‌ی موجود.
2. «چرا فیلد جدید باید حتماً آخر پارامترها باشه؟» → چون PHP آرگومان‌های موقعیتی (Positional) را دارد؛ اضافه‌کردن یک پارامتر وسط لیست، معنای پارامترهای بعدی را برای هر تماس موقعیتی قدیمی عوض می‌کند، حتی اگر پارامتر جدید اختیاری باشد.

🚩 **پرچم‌های قرمز:**
«فقط مستندات رو آپدیت می‌کنم که کلاینت‌ها بدونن» — این یک استراتژی سازگاری واقعی نیست؛ کد باید خودش تضمین کند، نه امید به این‌که کلاینت‌ها مستندات را دوباره بخوانند.

### Q12: خطای ۴۲۹ (Rate Limit) و ۴۲۲ (Validation) چه فرقی دارن از نظر طراحی API؟ کدوم Retry-able هست؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک این‌که کدهای ۴xx همه یک معنا ندارند — بعضی به کلاینت می‌گویند «دوباره امتحان کن»، بعضی می‌گویند «هرگز دوباره امتحان نکن تا چیزی عوض بشه».

✅ **جواب مدل:**
«`422 VALIDATION_ERROR` می‌گوید «همین درخواست، همیشه رد می‌شود، تا زمانی که خودِ ورودی عوض شود» — تلاش مجدد بدون تغییر ورودی، همیشه دوباره همان نتیجه را می‌دهد؛ اینجا هیچ منطق Retry واقعی معنا ندارد. `429 TOO_MANY_REQUESTS` کاملاً برعکس است — می‌گوید «همین درخواست، اگر کمی صبر کنی، احتمالاً موفق می‌شود» — این دقیقاً همان کدی است که یک کلاینت خوش‌رفتار (یا یک ایجنت هوشمند) باید با یک Backoff نمایی، دوباره امتحان کند. `EnforceRateLimitAction` این تمایز را با استفاده از `RateLimiter` استاندارد Laravel، به‌ازای هر Agent (نه کل سیستم)، پیاده می‌کند — یعنی یک Agent پرترافیک، بقیه‌ی Agentها را تحت تأثیر قرار نمی‌دهد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «۴۰۳ (بدون مجوز) Retry-able هست؟» → نه — دقیقاً مثل ۴۲۲، تا وقتی مجوزهای واقعی Agent عوض نشود (یک عملیات بیرون از این درخواست)، تلاش مجدد بی‌فایده است.
2. «SDKهای رسمی این تمایز رو نشون می‌دن؟» → بله — `ValidationException` و `AuthorizationException` و امثالشان کلاس‌های جدا هستند، دقیقاً تا کلاینت بتواند برنامه‌نویسی‌شده تصمیم بگیرد کدام‌یک واقعاً ارزش Retry دارد.

🚩 **پرچم‌های قرمز:**
پیشنهاد یک منطق Retry عمومی («فقط هر خطایی رو ۳ بار دوباره امتحان کن») بدون تفکیک بین خطاهای Retry-able و غیر-Retry-able — این می‌تواند یک درخواست نامعتبر را بی‌فایده سه برابر تکرار کند.
