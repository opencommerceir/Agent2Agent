# ۰۷. DDD تاکتیکی

[پیش‌آموزش](../pre-tutorial/04-طراحی-دامنه‌محور-DDD.md) و [فایل ۰۲ همین کتابچه](02-overall-architecture.md) مفاهیم پایه‌ی Entity/Value Object/Aggregate/Domain Event را دادند. این فایل عمیق‌تر می‌رود: این مفاهیم در کد واقعی این پروژه دقیقاً چه شکلی هستند، و کجا یک تصمیم ظریف (مثل «کجا دقیقاً یک رویداد پخش شود») واقعاً اهمیت داشته.

---

### Q1: Entity و Value Object رو با یک مثال واقعی از این کدبیس فرق بذار.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
تشخیص عملی، نه فقط تعریف کتابی «Entity هویت داره، VO نداره».

✅ **جواب مدل:**
«`Order` یک Entity است — دو `Order` با همان مبلغ و همان آیتم‌ها، اگر `id` متفاوت داشته باشند، دو چیز کاملاً متفاوت‌اند؛ هویتش مستقل از مقدارش است و در طول زمان (وقتی وضعیتش از `Pending` به `Shipped` تغییر می‌کند) پایدار می‌ماند. `Money` یک Value Object است — دو `Money` با همان مبلغ و همان ارز، از نظر معنایی **همان** چیزند، بدون این‌که هیچ‌کدام یک `id` داشته باشند؛ اگر بخواهید مقدارش را عوض کنید، یک نمونه‌ی جدید می‌سازید (`add()`)، نمونه‌ی قبلی را تغییر نمی‌دهید. تفاوت عملی در کد: `Order` یک متد `id()` دارد که یک‌بار مقداردهی می‌شود؛ `Money` هیچ متد `id()`ای ندارد، فقط `equals()` که مقدار را با مقدار مقایسه می‌کند، نه هویت با هویت.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چند تا Value Object دیگه اسم ببر.» → `SKU`، `Email`، `CouponCode`، `Address` — همه، خودشان قوانین اعتبارسنجی‌شان را در سازنده اجرا می‌کنند.
2. «یک Entity می‌تونه هیچ رفتاری نداشته باشه، فقط داده؟» → اگر این‌طور باشد، یک نشانه‌ی هشدار «مدل آنمیک» است — سؤال ۶ همین فایل دقیقاً همین را باز می‌کند.

🚩 **پرچم‌های قرمز:**
گفتن «Entity یعنی هر چیزی که تو پایگاه‌داده ذخیره میشه» — Value Objectها هم در پایگاه‌داده ذخیره می‌شوند (مثلاً به‌شکل چند ستون)؛ تمایز واقعی هویت است، نه محل ذخیره‌سازی.

### Q2: Aggregate Root چیه؟ چرا Order یک Aggregate Root هست ولی OrderItem نیست؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک مرز تراکنشی/سازگاری (Consistency Boundary)، نه فقط یک اسم فانتزی برای «Entity اصلی».

✅ **جواب مدل:**
«Aggregate Root تنها نقطه‌ی ورودی برای تغییر یک خوشه از Entityهای مرتبط است — هیچ کد بیرونی هرگز مستقیم یک `OrderItem` را نمی‌سازد یا تغییر نمی‌دهد؛ همیشه از طریق `Order` (مثلاً `Order::addItem()`). دلیل: `Order` باید بتواند قوانینی را که به چند Item هم‌زمان وابسته‌اند تضمین کند — مثلاً «مجموع قیمت آیتم‌ها باید با Subtotal ثبت‌شده هماهنگ باشد». اگر `OrderItem` مستقل و مستقیماً قابل‌تغییر بود، هیچ‌کس تضمین نمی‌کرد این هماهنگی حفظ شود. الگوی «Immutable Order Items» در این پروژه یک قدم فراتر می‌رود: آیتم‌های یک سفارش، بعد از ثبت، اصلاً قابل‌تغییر نیستند — یک تصمیم آگاهانه برای این‌که یک سفارش ثبت‌شده، یک رکورد تاریخی دست‌نخورده بماند، نه چیزی که بعداً بی‌صدا عوض شود.»

🔁 **سوالات تعقیبی احتمالی:**
1. «Repository برای OrderItem جدا هست؟» → نه — `OrderRepositoryInterface` مالکیت پایداری `OrderItem` را هم دارد؛ هیچ Repository مستقلی برای یک Entity فرزند بدون هویت مستقل ساخته نمی‌شود (سؤال ۷ همین فایل).
2. «کدوم Aggregateهای دیگه همین الگو رو دارن؟» → `Invoice`/`InvoiceItem`، `WarehouseTransfer`/`WarehouseTransferItem` — همه با همان «آیتم‌های منجمدشده در زمان ساخت» دقیقاً همین شکل را تکرار می‌کنند.

🚩 **پرچم‌های قرمز:**
پیشنهاد یک Repository مستقل برای `OrderItem` «چون شاید بعداً لازم بشه» — این دقیقاً همان مرز Aggregate را می‌شکند که کل الگو برایش طراحی شده.

### Q3: چطور یک Entity از ساخته‌شدن در یک وضعیت نامعتبر جلوگیری می‌کنه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک این‌که «همیشه معتبر» باید در سازنده تضمین شود، نه با یک متد `validate()` جدا که ممکن است فراموش شود.

✅ **جواب مدل:**
«سازنده‌ی هر Entity/Value Object، هر قانونی که برای معتبربودن لازم است را همان لحظه اجرا می‌کند و در صورت نقض، یک Exception پرتاب می‌کند — یعنی به‌جای «بساز، بعد چک کن»، الگو «چک کن، بعد بساز» است. مثال ملموس: سازنده‌ی `SKU` یک الگوی Regex را روی رشته‌ی ورودی اجرا می‌کند؛ اگر مطابقت نداشته باشد، `InvalidSKUException` همان لحظه پرتاب می‌شود — یک شیء `SKU` نامعتبر **اصلاً نمی‌تواند** در حافظه وجود داشته باشد. این یعنی هر جای دیگر کد که یک `SKU` در دست دارد، مجبور نیست دوباره اعتبارش را چک کند — خودِ نوع، تضمین است.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این برای قوانینی که به چند فیلد هم‌زمان وابسته‌ن هم صدق می‌کنه؟» → بله، دقیقاً سؤال ۱۱ همین فایل — سازنده‌ی `DateRange` هم `start`/هم `end` را می‌گیرد و اگر `end < start` باشد، همان‌جا رد می‌کند.
2. «فرق این با اعتبارسنجی سطح MCP (فایل ۰۵) چیه؟» → دو لایه‌ی کاملاً جدا: اعتبارسنجی MCP یعنی «آیا شکل JSON درست است» (لایه‌ی بیرونی)؛ سازنده‌ی Entity یعنی «آیا این مقدار از نظر کسب‌وکاری معتبر است» (لایه‌ی داخلی) — یک ورودی می‌تواند شکل درستی داشته باشد ولی هنوز از نظر Domain نامعتبر باشد.

🚩 **پرچم‌های قرمز:**
پیشنهاد یک متد `isValid()` که بعد از ساخت صدا زده شود — این الگو اجازه می‌دهد یک شیء نامعتبر برای مدتی در حافظه وجود داشته باشد، دقیقاً همان چیزی که سازنده‌های سخت‌گیر جلویش را می‌گیرند.

### Q4: چرا Value Objectها Immutable هستن؟ یک مثال بزن که چطور «تغییر» یک VO واقعاً کار می‌کنه.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک عملی Immutability، نه فقط تکرار «چون بهتره».

✅ **جواب مدل:**
«اگر `Money` قابل‌تغییر بود، دو کد که به همان نمونه‌ی `Money` اشاره دارند می‌توانستند بی‌خبر از هم، مقدار را عوض کنند — یک باگ کلاسیک Aliasing. به‌جایش، `Money::add(Money $other): Money` یک **نمونه‌ی کاملاً جدید** برمی‌گرداند؛ نمونه‌ی اصلی دست‌نخورده می‌ماند. در سطح Entity، این یعنی وقتی `PricingService` قیمت نهایی را حساب می‌کند، هر مرحله (`Subtotal.add(Tax).subtract(Discount)`) یک `Money` تازه می‌سازد، و می‌توان با اطمینان کامل یک `Money` واسط را در جای دیگری هم استفاده کرد، بدون ترس از این‌که یک محاسبه‌ی بعدی آن را بی‌صدا تغییر دهد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این هزینه‌ی حافظه‌ای نداره؟» → یک هزینه‌ی کوچک و قابل‌قبول (ساخت نمونه‌های موقت بیشتر) در برابر حذف کامل یک کلاس کامل از باگ‌های Aliasing.
2. «Entity هم Immutable هست؟» → نه — Entity عمداً Mutable است (چون هویتش پایدار می‌ماند ولی وضعیتش باید بتواند تغییر کند، مثل `Order::cancel()`)؛ Immutability فقط قانون Value Objectهاست، نه Entityها.

🚩 **پرچم‌های قرمز:**
گفتن «Immutability یعنی نمی‌شه هیچ‌وقت مقدارش رو عوض کرد» — دقیقاً می‌شود، فقط با ساختن یک نمونه‌ی جدید، نه با تغییر نمونه‌ی موجود.

### Q5: Domain Event دقیقاً کجا Dispatch میشه — داخل Entity یا داخل Action؟ چرا اهمیت داره؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک جزئیات معماری ظریف که فقط با خواندن کد واقعی قابل‌جواب‌دادن است.

✅ **جواب مدل:**
«داخل Action، نه داخل Entity. `PlaceOrderAction` بعد از این‌که `Order` را از طریق Repository ذخیره کرد، خودش صریحاً `event(new OrderWasPlaced($order))` را صدا می‌زند — خودِ Entity `Order` هیچ‌وقت به `Event` Facade دسترسی ندارد (چون Entity کاملاً فریم‌ورک‌مستقل است، فایل ۰۲ همین کتابچه). دلیل مهم‌تر این ترتیب: اگر رویداد داخل Entity پخش می‌شد و قبل از ذخیره‌ی موفق در پایگاه‌داده اجرا می‌شد، یک Listener (مثل `OrderPlacedListener` در Loyalty) می‌توانست برای سفارشی که هنوز واقعاً پایدار نشده امتیاز اضافه کند — یک ناسازگاری واقعی اگر ذخیره‌سازی بعداً شکست بخورد. Action صریحاً رویداد را *بعد* از تأیید موفقیت ذخیره‌سازی پخش می‌کند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این یعنی همیشه رویداد بعد از commit تراکنشه؟» → معمولاً بله، ولی دقیقاً «بعد از یک ذخیره‌ی موفق»، نه لزوماً بعد از پایان کل تراکنش HTTP — یک تفاوت ظریف که در فایل ۰۹ همین کتابچه با جزئیات بیشتر باز می‌شود.
2. «یک رویداد داده‌ی کامل حمل می‌کنه یا فقط شناسه؟» → بستگی دارد — `OrderWasPlaced` کل `Order` را حمل می‌کند (چون Listenerهای واقعی به جزئیات کامل نیاز دارند)، ولی رویدادهای دیگر مثل `InventoryWasCommitted` عمداً فقط شناسه حمل می‌کنند و Listener خودش دوباره از Repository می‌خواند — این تفاوت هم در فایل ۰۹ باز می‌شود.

🚩 **پرچم‌های قرمز:**
«رویداد رو داخل خودِ Entity پخش می‌کنم که همه‌جا در دسترس باشه» — این دقیقاً همان چیزی است که استقلال فریم‌ورک لایه‌ی Domain را می‌شکند.

### Q6: مدل آنمیک دامنه (Anemic Domain Model) چیه، و این پروژه چطور ازش دوری کرده؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک تفاوت بین «Entity واقعی با رفتار» و «یک کیسه‌ی داده که همه‌ی منطق بیرونش زندگی می‌کند» — یک نقد رایج و درست به خیلی از پیاده‌سازی‌های ادعایی DDD.

✅ **جواب مدل:**
«مدل آنمیک یعنی Entityها فقط Getter/Setter دارند و تمام منطق واقعی (قوانین، اعتبارسنجی، گذارهای وضعیت) در یک Service بیرونی زندگی می‌کند — که عملاً یعنی DDD فقط در اسم رعایت شده، نه در عمل. این پروژه عمداً برعکس این کار می‌کند: `Order::cancel()` خودش چک می‌کند آیا وضعیت فعلی اصلاً اجازه‌ی این گذار را می‌دهد، و اگر نه، خودش Exception می‌اندازد — این منطق در `PlaceOrderAction` یا یک `OrderService` بیرونی نیست، داخل خودِ `Order` است. همین‌طور `Coupon::calculateDiscount()`، `Subscription::changePlan()`، `WarehouseTransfer`'s state machine — همگی رفتار واقعی روی خودِ Entity، نه اطرافش.»

🔁 **سوالات تعقیبی احتمالی:**
1. «پس Action اصلاً منطقی نداره؟» → داره، ولی نوع دیگری از منطق — هماهنگی چند مرحله (مثلاً «قیمت را حساب کن، بعد موجودی را کم کن، بعد Order را ذخیره کن»)، نه *قوانین* خودِ یک تصمیم Domain واحد.
2. «یه مثال از یک تصمیم که تقریباً آنمیک ساخته می‌شد ولی رفع شد رو بگو.» → همان مثال Product Variants (فایل ۰۱ همین کتابچه) — اگر یک ستون موجودی جدا و بی‌رفتار روی `product_variants` ساخته می‌شد، منطق موجودی مجبور بود جای دیگری (احتمالاً پراکنده در چند Action) تکرار شود؛ گسترش `Inventory` موجود، رفتار را در یک‌جا نگه داشت.

🚩 **پرچم‌های قرمز:**
تعریف Entity فقط با فیلد و Getter/Setter، بدون ذکر هیچ متد رفتاری واقعی — این خودش نمونه‌ی زنده‌ی همان مدل آنمیکی است که سؤال از آن پرسیده.

### Q7: چرا بعضی Entityها (مثل OrderItem یا WorkflowRule) شناسه (id) ندارن؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک جزئیات ظریف و تکرارشونده که فقط با خواندن واقعی کد قابل‌کشف است.

✅ **جواب مدل:**
«Entityهای فرزند (Child Entities) که هیچ‌وقت به‌تنهایی، مستقل از Aggregate Root خودشان، ارجاع داده نمی‌شوند، عمداً `id` مستقل نمی‌گیرند — مثلاً `OrderItem` یا `WorkflowRule`. دلیل: اگر هیچ کدی هرگز نیاز نداشته باشد «فقط این یک آیتم را با شناسه‌اش پیدا کن» (بدون عبور از `Order` والدش)، ساختن یک هویت مستقل برای آن، پیچیدگی بدون سود اضافه می‌کند. این الگو آن‌قدر تکرار شده که در `HANDOFF.md` یک «گوچا»ی رسمی و شماره‌گذاری‌شده است — و مستقیماً به سؤال ۲ همین فایل وصل است: یک Entity بدون هویت مستقل، دقیقاً نشانه‌ی این است که هرگز نباید Aggregate Root خودش باشد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «اگه بعداً لازم شد یک آیتم خاص رو مستقیم ویرایش کنیم چی؟» → دقیقاً یکی از بدهی‌های فنی مستندشده‌ی این پروژه است (`TicketComment`/`CustomerNote` هم همین محدودیت را دارند) — تبدیلش به یک Entity با هویت مستقل، یک تصمیم آگاهانه و آینده است، نه یک باگ فراموش‌شده.
2. «این Entityها اصلاً هیچ شناسه‌ای در پایگاه‌داده ندارن؟» → چرا، ردیف پایگاه‌داده‌شان یک `id` عددی دارد (چون Eloquent نیاز دارد) — ولی خودِ Entity Domain این `id` را در معنای کسب‌وکاری‌اش افشا/استفاده نمی‌کند.

🚩 **پرچم‌های قرمز:**
«هر Entity باید همیشه یک id مستقل داشته باشه» — این یک قانون جهانی نادرست است؛ داشتن هویت مستقل باید توجیه واقعی داشته باشد، نه یک عادت.

### Q8: State Machine روی یک Aggregate چطور پیاده‌سازی میشه؟ یک مثال با گذارهای مجاز بزن.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک مثال کد واقعی، نه فقط تعریف عمومی State Machine (پیش‌آموزش فایل ۰۵ مفهومش را داد؛ این‌جا پیاده‌سازی واقعی).

✅ **جواب مدل:**
«`Shipment` یک نقشه‌ی صریح `ALLOWED_TRANSITIONS` دارد — یک آرایه‌ی ثابت که هر وضعیت فعلی را به لیست وضعیت‌های بعدی مجازش نگاشت می‌کند (مثلاً `Pending → InTransit`، `InTransit → Delivered/Returned/Exception`). متد `changeStatus()` قبل از هر گذار، این نقشه را چک می‌کند و اگر گذار درخواستی در آن نبود، `InvalidArgumentException` می‌اندازد — و اگر معتبر بود، علاوه‌بر تغییر وضعیت، عوارض جانبی مربوطه (مثل ثبت `shipped_at`) را هم خودش انجام می‌دهد. یک نکته‌ی ظریف و آگاهانه: `Exception` (یک وضعیت مشکل حمل) عمداً **قابل‌بازگشت** است — می‌تواند به `InTransit` یا `Returned` برگردد، برخلاف `Delivered`/`Returned` که واقعاً پایانی‌اند — چون یک مشکل واقعی حمل‌ونقل معمولاً حل‌شدنی است، برخلاف تحویل واقعی.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا این نقشه یک ثابت (Constant) روی خودِ کلاسه، نه یک جدول پایگاه‌داده؟» → چون این یک قانون کسب‌وکاری ثابت و بخشی از منطق Domain است، نه داده‌ای که باید در Runtime تغییر کند — گذاردادنش در پایگاه‌داده، معنایش را از Domain به Infrastructure منتقل می‌کرد.
2. «کدوم Aggregateهای دیگه همین الگو دارن؟» → `WarehouseTransfer`، `DelegationRequest`، `Subscription` — هرکدام نقشه‌ی گذار خودشان را دارند، با معنای متفاوت (مثلاً `Subscription` یک گذار خودبازگشتی از `PastDue` به `PastDue` هم دارد، یک تصحیح واقعی که در فایل ۱۶ همین کتابچه با جزئیات بیشتر باز می‌شود).

🚩 **پرچم‌های قرمز:**
پیشنهاد یک زنجیره‌ی `if/elseif` پراکنده برای چک‌کردن گذارها به‌جای یک نقشه‌ی صریح و متمرکز — این دقیقاً همان چیزی است که باعث می‌شود یک گذار غیرمجاز فراموش شود.

### Q9: چرا دو Value Object با یک اسم مشابه (مثل Money) در چند ماژول جدا وجود داره؟ این تکرار کد نیست؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک تبادل آگاهانه بین DRY (Don't Repeat Yourself) و استقلال ماژولی.

✅ **جواب مدل:**
«بله، تکرار کد است — و کاملاً عمدی. Commerce، Finance، و Shipping هرکدام یک کلاس `Money` کاملاً مستقل خودشان را دارند، با تقریباً همان ۴۰ خط منطق. دلیل: وابسته‌شدن Finance به `Commerce\Domain\ValueObjects\Money` یعنی یک وابستگی مستقیم لایه‌ی Domain به یک ماژول دیگر — دقیقاً همان Coupling‌ای که قانون «هیچ ماژولی مستقیم به کلاس ماژول دیگر وابسته نیست» (فایل ۰۲ همین کتابچه) جلویش را می‌گیرد. این پروژه هیچ‌وقت یک «Shared Kernel» برای چیزی به‌کوچکی و ثباتِ `Money` نساخته — تصمیم آگاهانه این بود که تکرار ۴۰ خط، ارزان‌تر از ایجاد یک وابستگی مشترک بین ماژول‌هاست.»

🔁 **سوالات تعقیبی احتمالی:**
1. «اگه فردا یک باگ در فرمول Money پیدا بشه، باید تو چند جا رفعش کنید؟» → یک تبادل صادق — بله، در هر نسخه‌ی مستقل جداگانه؛ این هزینه‌ی واقعی این تصمیم است، پذیرفته‌شده در برابر هزینه‌ی جایگزین (Coupling بین ماژول‌ها).
2. «کِی یک Shared Kernel توجیه داره؟» → وقتی یک مفهوم آن‌قدر پایه‌ای و پایدار است که تغییرش عملاً هرگز اتفاق نمی‌افتد و هزینه‌ی هماهنگی نسخه‌ها بیشتر از سود استقلال می‌شود — چیزی که این پروژه هنوز برایش پیش نیامده.

🚩 **پرچم‌های قرمز:**
«این تکرار حتماً یه اشتباهه، باید یکی‌شون کنید» — بدون شنیدن استدلال معماری پشتش، این نتیجه‌گیری عجولانه و غلط است.

### Q10: یک Repository Interface دقیقاً چه چیزی رو Persist می‌کنه — فقط Aggregate Root، یا Child Entity هم؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک این‌که مرز Repository دقیقاً همان مرز Aggregate است، نه یک مرز جداگانه.

✅ **جواب مدل:**
«یک Repository همیشه مسئولیت پایداری **کل Aggregate** را دارد، نه فقط Root آن — یعنی `InvoiceRepositoryInterface` هم `Invoice` را ذخیره می‌کند هم `InvoiceItem`های آن را، در یک عملیات منسجم، نه دو Repository جدا. این مستقیماً از سؤال ۲ و ۷ همین فایل می‌آید: چون `InvoiceItem` هویت مستقل ندارد و هرگز بیرون از `Invoice` معنا ندارد، هیچ‌وقت `InvoiceItemRepositoryInterface`ی مستقل ساخته نمی‌شود. یک نمونه‌ی جالب‌تر: `BulkOperation` عمداً از این الگوی معمول «ذخیره‌ی کل مجموعه‌ی فرزندان دوباره» عبور می‌کند — چون آیتم‌هایش می‌توانند هزاران‌تا باشند و یک‌به‌یک توسط یک Job طولانی اضافه شوند، `saveItem()` یک ردیف را مستقیم اضافه می‌کند به‌جای بازنویسی کل مجموعه — یک استثنای مستند، نه یک ناهماهنگی.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا BulkOperation این الگوی معمول رو نداره؟» → چون الگوی معمول (بازنویسی کل فرزندان در هر ذخیره) برای یک Transfer با چند آیتم ثابت منطقی است، ولی برای هزاران آیتمی که تدریجاً اضافه می‌شوند، فاجعه‌ی کارایی می‌شود.
2. «این یعنی هیچ Entity فرزندی هیچ‌وقت Repository مستقل نداره؟» → تقریباً همیشه، به‌جز جایی که یک Entity فرزند واقعاً هویت و طول‌عمر مستقل پیدا می‌کند — چیزی که تا امروز در این پروژه اتفاق نیفتاده.

🚩 **پرچم‌های قرمز:**
پیشنهاد یک Repository جدا برای هر Entity، بدون توجه به این‌که کدام‌ها واقعاً هویت مستقل دارند و کدام‌ها نه.

### Q11: چطور یک Invariant چندفیلدی (که به چند مقدار هم‌زمان وابسته‌س) رو در سازنده‌ی یک Entity اجرا می‌کنید؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک مثال واقعی از یک قانون که ساده‌تر از «این فیلد باید مثبت باشه» است.

✅ **جواب مدل:**
«`DateRange` (در ماژول Reporting) دقیقاً همین است — سازنده‌اش هم `start` هم `end` را می‌گیرد، و قبل از تکمیل ساخت، چک می‌کند `end >= start`؛ اگر نه، `InvalidDateRangeException`. جالب این‌جاست که این سازنده کار بیشتری هم می‌کند — به‌جای این‌که فقط اعتبار را چک کند، مقادیر را هم نرمال‌سازی می‌کند (`start` به ابتدای روز، `end` به انتهای روز)، تا یک بازه‌ی «یک‌روزه» هرگز به‌اشتباه داده‌ی همان روز را از دست ندهد. این نشان می‌دهد یک سازنده‌ی Entity/VO می‌تواند هم‌زمان اعتبارسنجی **و** نرمال‌سازی را انجام دهد — هر دو، بخشی از تضمین «این شیء همیشه در یک وضعیت معنادار است».»

🔁 **سوالات تعقیبی احتمالی:**
1. «مثال دیگه‌ای از یک Invariant چندفیلدی بزن.» → `WarehouseTransfer::create()` رد می‌کند اگر انبار مبدا و مقصد یکسان باشند — یک قانونی که به دو مقدار هم‌زمان (نه یکی) وابسته است.
2. «این نرمال‌سازی داخل VO درسته یا باید بیرون از اون باشه؟» → داخلش درست است، چون یک `DateRange` که نرمال نشده اصلاً نباید بتواند در حافظه وجود داشته باشد — همان اصل «چک کن، بعد بساز» سؤال ۳.

🚩 **پرچم‌های قرمز:**
پیشنهاد اعتبارسنجی این نوع قانون در لایه‌ی Application («تو Action چک می‌کنم end بزرگ‌تر از start باشه») — این یعنی هر Call Site دیگری که همین Value Object را می‌سازد، باید همین منطق را دوباره تکرار کند.

### Q12: یک مثال از جایی که یک Invariant رو فراموش کردید در Domain اجرا کنید، و بعداً کشف شد.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک داستان واقعی و صادقانه، نه ادعای «همیشه همه‌چیز رو از اول درست گرفتیم».

✅ **جواب مدل:**
«یک نمونه‌ی واقعی و مستندشده: وقتی تنوع محصول به `CartItem` اضافه شد، قانون واقعی این بود که دو واریانت مختلف از همان محصول باید همیشه دو ردیف جدا در سبد باشند، نه یک ردیف تجمیعی. ولی محدودیت سطح پایگاه‌داده‌ی قدیمی (`unique(cart_id, product_id)`) هنوز فقط ترکیب محصول را می‌شناخت، نه ترکیب محصول+واریانت — یعنی افزودن یک واریانت دوم از همان محصول، می‌توانست با یک خطای خام تکرار در پایگاه‌داده شکست بخورد، نه یک پیام معنادار. این در مرحله‌ی برنامه‌ریزی (نه بعد از یک باگ واقعی در Production) کشف شد — با ممیزی صریح محدودیت‌های واقعی پایگاه‌داده قبل از پیاده‌سازی — و رفعش گسترش همان محدودیت به `unique(cart_id, product_id, variant_id)` بود، هماهنگ با همان قانون Domain که از اول قرار بود اجرا شود.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا این تو Domain به‌جای فقط تو پایگاه‌داده اجرا نمی‌شه؟» → هردو — قانون Domain (`Cart::findItem()` بر اساس ترکیب محصول+واریانت جست‌وجو می‌کند) لایه‌ی اول است؛ محدودیت پایگاه‌داده یک لایه‌ی دفاعی دوم برای زمانی است که چند درخواست هم‌زمان به همان نتیجه برسند.
2. «این نشونه‌ی ضعف فرآیند برنامه‌ریزی‌تونه؟» → برعکس — نشان می‌دهد فرآیند ممیزی قبل از پیاده‌سازی (که در این کدبیس تکرار می‌شود) دقیقاً برای همین نوع شکاف طراحی شده و کار کرد.

🚩 **پرچم‌های قرمز:**
نداشتن هیچ داستان واقعی برای این سؤال — یک نشانه‌ی قوی که فرد هیچ‌وقت واقعاً یک Aggregate پیچیده را از صفر طراحی نکرده.
