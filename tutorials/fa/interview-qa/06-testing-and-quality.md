# ۰۶. تست و کیفیت

۱۱۵۶ تست یک عدد است؛ این فایل نشان می‌دهد پشت آن عدد چه انضباط واقعی‌ای وجود دارد — و کجا این پروژه صادقانه اعتراف می‌کند یک چیز هنوز اندازه‌گیری نشده.

---

### Q1: تست واحد در برابر تست ویژگی — چه زمانی کدوم رو انتخاب می‌کنید؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک قاعده‌ی تصمیم‌گیری واقعی، نه فقط تعریف دو نوع تست.

✅ **جواب مدل:**
«قاعده مستقیماً از لایه‌بندی معماری می‌آید (فایل ۰۲ همین کتابچه): اگر کلاسی که تست می‌کنید در لایه‌ی `Domain` است (کاملاً فریم‌ورک‌مستقل)، یک تست واحد خالص کافی و درست‌تر است — مثل `PricingServiceTest` که هیچ‌وقت Laravel را بوت نمی‌کند. اگر منطق واقعاً به چند لایه (Controller → Action → Repository → پایگاه‌داده) وابسته است، یا رفتاری را تست می‌کند که فقط وقتی Laravel واقعاً بوت شده معنا دارد (مثل `Event`/`Log` Facade، یا `config()`)، یک تست ویژگی لازم است. یک نکته‌ی ظریف و واقعی: بعضی کلاس‌ها که به‌نظر می‌رسد باید تست واحد باشند، در عمل تست ویژگی‌اند — `PlanExecutor` رویدادهای Domain واقعی را از طریق `Event` Facade پخش می‌کند و `CapabilityToolInvoker` به سیستم واقعی مجوز نیاز دارد؛ این‌ها با این‌که فقط یک کلاس را تست می‌کنند، چون به زیرساخت Laravel واقعی نیاز دارند، تست ویژگی حساب می‌شوند، نه چون سناریوی end-to-end کاملی هستند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «پس تست ویژگی همیشه یعنی end-to-end؟» → نه — دقیقاً همان مثال بالا نشان می‌دهد؛ یک تست ویژگی می‌تواند فقط یک کلاس را تست کند، فقط چون آن کلاس به زیرساخت بوت‌شده نیاز دارد.
2. «کدوم سریع‌تر اجراست؟» → تست‌های واحد به‌طور محسوسی سریع‌ترند، چون هیچ Container/پایگاه‌داده بوت نمی‌شود — یک دلیل عملی دیگر برای نگه‌داشتن لایه‌ی Domain کاملاً مستقل.

🚩 **پرچم‌های قرمز:**
«همیشه از تست Feature استفاده می‌کنم چون واقعی‌تره» — نادیده‌گرفتن هزینه‌ی سرعت و ارزش ایزوله‌سازی تست واحد.

---

### Q2: چطور یک Aggregate DDD (مثل Order) رو تست می‌کنید بدون درگیرکردن پایگاه‌داده؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک عملی این‌که چرا Clean Architecture (فایل ۰۲) واقعاً تست را ساده‌تر می‌کند، نه فقط یک شعار معماری.

✅ **جواب مدل:**
«چون `Order` (و هر Entity دیگر) کاملاً فریم‌ورک‌مستقل است، می‌توان مستقیماً با `new Order(...)` یک نمونه ساخت و رفتارش را تست کرد — مثلاً `$order->cancel()` را روی یک سفارش در وضعیت `Pending` صدا زد و ادعا کرد وضعیتش به `Cancelled` تغییر کرد، یا روی یک سفارش `Shipped` صدا زد و ادعا کرد `InvalidOrderStateException` پرتاب می‌شود — همه بدون هیچ پایگاه‌داده‌ای. تست ماشین‌حالت (State Machine) کامل یک Aggregate، دقیقاً همین‌طور نوشته می‌شود: هر گذار مجاز و هر گذار غیرمجاز، به‌شکل جداگانه، روی نمونه‌های خالص PHP. تنها جایی که پایگاه‌داده وارد می‌شود، تست خودِ Repository است (`toEntity()` درست بازسازی می‌کند؟) — که یک لایه‌ی کاملاً جدا و مجزا از تست خودِ Entity است.»

🔁 **سوالات تعقیبی احتمالی:**
1. «مثال واقعی از تست ماشین‌حالت کامل رو بگو.» → `SubscriptionTest` کل ماتریس گذارهای مجاز/غیرمجاز `Subscription` (Trial → Active → PastDue → Cancelled و امثالش) را به‌شکل کامل و خالص پوشش می‌دهد.
2. «Value Objectها هم همین‌طور تست می‌شن؟» → بله، حتی ساده‌تر — مثلاً `SKUTest` فقط ادعا می‌کند یک رشته‌ی نامعتبر باعث پرتاب `InvalidArgumentException` در سازنده می‌شود، بدون هیچ Entity یا پایگاه‌داده‌ای.

🚩 **پرچم‌های قرمز:**
فکرکردن که تست یک Entity همیشه نیاز به Factory/Seeder پایگاه‌داده دارد — دقیقاً برعکس ارزش اصلی DDD تاکتیکی.

### Q3: چطور یک سرویس بیرونی (مثل Stripe) رو در تست شبیه‌سازی می‌کنید؟ چرا هیچ تستی واقعاً به شبکه وصل نمی‌شه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک Test Double در سطح HTTP، نه فقط Mockکردن یک کلاس PHP.

✅ **جواب مدل:**
«دو سطح Mock وجود دارد، برای دو هدف متفاوت. اول، یک کلاس ساختگی کامل (مثل `MockPaymentGateway`) که کل Interface را با رفتار ساده و قابل‌کنترل (`simulate_failure`) پیاده می‌کند — برای تست منطق کسب‌وکاری که فقط به «موفق شد یا نه» اهمیت می‌دهد. دوم، و ظریف‌تر، برای درگاه‌های *واقعی* (Zibal/Stripe) که خودشان باید تست شوند: یک `MockHandler` روی خودِ کتابخانه‌ی HTTP (Guzzle) تزریق می‌شود — یعنی کد واقعی `StripePaymentGateway` واقعاً اجرا می‌شود (ساخت درخواست، تحلیل پاسخ، تبدیل خطا)، فقط پاسخ HTTP از یک فایل/آرایه‌ی از پیش‌نوشته‌شده می‌آید، نه یک سرور واقعی. این تفاوت مهم است: نوع اول فقط قرارداد را تست می‌کند؛ نوع دوم، منطق واقعی Parse/Serialize کلاینت را هم تست می‌کند، بدون این‌که به اینترنت واقعی وصل شود.»

🔁 **سوالات تعقیبی احتمالی:**
1. «پس هیچ‌وقت تست زنده انجام نمی‌دید؟» → نه در `php artisan test` — ولی این پروژه یک نمونه‌ی مستندشده‌ی واقعی از تست زنده‌ی دستی (خارج از مجموعه‌ی خودکار) دارد؛ سؤال ۸ همین فایل دقیقاً همین را باز می‌کند.
2. «این الگو رو کجای دیگه‌ای هم می‌بینید؟» → دقیقاً همین `MockHandler` برای `OpenAIClient`/`ClaudeClient`/`OpenRouterClient` هم استفاده شده — یک الگوی ثابت برای هر کلاینت HTTP بیرونی در این کدبیس.

🚩 **پرچم‌های قرمز:**
«یک متغیر Environment می‌ذارم که تو تست به سرور واقعی وصل نشه» — این پروژه هرگز به این روش تکیه نمی‌کند؛ Mock همیشه در سطح کد تزریق می‌شود، نه یک پرچم محیطی شکننده.

### Q4: یک مثال از تست رگرسیون واقعی که برای یک باگ خاص نوشته شده رو بگو.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک داستان کامل: باگ چی بود، تست چطور دقیقاً همان سناریو را می‌بندد.

✅ **جواب مدل:**
«`OrderRepositoryEagerLoadingTest` دقیقاً برای این ساخته شد. باگ (فایل ۰۴ همین کتابچه، سؤال ۵) این بود که `listByTenant()` رابطه‌ی `items` را Eager Load نمی‌کرد، پس هزینه‌اش با تعداد سفارش‌ها خطی رشد می‌کرد. تست رگرسیون این‌طور نوشته شده: یک سفارش بساز، تعداد Queryهای واقعی اجراشده را بشمار؛ سه سفارش دیگر بساز، دوباره بشمار — و ادعا کن این دو عدد **دقیقاً یکسان** هستند، نه فقط این‌که «نتیجه درست است». نکته‌ی مهم این است که تست، نتیجه را چک نمی‌کند (که همیشه درست بود)، بلکه **تعداد Query** را چک می‌کند — چون خودِ باگ در کارایی بود، نه در صحت داده.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چطور تعداد Query واقعی رو تو تست می‌شمرید؟» → از طریق `DB::listen()` یا ابزار مشابه Laravel که هر Query اجراشده را ثبت می‌کند؛ تست بعد از یک بلوک کد، همان لاگ را می‌شمرد.
2. «این الگو رو جای دیگه‌ای هم دارید؟» → `CheckPermissionTest` خودش یک تست رگرسیون N+1 قدیمی‌تر دارد (برای `findRolesForMember()`، Tech Debt Sprint) که دقیقاً همین سبک را اولین‌بار در این کدبیس تثبیت کرد.

🚩 **پرچم‌های قرمز:**
نوشتن یک تست که فقط «نتیجه درست است» را چک می‌کند برای یک باگ کارایی — این هیچ‌وقت باگ اصلی (تعداد Query) را دوباره کشف نمی‌کند اگر برگردد.

### Q5: خط CI این پروژه چطوره؟ پوشش تست (Coverage) واقعاً چقدره؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
صداقت درباره‌ی یک محدودیت واقعی محیط توسعه، به‌جای یک عدد ساختگی.

✅ **جواب مدل:**
«`.github/workflows/tests.yml` کل ۱۱۵۶ تست را روی هر Push اجرا می‌کند، با `coverage: pcov` (یک افزونه‌ی واقعی PHP که فقط CI آن را نصب می‌کند). جواب صادق درباره‌ی عدد واقعی Coverage این است: این محیط توسعه محلی نه PCOV دارد نه Xdebug — یعنی عدد واقعی Coverage هرگز محلی اندازه‌گیری نشده، فقط CI می‌تواند آن را واقعاً بدهد. آستانه‌ی فعلی CI (`--min=60`) یک مقدار محافظه‌کارانه و placeholder است، نه یک عدد واقعی اندازه‌گیری‌شده — و این محدودیت به‌جای پنهان‌شدن، صریحاً در `HANDOFF.md` ثبت شده، با یک یادداشت که آستانه باید بعد از یک اجرای واقعی CI و خواندن گزارش آپلودشده، به عدد واقعی تنظیم شود.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا این عدد رو حدس نمی‌زنید یا ادعا نمی‌کنید؟» → چون یک عدد ساختگی، بدتر از نداشتن عدد است — به همان اندازه که در فایل ۰۱ (سؤال ۵ همین کتابچه) درباره‌ی صداقت آماری بحث شد.
2. «PCOV چیه و چرا فقط CI داره؟» → یک افزونه‌ی PHP (نه یک پکیج Composer قابل‌نصب) که خط‌های اجراشده را ردیابی می‌کند؛ نصبش نیاز به دسترسی سطح سیستم دارد که در این محیط توسعه‌ی خاص فراهم نیست.

🚩 **پرچم‌های قرمز:**
گفتن یک عدد Coverage قطعی («۸۵٪ داریم») بدون این‌که واقعاً اندازه‌گیری شده باشد — دقیقاً همان نوع ادعای بی‌پایه‌ای که این پروژه عمداً از آن پرهیز می‌کند.

### Q6: چطور تست می‌کنید که چندمستأجری واقعاً درست کار می‌کنه؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
آیا ایزوله‌سازی Tenant فقط یک ادعای معماری است، یا واقعاً با تست اثبات شده.

✅ **جواب مدل:**
«تقریباً هر تست Feature یک سناریوی صریح ایزوله‌سازی دارد: دو Tenant واقعی بساز، برای هرکدام داده‌ی مشابه (مثلاً یک محصول با همان `id` عددی یا یک نام یکسان) بساز، بعد با توکن Agent مربوط به Tenant اول یک قابلیت را صدا بزن و ادعا کن فقط داده‌ی Tenant اول برمی‌گردد — هرگز داده‌ی Tenant دوم، حتی اگر Agent شناسه‌ی دقیق رکورد Tenant دوم را حدس بزند (تلاش برای دسترسی مستقیم با یک `id` که به Tenant دیگری تعلق دارد، باید `404` بدهد، نه داده‌ی واقعی). این دقیقاً همان الگویی است که باگ واقعی نشت Cache (فایل ۰۴، سؤال ۳ همین کتابچه) را کشف کرد.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این تست برای هر قابلیت جداست یا یک تست عمومی؟» → هردو — یک تست عمومی این الگو را روی چند قابلیت پرکاربرد ثابت می‌کند، ولی هر قابلیت جدید هم خودش، مطابق الگوی سؤال ۹ فایل ۰۵ همین کتابچه، این سناریو را در تست Feature خودش دارد.
2. «حدس‌زدن `id` یک ریسک واقعیه؟» → بله — دقیقاً به همین دلیل تست‌ها صریحاً «تلاش با یک id واقعی متعلق به Tenant دیگر» را چک می‌کنند، نه فقط «لیست خالی برمی‌گرده».

🚩 **پرچم‌های قرمز:**
تست ایزوله‌سازی فقط با یک Tenant («مطمئن شو `tenant_id` درسته») — این هیچ‌وقت نشت واقعی بین دو Tenant را کشف نمی‌کند.

### Q7: چرا بعضی تست‌ها Framework-Free (فقط PHPUnit خالص) و بعضی Feature test (نیازمند Laravel بوت‌شده) هستن؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک قاعده‌ی روشن و قابل‌دفاع، نه یک انتخاب دلبخواهی.

✅ **جواب مدل:**
«قاعده مستقیم است: اگر کلاس زیر تست هیچ وابستگی به چیزی «واقعاً بوت‌شده» ندارد (نه `Event` Facade، نه `config()`، نه پایگاه‌داده)، Framework-Free اجرا می‌شود — سریع‌تر، ایزوله‌تر. `PlanExecutorTest`/`CapabilityToolInvokerTest` نمونه‌ی جالبی از استثنای این قاعده‌اند: با این‌که فقط یک کلاس تست می‌کنند (نه یک سناریوی end-to-end کامل)، چون `PlanExecutor` واقعاً رویداد Domain را از طریق `Event` Facade پخش می‌کند و `CapabilityToolInvoker` به سیستم واقعی مجوز نیاز دارد، این‌ها Feature test‌اند — همان دلیل دقیق که `DeprecationNotifierTest`/`MCPRateLimitTest` هم Feature test هستند: نیاز به یک Container بوت‌شده، نه این‌که یک سناریوی کامل چندمرحله‌ای باشند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این یعنی Feature test همیشه کندتره؟» → قابل‌اندازه‌گیری کندتر، بله — ولی این پروژه ترجیح می‌دهد صحت واقعی را بر سرعت تست اولویت بدهد وقتی واقعاً به زیرساخت بوت‌شده نیاز است.
2. «چطور تشخیص می‌دید یک کلاس ناخواسته وابستگی بوت‌شده گرفته؟» → وقتی یک تست Framework-Free ناگهان با خطای «Facade root has not been set» شکست می‌خورد — خودِ خطا این وابستگی پنهان را لو می‌دهد.

🚩 **پرچم‌های قرمز:**
«همه‌چیز رو Feature test می‌کنم که مطمئن‌تر باشم» — نادیده‌گرفتن هزینه‌ی واقعی سرعت و ارزش تست‌های واحد سریع و ایزوله برای بازخورد فوری.

### Q8: یک باگ واقعی که فقط با تست زنده (نه `php artisan test`) پیدا شد رو بگو.

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک محدودیت‌های واقعی تست خودکار — چیزهایی که هیچ Mockای هرگز نشانشان نمی‌دهد.

✅ **جواب مدل:**
«یک نمونه‌ی کامل و مستندشده: وقتی برای اولین‌بار `OpenRouterClient` با اعتبارنامه‌ی واقعی تست شد (نه یک `MockHandler`)، اولین تماس واقعی با `403` شکست خورد. علتش یک رفتار واقعی و ظریف Guzzle بود — وقتی `base_uri` یک مسیر دارد (مثل `https://openrouter.ai/api/v1`) و مسیر درخواست با `/` شروع می‌شود، طبق RFC 3986، Guzzle مسیر `base_uri` را **جایگزین** می‌کند، نه اضافه — یعنی `/api/v1` بی‌صدا حذف می‌شد. این باگ در ۷ تست واحد موجود، که همه یک کلاینت Guzzle از قبل ساخته‌شده تزریق می‌کردند (دقیقاً همان الگوی سؤال ۳ همین فایل)، هرگز دیده نمی‌شد — چون هیچ‌کدام مسیر واقعی «ساخت خودکار `base_uri`» را اجرا نمی‌کردند. رفعش، تغییر قرارداد استاندارد Guzzle بود (`base_uri` با `/` تمام شود، مسیر درخواست با `/` شروع نشود)، به‌همراه یک تست رگرسیون جدید که همان مسیر دقیق را از طریق Reflection، بدون نیاز به شبکه‌ی واقعی، دوباره اجرا می‌کند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا زودتر این باگ رو پیدا نکردید؟» → چون تا آن لحظه، هیچ تستی — حتی یکی — واقعاً این کلاینت را با اعتبارنامه‌ی زنده اجرا نکرده بود؛ یک شکاف واقعی و صادقانه‌مستندشده بین «تست‌شده در برابر Mock» و «تست‌شده در برابر واقعیت».
2. «این کلاس‌های مشابه دیگه هم همین باگ رو داشتن؟» → بله — دقیقاً همین اصلاح، پیش‌دستانه، روی درگاه‌های پرداخت واقعی جدید (Zibal/Stripe) هم از روز اول اعمال شد، بدون این‌که دوباره کشف شود.

🚩 **پرچم‌های قرمز:**
ادعای «Mockکردن کامل یعنی هیچ‌وقت به تست زنده نیاز نداریم» — این باگ دقیقاً اثبات برعکس این ادعا است.

### Q9: تست‌های N+1/تعداد Query چطور نوشته می‌شن؟ چرا فقط چک‌کردن نتیجه کافی نیست؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک الگوی تست کارایی مشخص، نه فقط تست صحت.

✅ **جواب مدل:**
«الگو ثابت است، دقیقاً همان که در سؤال ۴ همین فایل دیدیم: یک شمارنده‌ی Query واقعی (نه شبیه‌سازی‌شده) قبل و بعد از یک عملیات فعال می‌شود، و ادعا این است که تعداد Query با رشد داده (مثلاً از ۱ سفارش به ۴ سفارش) **ثابت** می‌ماند، نه خطی رشد می‌کند. این از تست معمولی («نتیجه درست است») اساساً متفاوت است، چون یک Eager Load ناقص می‌تواند همچنان نتیجه‌ی کاملاً درستی برگرداند — فقط با هزینه‌ی چند برابر Query — و یک تست معمولی هرگز این را نمی‌بیند.»

🔁 **سوالات تعقیبی احتمالی:**
1. «این تست‌ها چقدر شکننده‌ن؟» → یک ریسک واقعی — اگر یک تغییر معماری آینده عمداً یک Query اضافی معنادار اضافه کند، این تست باید آگاهانه به‌روزرسانی شود؛ این تست‌ها یک محافظ رگرسیون هستند، نه یک قانون تغییرناپذیر.
2. «چرا این الگو برای هر Repository اعمال نشده؟» → دقیقاً همان محدودیت صادقانه‌ی سؤال ۶ فایل ۰۴ همین کتابچه — ممیزی کامل ۴ مورد واقعی پیدا کرد و رفع کرد؛ این ابزار (`performance:check-lazy-loading`) امروز به‌عنوان یک محافظ مداوم اجرا می‌شود، نه این‌که همه‌ی Repositoryها یک‌بار برای همیشه دستی چک شده باشند.

🚩 **پرچم‌های قرمز:**
فکرکردن که «اگه تست سبز شد، کارایی هم تضمین شده» — یک تست معمولی هیچ‌وقت هزینه‌ی Query را نمی‌بیند، فقط نتیجه را.

### Q10: چطور مطمئن می‌شید یک Refactor بزرگ (مثل استخراج `FinalizeSuccessfulPaymentAction`) هیچی رو نشکسته؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
اعتماد به Refactor از طریق تست، نه از طریق بازخوانی دستی کد.

✅ **جواب مدل:**
«وقتی منطق مشترک «یک پرداخت موفق شد» از داخل `ProcessPaymentAction` (که قبلاً این منطق را به‌شکل درون‌خطی داشت) به یک Action کاملاً جدید (`FinalizeSuccessfulPaymentAction`) استخراج شد تا هم مسیر همزمان قدیمی هم مسیر جدید مبتنی بر Redirect بتوانند از آن استفاده کنند، معیار موفقیت این بود: **کل مجموعه‌ی تست پیش از این Refactor (`ProcessPaymentTest`/`CheckoutCapabilityTest`/`RefundPaymentTest`/`PaymentTest`)، بدون تغییر یک خط، باید کاملاً سبز بماند.** این نه یک ادعا، بلکه یک تأیید واقعی و اجراشده بود — چون این تست‌ها رفتار *مشاهده‌پذیر* (Observable Behavior) را چک می‌کنند، نه پیاده‌سازی داخلی، سبزماندنشان بدون تغییر، دقیقاً همان مدرکی است که یک Refactor واقعاً فقط ساختار را عوض کرده، نه رفتار را.»

🔁 **سوالات تعقیبی احتمالی:**
1. «اگه یکی از تست‌های قدیمی شکسته بود چی؟» → یعنی Refactor رفتار را هم عوض کرده بود، نه فقط ساختار — یک سیگنال فوری برای توقف و بازبینی، نه فقط اصلاح تست برای سبزکردنش.
2. «تست جدیدی هم برای خودِ Action استخراج‌شده نوشتید؟» → بله — علاوه‌بر اثبات «هیچی نشکسته»، `FinalizeSuccessfulPaymentAction` تست‌های مستقل خودش را هم گرفت، چون حالا یک واحد قابل‌فراخوانی مستقل از دو مسیر مختلف است.

🚩 **پرچم‌های قرمز:**
«بعد از Refactor یه‌کم تست‌ها رو ویرایش کردم که سبز بشن» — اگر تست‌های رفتاری (نه پیاده‌سازی) بعد از یک Refactor خالص نیاز به ویرایش داشته باشند، این یک نشانه‌ی هشدار است، نه یک قدم عادی.

### Q11: SDKهای رسمی این پروژه چطور تست می‌شن؟ چرا مستقل از `php artisan test` هستن؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
درک این‌که یک SDK باید بتواند کاملاً بیرون از اپلیکیشن اصلی، مستقل، اثبات‌پذیر باشد.

✅ **جواب مدل:**
«هر پنج SDK (PHP، Laravel، Python، Node.js/TypeScript، Go) مجموعه‌ی تست کاملاً مستقل خودشان را دارند، هرکدام با ابزار استاندارد زبان خودش (`phpunit`، `python -m unittest`، `node --test`، `go test`) — نه بخشی از `php artisan test`. دلیل ساده است: یک SDK باید بتواند کاملاً بیرون از این مخزن، در پروژه‌ی یک توسعه‌دهنده‌ی دیگر، کار کند؛ اگر تست‌هایش به بوت‌شدن Laravel وابسته بود، این ادعا خودش دروغ می‌شد. هر پنج SDK همان انضباط «هیچ تستی واقعاً به شبکه وصل نمی‌شود» (سؤال ۳) را هم دارند — یک `Transport` تزریقی قابل‌جایگزینی با یک نسخه‌ی ساختگی، دقیقاً همان الگوی `MockHandler` که برای Guzzle دیدیم، فقط در چهار زبان دیگر تکرار شده.»

🔁 **سوالات تعقیبی احتمالی:**
1. «SDK لاراول هم همینه؟» → نه دقیقاً — چون هدفش اتصال به یک اپلیکیشن Laravel واقعی است، با Orchestra Testbench (یک کانتینر واقعی Laravel، ولی بدون شبکه) تست می‌شود؛ اولین بار در `packages/` که یک بسته واقعاً نیاز به بوت‌شدن Laravel داشت.
2. «۷۱ تست جدید SDKهای چندزبانه چطور واقعاً اجرا و تأیید شدن؟» → با اجرای واقعی هر ابزار تست هر زبان در همان سشن، نه فقط نوشتن و فرض‌کردن که کار می‌کنند — همان انضباط «هرگز بدون اجرای واقعی ادعا نکن».

🚩 **پرچم‌های قرمز:**
فکرکردن که همه‌ی تست‌های پروژه، شامل SDKها، در یک دستور واحد اجرا می‌شوند — این پروژه عمداً این‌ها را جدا نگه داشته.

### Q12: تست‌نویسی برای Webhook (مثل Stripe) چطوره؟ امضای HMAC رو چطور در تست تأیید می‌کنید؟

🎯 **مصاحبه‌کننده واقعاً دنبال چیه؟**
یک مثال دقیق از تست یک مکانیزم امنیتی واقعی، نه فقط یک مسیر HTTP معمولی.

✅ **جواب مدل:**
«`PaymentCallbackRouteTest` یک امضای Stripe **واقعی خودامضا** (Self-Signed) در خودِ تست می‌سازد — با همان فرمول واقعی Stripe (`hash_hmac('sha256', "{timestamp}.{raw_body}", $secret)`) که `StripeWebhookVerifier` هم استفاده می‌کند، ولی با یک کلید مخفی آزمایشی، نه واقعی. این یعنی تست، خودِ منطق اعتبارسنجی امضا را — نه فقط «آیا مسیر Webhook جواب ۲۰۰ می‌دهد» — واقعاً اجرا می‌کند: یک درخواست با امضای درست باید قبول شود، یک درخواست با امضای دستکاری‌شده باید با `400` رد شود. یک سناریوی ظریف‌تر هم پوشش داده می‌شود: Stripe گاهی چند مقدار `v1` امضا هم‌زمان می‌فرستد (دوره‌ی چرخش کلید)؛ تست ثابت می‌کند تطابق با **هرکدام** از این چند امضا کافی است، نه فقط اولی.»

🔁 **سوالات تعقیبی احتمالی:**
1. «چرا کلید واقعی Stripe رو تو تست استفاده نمی‌کنید؟» → چون هیچ تستی نباید به یک راز واقعی Production وابسته باشد؛ یک کلید آزمایشی، همان فرمول ریاضی را کاملاً تست می‌کند بدون افشای هیچ رازی.
2. «Idempotency Webhook هم همینجا تست میشه؟» → بله — همان فایل، سناریوی «همان Webhook دوبار می‌رسد» را هم پوشش می‌دهد، ادعا می‌کند فقط یک‌بار سفارش/پرداخت واقعاً پردازش می‌شود (سؤال ۸، فایل ۰۵ همین کتابچه).

🚩 **پرچم‌های قرمز:**
تست‌کردن یک مسیر Webhook فقط با «آیا ۲۰۰ برمی‌گردونه» بدون تست خودِ منطق اعتبارسنجی امضا — این دقیقاً همان چیزی است که یک آسیب‌پذیری امنیتی واقعی را پنهان نگه می‌دارد.
