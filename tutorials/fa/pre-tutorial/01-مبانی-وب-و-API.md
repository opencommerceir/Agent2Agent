# ۱. مبانی برنامه‌نویسی وب و API

قبل از هر چیز دیگری، باید بدانیم وقتی می‌گوییم «یک ایجنت هوش مصنوعی به پلتفرم وصل می‌شود»، دقیقاً چه اتفاق فنی‌ای می‌افتد. جواب کوتاه: یک درخواست HTTP فرستاده می‌شود و یک پاسخ JSON برمی‌گردد. این فصل یعنی همین جمله را کامل باز کنیم.

## کلاینت و سرور (Client / Server)

**تعریف ساده:** «کلاینت» چیزی است که درخواست می‌دهد (مرورگر شما، یک اپ موبایل، یک اسکریپت پایتون، یک ایجنت هوش مصنوعی). «سرور» چیزی است که همیشه روشن است، منتظر درخواست می‌ماند، و جواب می‌دهد.

**چرا مهم است:** تقریباً هر سیستم نرم‌افزاری امروزی روی همین مدل ساده بنا شده — یک طرف چیزی می‌خواهد، طرف دیگر آن را فراهم می‌کند.

📍 **در این پروژه:** سرور Laravel این پروژه است (روی `php artisan serve` یا هر هاست واقعی). کلاینت می‌تواند مرورگر یک ادمین باشد که پنل مدیریت را باز کرده، یا یک ایجنت هوش مصنوعی که با یکی از پنج SDK این پلتفرم وصل شده (سری اصلی، فایل ۲۱).

## HTTP

**تعریف ساده:** HTTP یک «زبان مشترک» است که کلاینت و سرور با آن با هم حرف می‌زنند — یک قرارداد ثابت برای این‌که درخواست و پاسخ چه شکلی باشند.

**چرا مهم است:** بدون یک قرارداد مشترک، هر سرور باید یک زبان اختصاصی خودش را اختراع می‌کرد و هیچ کلاینتی نمی‌توانست با اطمینان با آن حرف بزند. HTTP این مشکل را برای کل اینترنت یک‌بار برای همیشه حل کرده.

📍 **در این پروژه:** هر تعامل با این پلتفرم — از باز کردن پنل مدیریت تا صدا زدن یک قابلیت هوش مصنوعی — روی HTTP سوار است.

## متدهای HTTP (GET، POST، PUT/PATCH، DELETE)

**تعریف ساده:** هر درخواست HTTP یک «فعل» (Verb) دارد که نیت آن را مشخص می‌کند:

| متد | نیت | مثال ساده |
|---|---|---|
| `GET` | «فقط بده ببینم» — هیچ چیزی را تغییر نمی‌دهد | لیست محصولات را بگیر |
| `POST` | «یک چیز جدید بساز» یا «یک عملیات را اجرا کن» | یک سفارش جدید ثبت کن |
| `PUT`/`PATCH` | «چیزی که از قبل هست را ویرایش کن» | آدرس مشتری را به‌روزرسانی کن |
| `DELETE` | «چیزی را پاک کن» | یک محصول را حذف کن |

**چرا مهم است:** این تفکیک به سرور و هر واسطه‌ای (مثل یک Cache یا Firewall) اجازه می‌دهد فوراً بفهمد یک درخواست «فقط خواندنی» است یا «چیزی را تغییر می‌دهد» — بدون این‌که محتوای درخواست را باز کند.

📍 **در این پروژه:** جالب است بدانید دروازه‌ی اصلی این پلتفرم (MCP Gateway، فصل ۱۰ همین پیش‌آموزش) عمداً همه‌چیز را از طریق یک متد واحد (`POST`) رد می‌کند، نه این‌که برای هر قابلیت یک آدرس/متد جدا بسازد — دلیلش را در فصل ۱۰ می‌بینید.

## کدهای وضعیت HTTP (Status Codes)

**تعریف ساده:** هر پاسخ HTTP یک عدد سه‌رقمی دارد که نتیجه را خلاصه می‌کند — کلاینت لازم نیست کل متن پاسخ را بخواند تا بفهمد موفق بوده یا نه.

| بازه | معنی | مثال‌های پرکاربرد در این پروژه |
|---|---|---|
| `2xx` | موفق | `200 OK` |
| `4xx` | خطای سمت کلاینت (درخواست غلط بوده) | `401` (احراز هویت نشده)، `403` (مجوز ندارد)، `404` (پیدا نشد)، `422` (ورودی نامعتبر)، `429` (تعداد درخواست زیاد) |
| `5xx` | خطای سمت سرور | `500` (خطای داخلی غیرمنتظره) |

📍 **در این پروژه:** `MCPExceptionHandler` (سری اصلی، فایل ۵) دقیقاً همین کار را می‌کند — هر نوع خطای داخلی کد را به یکی از همین کدهای استاندارد HTTP ترجمه می‌کند، تا هر کلاینتی (نه فقط PHP) بتواند رفتار درستی نشان دهد.

## URL و Endpoint

**تعریف ساده:** URL آدرس یک منبع روی وب است (`https://api.opencommerce.ir/mcp/v1/execute`). «Endpoint» یعنی یک آدرس مشخص که سرور برایش رفتاری تعریف کرده.

📍 **در این پروژه:** `POST /mcp/v1/execute` مهم‌ترین Endpoint کل پلتفرم است — تقریباً هر قابلیت کسب‌وکاری (از جست‌وجوی محصول تا اجرای یک هدف با هوش مصنوعی) از همین یک آدرس عبور می‌کند.

## REST و «API»

**تعریف ساده:** API (Application Programming Interface) یعنی «دری که یک برنامه برای برنامه‌های دیگر باز می‌گذارد تا بدون دیدن کد داخلی‌اش، با آن کار کنند». REST یک سبک رایج برای طراحی API است: هر «چیز» (Resource) یک آدرس مشخص دارد، و متدهای HTTP (بالا) روی آن‌ها عمل می‌کنند — مثلاً `GET /products/5` یعنی «محصول شماره‌ی ۵ را بده».

**چرا مهم است:** بدون API، هر برنامه فقط می‌تواند با کاربر انسانی از طریق صفحه‌ی وب حرف بزند — نه با برنامه‌ی دیگری. API یعنی نرم‌افزارها با نرم‌افزارهای دیگر حرف می‌زنند.

📍 **در این پروژه:** MCP Gateway هم یک API است — ولی، همان‌طور که فصل ۱۰ توضیح می‌دهد، به‌طور آگاهانه کاملاً RESTful نیست (یک آدرس واحد به‌جای آدرس‌های جدا برای هر منبع) — چون مخاطبش انسان با مرورگر نیست، یک ایجنت هوش مصنوعی است که باید بتواند همه‌ی قابلیت‌های ممکن را **کشف** کند، نه این‌که از قبل آدرس هرکدام را بداند.

## JSON

**تعریف ساده:** یک فرمت متنی ساده برای نشان‌دادن داده — یک سری جفت «کلید: مقدار»، شبیه یک دیکشنری:

```json
{
  "name": "لپ‌تاپ",
  "price": 25000000,
  "in_stock": true
}
```

**چرا مهم است:** تقریباً هر زبان برنامه‌نویسی امروزی می‌تواند JSON را بخواند و بنویسد — یعنی یک زبان مشترک بین سرور PHP و کلاینت Python/Go/JavaScript.

📍 **در این پروژه:** هر درخواست و پاسخ MCP Gateway، صد در صد JSON است. حتی وقتی یک ایجنت با زبان کاملاً متفاوتی (Go) وصل می‌شود، همان JSON دقیقاً به همان شکل خوانده می‌شود.

## بدنه‌ی درخواست/پاسخ (Body) و هدرها (Headers)

**تعریف ساده:** یک درخواست HTTP از دو بخش اصلی تشکیل شده — «هدرها» (اطلاعات فراداده، مثل «این توکن منم» یا «محتوا از نوع JSON است») و «بدنه» (خودِ داده، معمولاً JSON).

📍 **در این پروژه:** توکن احراز هویت یک Agent همیشه در هدر `Authorization: Bearer <token>` فرستاده می‌شود، نه در بدنه‌ی JSON — یک قرارداد امنیتی استاندارد که در فصل ۷ این پیش‌آموزش بیشتر توضیح داده می‌شود.

## بی‌حالت بودن (Stateless)

**تعریف ساده:** یعنی سرور هیچ‌چیزی از درخواست قبلی همان کلاینت به یاد نمی‌آورد — هر درخواست باید کامل و مستقل باشد (مثلاً هر بار توکن را دوباره بفرستد، نه این‌که فرض کند «چون قبلاً لاگین کرده بود، این بار هم می‌شناسمش»).

**چرا مهم است:** بی‌حالت بودن یعنی می‌توان صدها سرور موازی داشت بدون این‌که نگران باشیم کدام سرور «حافظه‌ی» یک کاربر خاص را دارد — مقیاس‌پذیری از همین‌جا می‌آید.

📍 **در این پروژه:** دروازه‌ی MCP کاملاً بی‌حالت است (هر تماس، توکن خودش را با خودش می‌آورد) — برخلاف پنل مدیریت انسانی که از Session (نشست، فصل ۷) استفاده می‌کند، چون کاربرش مرورگر با کوکی است، نه یک ایجنت.

## Backend در برابر Frontend

**تعریف ساده:** «Frontend» چیزی است که کاربر مستقیماً می‌بیند و با آن کلیک می‌کند (رابط کاربری). «Backend» منطق، پایگاه‌داده و قوانین کسب‌وکاری‌ای است که پشت پرده اجرا می‌شود و معمولاً کاربر آن را نمی‌بیند.

📍 **در این پروژه:** این پلتفرم اساساً یک **Backend خالص** است — عمداً هیچ فروشگاه رو-به-مشتری (Storefront) ندارد (سری اصلی، فایل ۱۹). تنها بخش‌های Frontend واقعی، پنل مدیریت انسانی و دموی Showcase هستند؛ بقیه‌ی پلتفرم فقط با API حرف می‌زند.
