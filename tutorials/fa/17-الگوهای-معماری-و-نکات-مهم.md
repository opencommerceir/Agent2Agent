# ۱۷. الگوهای معماری تثبیت‌شده و نکات مهم

در فایل‌های قبلی، این الگوها بارها و بارها تکرار شدند. این فایل، همه‌ی آن‌ها را یک‌جا و به‌شکل مرجع سریع جمع می‌کند — اگر روی این پروژه کار می‌کنید، این فایل «چیت‌شیتی» است که باید همیشه در دسترس باشد.

## بخش الف — الگوهای معماری (باید همیشه رعایت شوند)

### ۱. اسکالر صریح همه‌جا، `AuthContext` فقط در مرز MCP
Repository ها و Action ها همیشه `int $tenantId`/`int $agentId` می‌گیرند، هرگز `AuthContext` کامل. فقط Handler های داخل ServiceProvider، `AuthContext` را باز می‌کنند. (استثنای مستند: چند Interface داخل Agent Orchestrator که واقعاً باید دوباره وارد همان مرز شوند — فایل ۱۲ و ۱۴.)

### ۲. Marker Interface برای مسیریابی خطا
هر Exception دامنه‌ای که باید ۴۰۴ یا ۴۰۹ برگرداند، `NotFoundExceptionInterface` یا `ConflictExceptionInterface` را پیاده‌سازی می‌کند — نه این‌که هسته کلاس آن ماژول را بشناسد.

### ۳. Action ترکیب‌شده از Action دیگر، عادی است
مثل `AddToCartAction` که به `CheckInventoryAction` وابسته است. تکرار منطق درست، همیشه بدتر از فراخوانی آن است.

### ۴. جدایی Preview و Apply واقعی
هر محاسبه‌ای که اثر جانبی دارد، دو Action جدا می‌گیرد: یکی پیش‌نمایش بدون اثر (`CalculatePricingAction`)، یکی اعمال واقعی (`ApplyCouponAction`) — نه یک پرچم `$apply = false`.

### ۵. چرخه‌ی دوفازی موجودی
`reserve()/release()` (نگه‌داشتن نرم) در برابر `commit()/restore()` (انتقال سخت). هیچ حالت سومی اضافه نشود.

### ۶. گسترش با پارامتر انتهایی اختیاری
وقتی یک Action باید کمی بیشتر کار کند، یک پارامتر جدید و **اختیاری در انتها** اضافه می‌شود؛ هر فراخوان قبلی که آن را پاس نمی‌دهد، رفتارش صددرصد بدون تغییر می‌ماند. این پرکاربردترین الگوی کل پروژه است.

### ۷. فیلد اختیاری MCP، فقط از inputSchema حذف می‌شود
هیچ `nullable: true` وجود ندارد؛ یک فیلد اختیاری صرفاً در schema نمی‌آید و در Action با `$input['x'] ?? null` خوانده می‌شود.

### ۸. وابستگی بین ماژول‌ها فقط از طریق Repository Interface
هرگز به Model یا Exception یک ماژول دیگر وابسته نشوید — فقط به Interface دامنه‌ی آن.

### ۹. Exception ماژول فراخوان، نه ماژول هدف
یک بررسی «آیا این وجود دارد؟» بین دو ماژول، همیشه Exception خودِ ماژول فراخوان را پرتاب می‌کند (حتی اگر هر دو یک Marker Interface مشترک داشته باشند).

### ۱۰. یکپارچگی دوطرفه از طریق Interface تعریف‌شده توسط مصرف‌کننده
وقتی ماژول A به چیزی از ماژول B نیاز دارد، **خود A** آن Interface را تعریف و یک پیاده‌سازی بی‌اثر پیش‌فرض می‌دهد؛ B (اگر نصب باشد) آن را با پیاده‌سازی واقعی جایگزین می‌کند.

### ۱۱. Listener هم مثل هر مصرف‌کننده‌ی دیگر بین‌ماژولی رفتار می‌کند
یک Listener روی رویداد ماژول دیگر، دوباره از طریق Repository Interface آن ماژول داده‌ی تازه می‌خواند — به داده‌ی داخل رویداد اعتماد کامل نمی‌کند.

### ۱۲. اضافه‌کردن بی‌درخواست چیزی که درخواست ضمنی آن را دارد
اگر چیزی (یک Exception، یک متد Repository) صراحتاً درخواست نشده ولی نبودش یعنی دور زدن یک قرارداد یا یک شکست زشت در Runtime، اضافه می‌شود — همیشه با یک توضیح مستند.

### ۱۳. نام قابلیت/مجوز همیشه دقیقاً سه بخش
`domain.resource.action`. اگر ۲ یا ۴ بخش شد، بازسازماندهی می‌شود.

### ۱۴. نوشتن روی موجودیت یک ماژول قدیمی‌تر، فقط با یک متد اختصاصی
مثل `Order::assignShipping()` — تصویر آینه‌ای الگوی ۸، فقط برای نوشتن نه خواندن.

### ۱۵. رجیستری در حافظه برای «انتخاب بین چند پیاده‌سازی با نام»
`ConnectorRegistry`/`ShippingProviderRegistry`/`ChannelSenderRegistry` — همیشه همین شکل: `register()`/`get()`، Bind شده به‌عنوان Singleton، پر شده در `boot()`.

### ۱۶. دغدغه‌ی میان‌بخشی بدون Middleware طبیعی، یک فراخوانی صریح Action است
مثل محدودیت نرخ MCP — چون مسیرهای `mcp/*` هیچ Middleware Pipeline ندارند.

### ۱۷. Retry با تأخیر نمایی، داخل Action ای که کل عملیات را صاحب است
نه داخل Client/Sender سطح پایین.

### ۱۸. یک Repository interface می‌تواند رکورد فرزند خودش را هم صاحب باشد
مثل `TicketRepositoryInterface` که `TicketComment` را هم مدیریت می‌کند.

### ۱۹. یک رابط انسانی (پنل مدیریت یا دمو) همیشه از همان Action های موجود استفاده می‌کند
هرگز منطق کسب‌وکاری را برای یک Transport جدید دوباره نمی‌نویسد.

### ۲۰. استفاده‌ی مجدد از لایه‌ی خواندن یک ماژول دیگر برای محاسبه‌ی تکراری
مثل Analytics که مستقیم Query Builder های Reporting را صدا می‌زند، نه یک محاسبه‌ی موازی.

| ۲ | نام قابلیت/مجوز باید دقیقاً ۳ بخش داشته باشد. |

| ۵ | ثبت **Handler** و ثبت **Description** یک قابلیت، دو کار کاملاً جدا هستند — فراموش‌کردن Seeder، یعنی خطای «Handler پیدا نشد» با وجود این‌که در ServiceProvider نوشته شده. |

| ۷ | ریاضیات رزرو موجودی فقط اگر بدانید «در کدام فاز هستید» درست جمع می‌شود — همیشه هم `quantityOnHand()` و هم `quantityReserved()` را در تست چک کنید، نه فقط `available()`. |
| ۸ | `OrderItem`/`Discount` هیچ فیلد `id` روی موجودیت Domain ندارند — چون هیچ‌جا با شناسه‌ی خودشان جست‌وجو نمی‌شوند. |
| ۹ | وابستگی یک Connector فقط یک‌بار، در `boot()`، تزریق می‌شود — Rebind بعد از آن در تست بی‌اثر است؛ باید یک نمونه‌ی تازه مستقیم در Registry ثبت شود. |
| ۱۰ | یک `*/` واقعی داخل متن یک Docblock، کامنت را زودتر می‌بندد و بقیه‌اش PHP واقعی (خراب) می‌شود. |
| ۱۱ | کلید ترجمه همیشه باید پیشوند گروه داشته باشد: `t('messages.dashboard.title')`، نه `t('dashboard.title')`. |
| ۱۲ | `?->` فقط مرحله‌ی فراخوانی متد را محافظت می‌کند، نه دسترسی به آرایه پیش از آن — فرم امن: `($arr[0] ?? null)?->method()`. |

## چرا این الگوها اهمیت دارند؟

هر کدام از این الگوها، دقیقاً از یک **تجربه‌ی واقعی** در ساخت خود این پروژه بیرون آمده‌اند — نه یک تئوری انتزاعی. وقتی در فایل‌های ۶ تا ۱۶ دیدیم که یک تصمیم معماری «تأیید شد» یا «رد شد»، این همان لحظه‌ای بود که یکی از این ۲۰ الگو یا ۱۲ نکته، شکل گرفت یا اعمال شد.

اگر یک روز بخواهید یک قابلیت جدید به این پلتفرم اضافه کنید، بهترین راه این است:
1. الگوی هفت‌مرحله‌ای ساخت یک قابلیت را دنبال کنید (فایل ۳).
2. قبل از نوشتن کد، این فایل را مرور کنید تا مطمئن شوید کدام الگو باید اعمال شود.
3. اگر یک تصمیم بزرگ معماری لازم بود (مثل چنگال‌های فایل ۱۱)، اول بپرسید، بعد کد بنویسید.

در فایل بعدی، وارد بخش کاملاً عملی می‌شویم: چطور این پروژه را روی سیستم خودتان نصب، اجرا و تست کنید — و در نهایت دموی زنده را ببینید.
