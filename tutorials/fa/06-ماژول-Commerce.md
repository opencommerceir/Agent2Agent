# ۶. ماژول Commerce — قلب تجاری پلتفرم (فاز ۲)

`Commerce` اولین و بزرگ‌ترین ماژول دامنه است — ۲۳ موجودیت دامنه، حدود ۸۱ Action، ۱۹ Repository و ۵۸ قابلیت MCP. در این فایل، شش مرحله‌ی ساخت آن را می‌بینیم.

## مرحله ۱ — محصول و دسته‌بندی

- موجودیت‌ها: `Product`، `Category`
- Value Object ها: `Money` (عدد صحیح به‌واحد کوچک‌ترین پول + کد ارز — **هرگز float**، چون JSON نوع اعشاری دقیق ندارد)، `SKU` (نرمال‌شده به حروف بزرگ)، `ProductStatus`
- قانون: `commerce.product.search` فقط محصولات **فعال (Active)** را برمی‌گرداند — این یک تصمیم کسب‌وکاری است و در Action نوشته شده، نه در Repository (Repository نباید قانون کسب‌وکاری بداند).
- SKU در سطح هر Tenant یکتاست.

## مرحله ۲ — سبد خرید و موجودی

- موجودیت‌ها: `Cart`، `CartItem`، `Inventory`
- **این مرحله همان‌جایی است که `AuthContext` متولد شد** — و همان‌جایی که یک بار به‌اشتباه `App\Modules\Commerce` داخل `App\Core` وارد شده بود و همان لحظه اصلاح شد. این یکی از یادگیری‌های بنیادین کل پروژه است.

### چرخه‌ی حیات دوفازی موجودی — یکی از مهم‌ترین مفاهیم کل پروژه

موجودی همیشه دو حالت مجزا دارد:

```
reserve() / release()   ← نگه‌داشتن نرم (Soft Hold). وقتی چیزی به سبد اضافه می‌شود.
                           هیچ‌وقت quantity_on_hand را کم نمی‌کند.
commit() / restore()    ← انتقال سخت. وقتی سفارش نهایی ثبت/لغو می‌شود.
                           commit() واقعاً موجودی را کم می‌کند و رزرو نرم را هم آزاد می‌کند.
                           restore() دقیقاً عکس commit() است.
```

این چهار متد روی خود موجودیت `Inventory` زندگی می‌کنند و **هیچ‌وقت نباید یک حالت سوم به این چرخه اضافه شود** — همه‌چیز باید در «نگه‌داشته‌شده در سبد» یا «واقعاً فروخته‌شده» جا بگیرد.

## مرحله ۳ — مدیریت سفارش

- موجودیت‌ها: `Order`، `OrderItem` (کاملاً غیرقابل‌تغییر — بدون هیچ متد تغییردهنده)
- `OrderNumber` به شکل `ORD-YYYYMMDD-XXXXX` (پسوند تصادفی + بررسی تکرار)
- `PlaceOrderAction` کل جریان Cart→Inventory→Order را در یک `DB::transaction` می‌پیچد.
- برخی وضعیت‌ها پایانی‌اند (`Cancelled`/`Refunded`/`Delivered`) و امکان بازگشت از آن‌ها با تابع عمومی `changeStatus()` وجود ندارد — فقط متدهای اختصاصی مثل `cancel()`/`refund()` می‌توانند به آن‌جا برسند تا اثرات جانبی روی موجودی هیچ‌وقت دور زده نشوند.

## مرحله ۴ — مدیریت مشتری

- موجودیت: `Customer`
- Value Object ها: `Email`، `Address`، `CustomerStatus`
- `orders.customer_id` به‌صورت اختیاری اضافه شد (چون سفارش‌های قبلی این ستون را نداشتند) — این اولین نمونه از یک الگوی مهم است: **گسترش با پارامتر انتهایی اختیاری** به‌جای شاخه‌زدن یا کپی‌کردن Action.

## مرحله ۵ — پرداخت و تسویه‌حساب

- موجودیت‌ها: `Payment`، `Coupon`، `Discount`
- سرویس‌های دامنه: `PricingService` (فرمول واحد: `Total = Subtotal + Tax − Discount`) و `CouponValidationService`

### جریان پرداخت-قبل-از-سفارش

```
سبد → محاسبه‌ی قیمت → اعتبارسنجی کوپن → PaymentGatewayInterface::charge()
   → فقط اگر موفق بود → PlaceOrderAction → ذخیره‌ی Payment → اعمال کوپن
```

این یعنی `payments.order_id` هیچ‌وقت null نیست — چون یک پرداخت ناموفق هیچ‌وقت به نقطه‌ای نمی‌رسد که سفارش یا رکورد پرداخت ساخته شود.

`MockPaymentGateway` تنها پیاده‌سازی موجود درگاه پرداخت است؛ همیشه موفق می‌شود مگر این‌که صریحاً `simulate_failure: true` پاس داده شود — روشی تمیز برای تست مسیر شکست بدون شبیه‌سازی واقعی شبکه.

## مرحله ۶ — اتصال‌دهنده‌های واقعی (WooCommerce)

اینجا **الگوی Connector** برای اولین بار به‌صورت واقعی پیاده‌سازی شد:

```
ConnectorInterface / ProductConnectorInterface   ← قرارداد
ConnectorRegistry                                 ← رجیستری در حافظه، ثبت به‌ازای نام
WooCommerceProductConnector                        ← پیاده‌سازی واقعی (Guzzle)
MockProductConnector                                ← پیاده‌سازی شبیه‌سازی‌شده (پیش‌فرض تست)
```

این الگو بعداً در ماژول‌های Shipping و Notifications دوباره تکرار می‌شود (فایل ۸) — یک الگوی استاندارد برای «انتخاب بین چند پیاده‌سازی خارجی به‌وسیله‌ی نام».

نکته‌ی مهم فنی: وابستگی یک Connector فقط **یک‌بار** در زمان `boot()` تزریق می‌شود؛ اگر بخواهید در تست یک پیاده‌سازی جایگزین کنید، باید یک نمونه‌ی تازه با وابستگی جدید دوباره ثبت کنید — نمی‌شود فقط Interface را دوباره Bind کرد و انتظار داشت اثر بگذارد.

## جدول خلاصه‌ی موجودیت‌های Commerce (پایه)

| موجودیت | نقش |
|---|---|
| Product / Category | کاتالوگ محصول |
| Cart / CartItem | سبد خرید فعال (پیش‌نمایش قابل‌تغییر) |
| Inventory | موجودی دوفازی |
| Order / OrderItem | سفارش نهایی (رکورد غیرقابل‌تغییر) |
| Customer | مشتری |
| Payment / Coupon / Discount | پرداخت و تخفیف |

## چند تصمیم کسب‌وکاری کلیدی که باید بدانید

- `commerce.order.place` **هیچ‌وقت** مالیات یا تخفیف اعمال نمی‌کند — فقط `commerce.checkout.process` قیمت واقعی را محاسبه می‌کند. یعنی همین امروز دو راه برای ثبت سفارش با رفتار قیمتی متفاوت وجود دارد — یک بدهی فنی شناخته‌شده و مستندشده (فایل ۱۹).
- کد کوپن اشتباه، خطای ۴۰۹ (Conflict) برمی‌گرداند، نه ۴۰۴ — چون `InvalidCouponException` هم برای «کوپن اصلاً وجود ندارد» و هم برای «کوپن هست ولی الان قابل‌استفاده نیست» استفاده می‌شود.

Commerce پایه‌ی همه‌ی چیزهایی است که در فایل‌های بعدی می‌بینیم — از تجارت پیشرفته (فایل ۱۱) تا عامل‌های هوشمندی که در نهایت همین قابلیت‌های Commerce را صدا می‌زنند (فایل ۱۲ به بعد).
