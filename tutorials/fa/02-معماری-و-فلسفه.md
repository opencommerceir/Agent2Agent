# ۲. معماری کلی و فلسفه‌ی طراحی

در فایل قبل گفتیم که هدف پروژه چیست. حالا می‌خواهیم ببینیم این هدف چگونه به یک معماری واقعی تبدیل شده است.

## نمای کلی لایه‌ها

از بالا به پایین، یک درخواست از یک ایجنت هوش مصنوعی این مسیر را طی می‌کند:

```
AI Agents
   ↓
MCP Gateway            ← دروازه‌ی ورودی، احراز هویت، مجوز
   ↓
OpenCommerce Core       ← هویت / سازمان / مستأجر / مجوز
   ↓
Capability Registry     ← دفترچه‌ی قابلیت‌های قابل‌کشف
   ↓
Agent Registry          ← اطلاعات خود ایجنت‌ها
   ↓
Connection Manager      ← اتصال به سیستم‌های خارجی
   ↓
Domain Modules           ← Commerce، CRM، Finance، Shipping، ...
   ↓
External Business Systems  ← WooCommerce، درگاه پرداخت، ...
```

هر جعبه در این نمودار، یک مسئولیت مشخص دارد و **هیچ‌کدام کار جعبه‌ی دیگر را انجام نمی‌دهد.**

## اجزای اصلی پلتفرم

### ۱. OpenCommerce Core
پایه‌ی کل پلتفرم. مسئول:
- هویت و احراز هویت (Identity & Authentication)
- سازمان‌ها (Organizations)
- چندمستأجری (Multi-tenancy)
- مجوزها (Permissions)
- کلیدهای API
- پیکربندی
- اتصالات (Connections)
- گذرگاه رویداد (Event Bus)
- ثبت لاگ (Audit Logs)

### ۲. Agent Registry
اطلاعات ایجنت‌های هوش مصنوعی ثبت‌شده — هویت، مجوزها، پروتکل‌های پشتیبانی‌شده و اتصالات موجود آن‌ها.

### ۳. Capability Registry
لایه‌ی کشف پلتفرم. هر سیستم تجاری متصل، قابلیت‌های خودش را در قالبی استاندارد عرضه می‌کند — مثلاً «جست‌وجوی محصول»، «بررسی موجودی»، «ایجاد سفارش»، «دریافت اطلاعات مشتری»، «تولید گزارش»، «صدور فاکتور». ایجنت‌ها این قابلیت‌ها را **پویا** کشف می‌کنند، نه با یکپارچه‌سازی سخت‌کدشده.

### ۴. MCP Gateway
لایه‌ی ارتباطی بین ایجنت‌ها و OpenCommerce، بر پایه‌ی **Model Context Protocol (MCP)**. مسئولیت‌ها:
- احراز هویت
- مجوزدهی
- کشف قابلیت‌ها
- اجرای ابزار (Tool Execution)
- پاسخ‌های ساخت‌یافته

**نکته‌ی مهم: منطق کسب‌وکار هرگز داخل MCP Gateway پیاده نمی‌شود.** این دروازه فقط یک لایه‌ی ارتباطی است.

### ۵. Universal Commerce Protocol (UCP)
یک مدل تجاری نرمال‌شده. سیستم‌های تجاری مختلف (Shopify، WooCommerce، Magento، اپلیکیشن‌های Laravel، سیستم‌های سفارشی) به یک ساختار مشترک تبدیل می‌شوند تا ایجنت‌ها همیشه یک شکل ثابت ببینند — مستقل از این‌که داده از کجا آمده.

### ۶. SDK Platform
SDKهای رسمی برای این‌که توسعه‌دهنده‌ها راحت‌تر اپلیکیشن‌شان را Agent-Ready کنند.

### ۷. Connectors
اتصال‌دهنده‌ها به سیستم‌های تجاری خارجی — مثل اتصال واقعی به WooCommerce که در فایل‌های بعدی می‌بینیم.

## اهداف معماری

| هدف | توضیح |
|---|---|
| **Agent First** | ایجنت‌ها شهروند درجه‌یک پلتفرم‌اند؛ باید بتوانند کشف کنند، بفهمند، اجرا کنند و پاسخ ساخت‌یافته بگیرند. |
| **هسته مستقل از دامنه** | همان Core باید بتواند از Commerce تا CRM، ERP، HR، سلامت، لجستیک و تولید را پشتیبانی کند. |
| **توسعه‌پذیری** | دامنه، اتصال‌دهنده و قابلیت جدید بدون تغییر زیرساخت موجود اضافه می‌شود. |
| **آماده برای سازمان (Enterprise Ready)** | چندمستأجری، احراز هویت، مجوزدهی، امنیت، ثبت لاگ، مقیاس‌پذیری و یکپارچه‌سازی خارجی. |

## محدودیت‌های هسته (Core Restrictions)

این یکی از مهم‌ترین قوانین کل پروژه است: **هسته هرگز نباید منطق دامنه‌ی کسب‌وکار داشته باشد.**

هسته نباید چیزی درباره‌ی این‌ها بداند:
- محصولات
- سفارش‌ها
- مشتری‌ها
- موجودی
- پرداخت‌ها
- ارسال
- تخفیف‌ها
- قوانین بازاریابی

مثال درست در برابر غلط:

```
❌ غلط:   Core/ProductService.php
✅ درست:  Modules/Commerce/ProductService.php
```

اگر یک روز در حال نوشتن کدی داخل `app/Core/` بودید و دیدید که دارید از `App\Modules\...` استفاده می‌کنید، همان لحظه دست نگه دارید .

## معماری داخل هر ماژول: طراحی لایه‌ای

هر ماژول دامنه (مثل Commerce یا Shipping) از یک ساختار ثابت پیروی می‌کند، شبیه Clean Architecture:

```
Module/
├── Domain/            ← منطق خالص کسب‌وکار، بدون وابستگی به فریم‌ورک
│   ├── Entities/       موجودیت‌های اصلی (مثل Product، Order)
│   ├── ValueObjects/   اشیاء ارزشی (مثل Money، SKU)
│   ├── Events/         رویدادهای دامنه
│   ├── Repositories/   Interface های ذخیره‌سازی (نه پیاده‌سازی)
│   ├── Services/       سرویس‌های دامنه، خالص و بدون وابستگی
│   └── Exceptions/      خطاهای دامنه
├── Application/        ← هماهنگ‌کننده‌ی موارد استفاده
│   ├── Actions/         یک Action = یک عملیات مشخص کسب‌وکار
│   ├── DTOs/             اشیاء انتقال داده بین لایه‌ها
│   └── Services/         سرویس‌های اپلیکیشنی (مثل کلاینت HTTP خارجی)
├── Infrastructure/     ← پیاده‌سازی واقعی (Eloquent Models، Repository ها)
├── Interfaces/          ← لایه‌ی ورودی HTTP/MCP (کنترلرها)
└── Support/, Tests/
```

**قانون طلایی:** منطق کسب‌وکار هرگز داخل Controller یا Model قرار نمی‌گیرد؛ فقط داخل `Domain` و `Application`.

## اصول مهندسی که در همه‌جا تکرار می‌شوند

این ۵ اصل که در فایل قبل دیدیم، این‌جا معنای عملی پیدا می‌کنند:

1. **معماری بر سرعت** → مثال: وقتی در فاز ۵ درخواستی آمد که یک ستون موجودی جدا برای تنوع محصول بسازد، تیم به‌جای پیاده‌سازی سریع، معماری موجودی دوفازی را گسترش داد (فایل ۱۱).
2. **قابلیت نگهداری بر میان‌بر** → استفاده‌ی مکرر از الگوی «Action ترکیب‌شده از Action دیگر» به‌جای کپی منطق.
3. **صراحت بر جادو** → مثلاً محدودیت نرخ درخواست (Rate Limiting) به‌صورت یک فراخوانی صریح Action پیاده شده، نه Middleware مخفی.
4. **رابط بر وابستگی سفت** → همه‌ی ماژول‌ها فقط با Interface به هم وصل می‌شوند، هرگز با کلاس مشخص یک ماژول دیگر.
5. **مستندسازی قبل از پیچیدگی** → هر فاز و هر تصمیم بزرگ در `HANDOFF.md` (و حالا در همین آموزش) ثبت شده.

## استراتژی چندمستأجری (Multi-Tenancy)

پلتفرم باید از یک SaaS واقعی پشتیبانی کند:

- **فاز ۱ (فعلی):** پایگاه‌داده‌ی مشترک با جداسازی بر اساس ستون `tenant_id` — همه‌ی جدول‌های مربوط به یک مستأجر (Tenant)، این ستون را دارند.
- **فاز ۲ (آینده):** پایگاه‌داده‌ی جداگانه برای هر مستأجر.

هیچ تصمیمی نباید مسیر مهاجرت به فاز ۲ را مسدود کند — این یک قانون طراحی دائمی است.

## چرخه‌ی توسعه (Development Workflow)

هیچ‌وقت مستقیم به سراغ پیاده‌سازی نمی‌رویم. ترتیب همیشگی:

1. **درک (Understand):** مسئله، نیازمندی، معماری موجود، وابستگی‌ها را تحلیل کن.
2. **طراحی (Design):** معماری، مسئولیت‌ها، جریان داده، اثر روی پایگاه‌داده و تبادل‌ها (Trade-offs) را توضیح بده.
3. **تأیید (Approval):** قبل از پیاده‌سازی بزرگ، منتظر تأیید بمان.
4. **پیاده‌سازی (Implement):** کد تمیز طبق استانداردها بنویس.
5. **بازبینی (Review):** انطباق معماری، امنیت، تست‌ها و مستندات را بررسی کن.

در فایل‌های بعدی (به‌خصوص ۶ تا ۱۶) بارها می‌بینیم که تیم توسعه، قبل از پیاده‌سازی هر فاز، ابتدا کد و مستندات موجود را با درخواست تطبیق داده و اگر ناسازگاری یا خطر معماری دیده، **متوقف شده و سؤال پرسیده** — این دقیقاً همان قدم ۱ و ۲ در عمل است.

## جمع‌بندی این فایل

- پلتفرم از بالا به پایین لایه‌بندی شده: ایجنت → MCP Gateway → Core → Capability Registry → ماژول‌های دامنه → سیستم‌های خارجی.
- Core همیشه مستقل از دامنه باقی می‌ماند.
- هر ماژول از یک ساختار لایه‌ای ثابت (Domain/Application/Infrastructure/Interfaces) پیروی می‌کند.
- پنج اصل مهندسی (معماری، نگهداری، صراحت، رابط، مستندسازی) پشت هر تصمیم قرار دارند.

در فایل بعدی، این معماری را به یک نقشه‌ی واقعیِ پوشه‌ها و پشته‌ی فناوری تبدیل می‌کنیم.
