# ۱۳. فاز ۶ (مراحل ۲ و ۳) — پروفایل عامل‌ها و برنامه‌ریز مبتنی بر LLM

## مرحله ۲ — پروفایل عامل‌ها و عامل CEO

### مشکل نسخه‌ی قبلی

در مرحله‌ی قبل، `DeterministicPlanner` قوانین هر پرسونا (فروش، پشتیبانی، مالی) را مستقیم در کد PHP سخت‌کد کرده بود — یعنی اضافه‌کردن یک پرسونای جدید یعنی تغییر کد Planner. این مرحله این را حل می‌کند: هر پرسونا الان یک **فایل پیکربندی** است.

```
config/agents/ceo.php
config/agents/sales.php
config/agents/support.php
config/agents/finance.php
```

هر فایل شامل:
- `planning_rules` — لیستی از قوانین؛ هر قانون یک کلیدواژه و یک دنباله از قابلیت‌هاست.
- `default_inputs` — مقادیر پیش‌فرض ورودی هر قابلیت (با توکن‌های خاص، مثل `{date:-7}` یا `{coupon_code}`).
- `permissions` — لیست **توصیفی** (نه اجرایی) از مجوزهایی که این پرسونا معمولاً نیاز دارد.

`AgentProfile` (موجودیت جدید Domain) این آرایه را می‌خواند و `DeterministicPlanner` به‌جای شاخه‌های سخت‌کد، از `planning_rules` همان پروفایل استفاده می‌کند.

### نکته‌ی خیلی مهم: `permissions` فقط توصیفی است

این یک تصمیم صریح است که باید همیشه به یاد داشت: لیست `permissions` داخل یک پروفایل، **هیچ نقش اجرایی ندارد** — فقط مستندسازی است. مجوزدهی واقعی همیشه در جای همیشگی‌اش اتفاق می‌افتد: داخل `CapabilityToolInvoker`، دقیقاً همان‌جا که هر قابلیت دیگری در کل پلتفرم بررسی می‌شود. این نکته در فایل بعدی (همکاری چندعامله) اهمیت حیاتی پیدا می‌کند.

### دو اصلاح واقعی روی مثال پیکربندی خود درخواست

1. `'start_date' => '-7 days'` یک رشته‌ی تاریخ نسبی معتبر PHP بود، ولی شکلی که `report.sales.generate` واقعاً انتظار دارد (`Y-m-d`) نبود. جایگزین شد با توکن صریح `{date:N}` که `DeterministicPlanner` آن را به یک تاریخ واقعی تبدیل می‌کند.
2. `'code' => 'AUTO_{date}'` هیچ‌وقت نمی‌توانست یک `CouponCode` معتبر (که باید با `COUPON-` شروع شود) تولید کند — با هر اجرا خطا می‌داد. جایگزین شد با توکن `{coupon_code}` که یک کد واقعاً معتبر می‌سازد.

### یک باگ نهفته‌ی دیگر: `glob()` در برابر `config()`

متن درخواست برای فهرست‌کردن همه‌ی پروفایل‌ها از `glob()` (خواندن مستقیم فایل‌های موجود روی دیسک) استفاده کرده بود. این در محیط توسعه کار می‌کند، ولی در هر Deploy واقعی که از `php artisan config:cache` استفاده کند (استاندارد رایج Laravel)، به‌آرامی از کار می‌افتد — چون پیکربندی کش‌شده دیگر مسیر فایل اصلی را ندارد. این مشکل قبل از انتشار شناسایی و اصلاح شد: به‌جای `glob()`، از `config('agents', [])` استفاده می‌شود که با کش پیکربندی هم سازگار است.

## مرحله ۳ — برنامه‌ریز مبتنی بر LLM

### `LLMPlanner` — دومین پیاده‌سازی واقعی `PlannerInterface`

این‌جا اولین باری است که یک مدل زبانی بزرگ واقعاً وارد پروژه می‌شود. معماری آن دقیقاً همان الگوی Connector است که چندبار دیده‌ایم:

```
LLMClientInterface     ← قرارداد
OpenAIClient            ← پیاده‌سازی واقعی (Guzzle)
ClaudeClient             ← پیاده‌سازی واقعی (Guzzle)
```

### مکانیزم بازگشت خودکار (Fallback) — یک قانون امنیتی حیاتی

`LLMPlanner::createPlan()` کل زنجیره‌ی «کشف قابلیت‌ها → ساخت پرامپت → صدازدن LLM → تجزیه‌ی پاسخ → ساخت برنامه» را در یک `try/catch` می‌پیچد. هر شکستی — قطعی شبکه، پاسخ نامعتبر، فیلد گم‌شده — یک مسیر یکسان دارد: یک هشدار لاگ می‌شود و `DeterministicPlanner` (که از قبل تزریق شده) به‌جای آن برنامه می‌سازد. این یعنی روشن‌کردن LLM هرگز کاربر نهایی را با یک شکست کامل مواجه نمی‌کند.

### تصمیم پیش‌فرض بسیار مهم: `PLANNER_TYPE=deterministic`

خود متن درخواست، `.env.example` را با `PLANNER_TYPE=llm` پیش‌فرض کرده بود. این عمداً **رد شد**. چرا؟ چون این یعنی یک نصب تازه، بدون هیچ کلید API، در همان اولین تماس با `/api/agents/*` سعی می‌کند یک درخواست شبکه‌ی واقعی و بدون کلید بزند — رفتاری غیرقابل‌پیش‌بینی (ممکن است سریع رد شود یا هنگ کند، بسته به شبکه). این دقیقاً همان الگوی «پیش‌فرض امن برای توسعه/تست، زیرساخت واقعی فقط با انتخاب صریح» است که در `WOOCOMMERCE_*` و `CACHE_STORE=database` هم دیده‌ایم. `phpunit.xml` هم صراحتاً `PLANNER_TYPE=deterministic` را ست می‌کند تا کل مجموعه‌ی تست هرگز حتی یک تماس واقعی با اینترنت نزند.

### یک تفاوت واقعی بین دو ارائه‌دهنده

OpenAI و Claude، هردو خروجی ساخت‌یافته (Structured Output) می‌دهند، ولی به‌شکل متفاوت: OpenAI با `response_format: json_object` (فقط تضمین می‌کند JSON معتبر باشد، نه لزوماً مطابق schema) و Claude با مکانیزم Tool Use خودش (که واقعاً schema را در سطح API اعتبارسنجی می‌کند). این یک تفاوت واقعی قابلیت بین دو ارائه‌دهنده است که در کد رعایت شده، نه یک فرض ساده‌انگارانه که «هردو یکسان رفتار می‌کنند».

### آزمایش بدون تماس واقعی شبکه

هیچ تستی در این کدبیس، حتی یک تماس واقعی با OpenAI/Claude نمی‌زند (چون اعتبارنامه‌ی واقعی در این محیط توسعه وجود ندارد) — یا از یک `LLMClientInterface` جعلی استفاده می‌شود، یا از یک کلاینت واقعی Guzzle که پشت `MockHandler` قرار گرفته (یعنی کد واقعی HTTP تست می‌شود، فقط پاسخ شبیه‌سازی است).

## جدول خلاصه

| مرحله | چه چیزی اضافه شد | تصمیم کلیدی |
|---|---|---|
| پروفایل عامل‌ها | `config/agents/*.php`، `AgentProfile` | `permissions` فقط توصیفی است؛ اجرا همیشه جدا بررسی می‌شود |
| LLM Planner | `LLMPlanner`، `OpenAIClient`، `ClaudeClient` | پیش‌فرض `deterministic`؛ بازگشت خودکار در هر شکست |

با پایان این دو مرحله: ۹۶۶ تست، ۱۱۸ قابلیت MCP. حالا وقت آن است که ببینیم چطور این عامل‌ها می‌توانند **از اجراهای قبلی یاد بگیرند** و **با هم همکاری کنند**.
