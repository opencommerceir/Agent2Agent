# ۲۰. راه‌های اتصال و استفاده‌ی دیگران از این پروژه

در تمام فایل‌های قبلی، معماری، ماژول‌ها و لایه‌ی هوش مصنوعی این پلتفرم را از داخل دیدیم. این فایل یک سؤال کاملاً متفاوت را جواب می‌دهد: **یک نفر بیرون از این تیم — یک کسب‌وکار، یک توسعه‌دهنده، یک آژانس — چطور می‌تواند از این پروژه استفاده کند، و اصلاً چه سودی برایش دارد؟**

جواب کوتاه: **دو مسیر کاملاً متفاوت** وجود دارد، و هیچ‌کدام به دیگری وابسته نیست.

## دو مسیر اصلی استفاده

### مسیر الف — دانلود، نصب و میزبانی شخصی (متن‌باز / Self-Hosted)

این پروژه با مجوز **MIT** (طبق `composer.json`) متن‌باز است — یعنی هرکسی می‌تواند کد را بگیرد، آن را روی سرور خودش نصب کند، تغییرش دهد و حتی برای مقاصد تجاری استفاده کند.

مراحل عملی همان چیزی است که در فایل ۱۸ کامل توضیح دادیم: کلون کردن مخزن، نصب وابستگی‌ها، مهاجرت پایگاه‌داده، و بالا آوردن سرور — روی زیرساخت خودشان، نه زیرساخت ما.

نکته‌ی مهم‌تر از خودِ نصب این است: چون طبق فلسفه‌ی «Infrastructure First, Domains Second» (فایل ۲) هسته‌ی این پلتفرم کاملاً مستقل از تجارت الکترونیک ساخته شده، کسی که این مسیر را انتخاب می‌کند فقط یک فروشگاه دانلود نمی‌کند — یک **زیرساخت کامل Agent-Ready** با یک هسته‌ی هویت/چندمستأجری/مجوز/دروازه‌ی MCP آماده به‌دست می‌آورد که می‌تواند رویش هرچیزی بسازد.

**چه کارهایی دقیقاً با این مسیر ممکن است؟**

1. **استفاده‌ی مستقیم برای کسب‌وکار خودشان** — همین ۱۰ ماژول موجود (Commerce، CRM، Finance، Shipping، ...) را با داده‌ی واقعی خودشان اجرا کنند و فروشگاه/کسب‌وکارشان همین امروز Agent-Ready شود، با کنترل کامل روی داده و برندسازی.
2. **ساخت یک دامنه‌ی کاملاً جدید روی همین هسته** — این دقیقاً همان چیزی است که هسته برایش طراحی شده (فایل ۲: «Core باید بتواند از Commerce تا سلامت، HR، املاک را پشتیبانی کند»). یک تیم می‌تواند این مخزن را Fork کند و به‌جای تجارت، یک دامنه‌ی کاملاً متفاوت (مثلاً نوبت‌دهی پزشکی، مدیریت املاک، منابع انسانی) بسازد — با همان الگوی هفت‌مرحله‌ای ماژول (فایل ۳)، بدون نیاز به تغییر هسته یا دروازه‌ی MCP.
3. **میزبانی برای چند مشتری (White-Label SaaS)** — چون چندمستأجری از روز اول در هسته وجود دارد (فایل ۴)، یک آژانس یا شرکت توسعه می‌تواند یک نمونه اجرا کند و آن را به چند کسب‌وکار مختلف، هرکدام به‌عنوان یک Tenant جدا، بفروشد یا اجاره دهد.
4. **جایگزینی یا افزودن اتصال‌دهنده‌های خودشان** — الگوی Connector (فایل ۶ و ۸) از قبل برای WooCommerce و یک درگاه ارسال ساخته شده؛ هرکسی می‌تواند به همان الگو یک اتصال‌دهنده‌ی جدید (مثلاً Shopify، یک درگاه پرداخت محلی) اضافه کند، بدون دست‌زدن به بقیه‌ی سیستم.
5. **حاکمیت کامل داده** — برای کسب‌وکارهایی که به هر دلیلی (مقرراتی، حساسیت داده، سیاست داخلی) نمی‌خواهند داده‌شان از زیرساخت خودشان خارج شود، این تنها مسیر ممکن است — چون هیچ داده‌ای هرگز به سمت ما نمی‌رود.

آنچه لازم دارند: دانش PHP/Laravel (یا استخدام کسی که دارد)، یک سرور، و دنبال‌کردن فایل ۱۸. **هیچ وابستگی‌ای به زیرساخت میزبانی‌شده‌ی OpenCommerce در این مسیر وجود ندارد.**

### مسیر ب — اتصال به زیرساخت میزبانی‌شده‌ی خود OpenCommerce (OpenCommerce.ir)

به‌جای نصب و نگهداری چیزی، در این مسیر فقط به‌عنوان یک **مصرف‌کننده (Client)** به یک نمونه‌ی از قبل در حال اجرا از این پلتفرم — روی زیرساخت OpenCommerce، در آدرس **OpenCommerce.ir** — وصل می‌شوند.

جریان کار دقیقاً همان چیزی است که در فایل‌های ۴ و ۵ دیدیم:

1. برایشان یک هویت روی پلتفرم (یک Tenant/Organization + یک Agent) ساخته می‌شود.
2. یک توکن Bearer (`AgentToken`) و مجوزهای مشخص (Role/Permission روی همان قابلیت‌هایی که نیاز دارند) دریافت می‌کنند.
3. از همان لحظه، بدون نصب هیچ چیزی روی سیستم خودشان، می‌توانند مستقیم با درخواست‌های HTTP+JSON به دروازه‌ی MCP وصل شوند و از ۱۲۴ قابلیت موجود روی ۱۰ ماژول استفاده کنند.

این مسیر برای کسی مناسب است که **نمی‌خواهد** درگیر نصب، به‌روزرسانی، امنیت سرور، پشتیبان‌گیری و نگهداری زیرساخت شود — فقط می‌خواهد سریع، از همان امروز، به یک بک‌اند کسب‌وکاری واقعی و Agent-Ready وصل شود.

**آیا SDK لازم است؟** نه — چون دروازه‌ی MCP چیزی بیشتر از یک API استاندارد HTTP+JSON نیست (فایل ۵)، هر زبانی (PHP، Python، Go، Node، هرچی) می‌تواند مستقیم وصل شود. فعلاً فقط یک SDK رسمی برای PHP ساخته شده (`packages/opencommerce-sdk`)؛ نسخه‌های زبان‌های دیگر در نقشه‌ی راه هستند، ولی نبودشان مانع اتصال نیست — پروتکل، نه SDK، چیزی است که این ارتباط را ممکن می‌کند.

## جدول مقایسه‌ی دو مسیر

| | مسیر الف: میزبانی شخصی | مسیر ب: اتصال به زیرساخت میزبانی‌شده |
|---|---|---|
| نیاز به نصب/سرور | بله | خیر |
| کنترل کامل کد و داده | بله، صددرصد | خیر — داده روی زیرساخت OpenCommerce می‌ماند |
| امکان افزودن دامنه‌ی کاملاً جدید (نه تجارت) | بله، فقط اینجا ممکن است | خیر — فقط مصرف‌کننده‌ی API موجود هستند |
| سرعت شروع | نیاز به نصب و پیکربندی (فایل ۱۸) | تقریباً فوری، فقط با دریافت یک توکن |
| مسئولیت نگهداری/به‌روزرسانی | بر عهده‌ی خودشان | بر عهده‌ی تیم OpenCommerce |
| مناسب‌ترین کاربر | کسب‌وکار/آژانسی که کنترل کامل یا دامنه‌ی جدید می‌خواهد | تیمی که فقط می‌خواهد سریع به یک بک‌اند Agent-Ready وصل شود |

## چه کسانی، دقیقاً چه استفاده‌ای می‌کنند؟ (مثال‌های واقعی)

| کاربر | نیاز واقعی | مسیر مناسب |
|---|---|---|
| یک فروشگاه که می‌خواهد Agent-Ready شود ولی نمی‌خواهد سرور مدیریت کند | یک بک‌اند آماده، سریع | مسیر ب |
| یک فروشگاه بزرگ با نیاز به برندسازی و کنترل کامل داده | مالکیت کامل زیرساخت | مسیر الف |
| یک آژانس توسعه که می‌خواهد این را به چند مشتری بفروشد | چندمستأجری + کنترل کامل | مسیر الف (با استفاده از چندمستأجری موجود) |
| توسعه‌دهنده‌ای که با Python/Go یک ایجنت هوش مصنوعی می‌سازد و نیاز به یک بک‌اند واقعی کسب‌وکار دارد | اتصال سریع، بدون نصب چیزی | مسیر ب — از طریق MCP مستقیم یا لایه‌ی هدف‌محور Agent Orchestrator |
| مشارکت‌کننده‌ی متن‌باز که می‌خواهد دامنه‌ی کاملاً جدیدی (سلامت، املاک، HR) روی همین هسته بسازد | دسترسی کامل به کد و امکان افزودن ماژول | فقط مسیر الف ممکن است |
| سازمانی با نیاز حاکمیت داده (دولتی، بانکی، پزشکی) | داده هرگز از زیرساخت خودشان خارج نشود | فقط مسیر الف |
| کسی که فقط می‌خواهد پروژه را یاد بگیرد یا در توسعه‌اش مشارکت کند | کلون کردن و اجرای محلی، بدون نیاز به Deploy واقعی | مسیر الف (دقیقاً همان چیزی که فایل ۱۸ توضیح می‌دهد) |

## یادآوری مهم: پروتکل در هر دو مسیر یکسان است

نکته‌ای که نباید فراموش شود: چه کسی خودش این پلتفرم را نصب کند (مسیر الف) و چه به نمونه‌ی میزبانی‌شده وصل شود (مسیر ب)، **نحوه‌ی تعامل با آن دقیقاً یکسان است** — چون هردو از همان دروازه‌ی MCP استاندارد (فایل ۵) عبور می‌کنند. این دقیقاً همان چیزی است که استانداردسازی پروتکل به‌جای یک API اختصاصی به ما می‌دهد: یک کد نوشته‌شده برای اتصال به یک نمونه‌ی خودمیزبانی، با تغییر فقط یک آدرس (`baseUrl`) و یک توکن، بدون هیچ تغییر دیگری روی همان زیرساخت میزبانی‌شده هم کار می‌کند — و برعکس.

دو سطح تعامل هم، مستقل از این‌که کدام مسیر انتخاب شده، همیشه در دسترس‌اند:

- **سطح ۱ — تماس مستقیم با قابلیت‌ها**: برای اتوماسیون قطعی و برنامه‌ریزی‌شده (مثلاً «این محصول را جست‌وجو کن»، «این سفارش را ثبت کن») — از طریق دروازه‌ی MCP (فایل ۵).
- **سطح ۲ — هدف‌محور از طریق عامل هوشمند**: برای وقتی خودِ برنامه‌ی مشتری یک ایجنت هوش مصنوعی است و فقط می‌خواهد یک هدف متنی بدهد و بگذارد موتور Planner/Executor/Reasoning پلتفرم (فایل ۱۲ تا ۱۵) تصمیم بگیرد چه قابلیت‌هایی را چطور اجرا کند.

## جمع‌بندی یک‌خطی

این پروژه هم‌زمان هم یک **محصول متن‌باز قابل‌نصب** است و هم یک **زیرساخت قابل‌اتصال** — و این انتخاب دوگانه، مستقیماً نتیجه‌ی همان تصمیم معماری بنیادین فایل ۲ است: هسته‌ای که کاملاً مستقل از دامنه ساخته شده، به همان اندازه که برای Fork-کردن و ساختن چیزی تازه مناسب است، برای اجرا و مصرف‌شدن به‌عنوان یک سرویس آماده هم مناسب است.
