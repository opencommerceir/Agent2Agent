# ۴. هسته Core — هویت، چندمستأجری، مجوز

هسته (`app/Core/`) از فاز ۱ ساخته شد و تا امروز **همچنان مستقل از هر دامنه‌ی کسب‌وکار باقی مانده** — هیچ‌کدام از کدهایش چیزی از `App\Modules\*` وارد نمی‌کند. این فایل، اجزای اصلی آن را معرفی می‌کند.

## مدل هویت (Identity Model)

چند مفهوم کلیدی که باید همیشه از هم تفکیک شوند:

### Tenant (مستأجر)
یک کسب‌وکار مستقل روی پلتفرم. جداسازی داده در سطح `tenant_id` انجام می‌شود. `Tenant` یکی از دو موجودیتی است که **بالاتر از سطح مستأجری** قرار دارد (یعنی خودش tenant_id ندارد) — دیگری `User` است (فایل ۹).

### Organization و OrganizationMember
مدل سازمان **درون** یک Tenant؛ برای آینده — زمانی که کارمندان یک کسب‌وکار بخواهند مستقیم وارد سیستم شوند (این هنوز پیاده‌سازی نشده، فقط مدل‌سازی شده).

### Agent (عامل)
هویت یک **ایجنت هوش مصنوعی** — نه یک انسان. هر Agent یک `AgentToken` (توکن Bearer) دارد که با آن به MCP وصل می‌شود. `Agent.type` یک enum مجزا است (`shopping`/`analytics`/`customer_service`/`custom`) — **این با `AgentType` ماژول Agent Orchestrator (`ceo`/`sales`/`support`/`finance`) کاملاً متفاوت است** و نباید با هم اشتباه گرفته شوند (این نکته در فایل ۱۴ اهمیت حیاتی پیدا می‌کند).

### User
هویت انسانی سطح پلتفرم — برای ورود به **پنل مدیریت (Admin Dashboard)**. برخلاف `Agent`، این یک کاربر انسانی با رمز عبور واقعی است. `User` نیز بدون `tenant_id` است، چون یک اپراتور پلتفرم باید بتواند همه‌ی مستأجرها را مدیریت کند (جزئیات کامل در فایل ۹).

## سیستم مجوز (Permission System)

یک مدل RBAC ساده و مؤثر:

```
Permission  → یک اجازه‌ی مشخص، مثل commerce.products.read
Role        → مجموعه‌ای از Permission ها
MemberRole  → اتصال یک عضو (مثلاً یک Agent) به یک Role
```

**نکته‌ی حیاتی:** این سیستم مجوز **فقط برای بررسی قابلیت‌های MCP توسط Agent هاست.** سیستم احراز هویت پنل مدیریت (`User`/`UserRole`) کاملاً جدا و مستقل است — دو تا session، دو تا مکانیزم، هرگز با هم ترکیب نمی‌شوند.

## رجیستری قابلیت (Capability Registry)

هر «قابلیت» (Capability) یک نام سه‌بخشی استاندارد دارد:

```
domain.resource.action
```

مثال: `commerce.product.search`، `crm.ticket.create`، `agent.goal.execute`

این محدودیت «دقیقاً سه بخش» یک قانون **سخت‌گیرانه** در کل پروژه است (`CapabilityName`/`PermissionKey` این را اجرا می‌کنند) — در فایل ۱۷ می‌بینیم که این محدودیت چندبار باعث تغییر نام قابلیت‌ها شده است.

## اجرای قابلیت (Capability Execution)

قلب تپنده‌ی هسته این دو کلاس هستند:

- `CapabilityHandlerRegistry` — هر ماژول، یک تابع (Handler) برای هر قابلیت خودش ثبت می‌کند.
- `CapabilityExecutionService` — قابلیت مورد نظر را پیدا می‌کند و همان تابع را با ورودی و `AuthContext` صدا می‌زند.

امضای یک Handler:

```php
callable(array $input, AuthContext $context): array
```

### AuthContext — مرز مقدس MCP

`AuthContext` یک شیء ساده است که شامل: `tenantId`، `agentId` و (از فاز i18n) `language`.

**قانون بسیار مهم:** `AuthContext` فقط در همین لایه (مرز MCP) وجود دارد. هیچ‌وقت به عمق Domain یا Application یک ماژول پاس داده نمی‌شود — آن‌جا فقط اسکالر‌های ساده مثل `int $tenantId` می‌بینند. این الگو (الگوی شماره ۱ در فایل ۱۷) یکی از مهم‌ترین قوانین معماری کل کدبیس است.

استثنای معدود و مستند این قانون: در ماژول Agent Orchestrator، چون آن ماژول باید دوباره وارد همان مرز MCP شود (یک قابلیت دیگر را صدا بزند)، چند Interface خاص واقعاً `AuthContext` می‌گیرند — این استثنا با دقت مستند شده (فایل ۱۲).

## Marker Interface ها — یک ترفند هوشمندانه

چطور هسته می‌تواند بدون شناختن یک Exception خاص از یک ماژول، آن را به کد HTTP درست (مثلاً ۴۰۴ یا ۴۰۹) تبدیل کند؟

جواب: دو Interface نشانه‌گذار در هسته تعریف شده:

```php
NotFoundExceptionInterface    → به HTTP 404 نگاشت می‌شود
ConflictExceptionInterface    → به HTTP 409 نگاشت می‌شود
```

هر ماژولی هر Exception که منطقاً «چیزی پیدا نشد» یا «تعارض داده» است را با یکی از این دو Interface پیاده‌سازی می‌کند. `MCPExceptionHandler` (هسته) فقط به این Interface ها نگاه می‌کند — نه به کلاس واقعی. این یعنی ماژول‌های جدید می‌توانند بدون تغییر هسته، Exception جدید اضافه کنند.

## دروازه‌ی MCP (نمای اول)

مسیرهای اصلی:
```
POST /mcp/v1/execute          POST /mcp/v2/execute
GET  /mcp/v1/capabilities      GET  /mcp/v2/capabilities
```

جزئیات کامل این بخش و پاسخ‌های JSON در فایل بعدی (۵) می‌آید.

## چندزبانگی در هسته (i18n)

از فاز ۴ به بعد، هسته یک زیرسیستم ترجمه‌ی کوچک و سفارشی دارد (نه ترجمه‌ی داخلی Laravel، چون شکل فایل‌های `lang/{code}/{group}.json` با آن سازگار نبود):

- `Language` (enum `en`/`fa`)
- `TranslationServiceInterface` / `JsonTranslationLoader`
- `LanguageDetector` — اولویت تشخیص زبان: پارامتر `?lang=` در URL → هدر `Accept-Language` → زبان پیش‌فرض Tenant → انگلیسی

جزئیات کامل در فایل ۹.

## احراز هویت پنل مدیریت (Human Auth)

از فاز ۴، مکانیزم لاگین انسانی هم به هسته اضافه شد: `User` واقعی با رمز هش‌شده (`password_hash`/`password_verify` خالص PHP، نه Facade لاراول — چون هر کلاس Domain باید بدون فریم‌ورک قابل تست باشد)، پشت یک Guard واقعی Laravel Session. جزئیات کامل در فایل ۹.

## جدول خلاصه‌ی مسئولیت‌های Core

| زیرسیستم | چه کاری می‌کند |
|---|---|
| Tenant | مدیریت مستأجرها |
| Organization/OrganizationMember | مدل سازمانی درون یک مستأجر (آماده برای آینده) |
| Agent Registry | ثبت و توکن‌دهی به عامل‌های هوش مصنوعی |
| Permission System | مجوزدهی سطح قابلیت برای Agent ها |
| Capability Registry | ثبت و کشف قابلیت‌ها |
| Capability Execution | اجرای واقعی یک قابلیت |
| MCP Gateway | دروازه‌ی ورودی برای همه‌ی درخواست‌های ایجنت |
| i18n | تشخیص و ترجمه‌ی زبان |
| Human Auth | لاگین انسانی پنل مدیریت |

در فایل بعدی، عمیق‌تر به داخل دروازه‌ی MCP می‌رویم و می‌بینیم یک درخواست واقعی از احراز هویت تا اجرا چه مسیری طی می‌کند.
