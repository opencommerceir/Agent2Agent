# ۱۵. فاز ۶ (مرحله ۶، آخر) و OpenRouter — بازتاب خود، استدلال و اتصال مدل‌های رایگان

## مرحله ۶ — بازتاب خود و استدلال (Self-Reflection & Reasoning)

این آخرین مرحله‌ی فاز ۶ است. از این پس، هر فراخوانی `agent.goal.execute` این جریان را دارد:

```
think()   ← قبل از ساخت برنامه: «چرا این کار را می‌کنم؟ چقدر مطمئنم؟»
   ↓
[ساخت و اجرای برنامه، بدون تغییر]
   ↓
reflect() ← بعد از اجرا: «نتیجه چطور بود؟ چقدر به هدف رسیدم؟»
```

هر دو مرحله یک `ReasoningTrace` تولید می‌کنند — شامل: چند جمله‌ی کوتاه توضیحی (`thoughts`)، حداکثر ۳ گزینه‌ی جایگزین (فقط پیش از اجرا)، یک امتیاز اطمینان بین ۰ تا ۱ (`ConfidenceScore`) و یک توضیح انسانی‌خوان.

## بزرگ‌ترین اصل این مرحله: استدلال فقط توضیح می‌دهد، هرگز برنامه را عوض نمی‌کند

این شاید مهم‌ترین جمله‌ی کل فاز ۶ باشد: **نه `PlannerInterface` و نه `PlanExecutorInterface` هیچ‌کدام چیزی از یک `ReasoningTrace` نمی‌خوانند.** دنباله‌ی قابلیت‌هایی که واقعاً اجرا می‌شوند، دقیقاً همان‌طور تعیین می‌شود که همیشه بوده (اول یک الگوی یادگرفته‌شده، بعد هر Planner ای که پیکربندی شده). این یک تصمیم آگاهانه است، دقیقاً همان محدودیت که در همکاری چندعامله دیدیم (تفویض، برنامه را دور نمی‌زند) — اینجا یک سطح دیگر تکرار شده: **بازتاب هم، برنامه را دور نمی‌زند.**

## دو پیاده‌سازی، دقیقاً مثل الگوی Planner

```
SimpleReasoningEngine    ← بدون تماس LLM. اطمینان را از تاریخچه‌ی واقعی الگوهای اجرا محاسبه می‌کند
LLMReasoningEngine        ← از یک ارائه‌دهنده‌ی LLM می‌خواهد JSON ساخت‌یافته بسازد؛ در هر شکست، خودکار
                             به SimpleReasoningEngine برمی‌گردد
```

## تصمیم فنی حیاتی: چرا `reasoning.type` هم پیش‌فرض `simple` است

`LLMClientInterface` **بدون قید و شرط** در سازنده‌ی ماژول Bind شده — مستقل از این‌که کدام Planner پیکربندی شده. اگر پیش‌فرض استدلال روی `llm` می‌بود، دیگر فقط یک مسیر اختیاری (کسی که Planner مبتنی بر LLM را انتخاب کرده) ریسک تماس شبکه‌ی واقعی می‌داشت — بلکه **هر تک فراخوانی** `agent.goal.execute` در کل پلتفرم، همان لحظه که این مرحله سیم‌کشی می‌شد، سعی می‌کرد یک تماس واقعی و بدون کلید بزند. برای همین `reasoning.type` هم دقیقاً همان پیش‌فرض امن `planner.type` را گرفت: `simple`. این با اجرای کامل مجموعه‌ی ۱۰۳۱ تستی قبلی (بدون هیچ تغییر) تأیید شد — صفر Regression، صفر تماس جدید شبکه.

## سه اصلاح واقعی دیگر نسبت به متن درخواست

1. متن درخواست، وابستگی‌هایی برای `ExecuteGoalAction` (مثل `ExecutionMemoryService`) نوشته بود که **اصلاً وجود نداشتند** — به‌جای بازنویسی کل سازنده، فقط ۳ وابستگی واقعاً جدید (`ReasoningEngineInterface`، `ReasoningTraceRepositoryInterface`، `ExplanationGeneratorInterface`) به لیست موجود اضافه شد.
2. `ExecutionResult` (موجودیت Domain) هیچ شناسه‌ای ندارد — شناسه‌ی واقعی فقط بعد از ذخیره‌شدن ساخته می‌شود. راه‌حل: یک `ReasoningTrace` پیش‌از-اجرا در حافظه نگه داشته می‌شود تا شناسه‌ی واقعی اجرا مشخص شود، سپس یک متغیر یک‌بارمصرف (`assignExecutionId()`) آن را قفل می‌کند — دقیقاً همان الگویی که `AgentMessage`/`DelegationRequest` (فایل قبل) قبلاً برای شناسه‌ی خودشان استفاده کرده بودند.
3. متن درخواست، متدی به نام `getSimilarExecutions()` روی `LearningServiceInterface` فرض کرده بود که وجود نداشت — معادل واقعی آن (`ExecutionPatternRepositoryInterface::findSimilarPatterns()`) از قبل وجود داشت و همان مستقیماً استفاده شد.

## دو قابلیت جدید

```
agent.reasoning.trace     ← بازیابی دو ردیابی (پیش/پس از اجرا) یک اجرای گذشته
agent.reasoning.explain    ← تبدیل همان ردیابی به یک توضیح انسانی‌خوان
```

با پایان این مرحله: **۱۰۶۷ تست، ۱۲۴ قابلیت — و فاز ۶ (هوش مصنوعی عامل‌محور) به‌طور کامل تمام شده، هر ۶ مرحله.**

## اتصال OpenRouter — بعد از پایان فاز ۶

این بخش دیگر یک «مرحله‌ی فاز» رسمی نیست، بلکه یک آماده‌سازی کوچک و مستقل برای دموی زنده است — دقیقاً مثل اسپرینت بدهی فنی که بین دو مرحله‌ی فاز ۴ آمد.

### چرا OpenRouter؟

`LLMClientInterface` تا این‌جا فقط دو پیاده‌سازی داشت (OpenAI و Claude) که هر دو نیاز به کلید API واقعی و پولی دارند. **OpenRouter** یک API واحد جلوی بیش از ۱۰۰ مدل از ارائه‌دهنده‌های مختلف می‌گذارد — و چندتای آن‌ها **کاملاً رایگان** هستند. این یعنی می‌شود بدون هیچ هزینه‌ای، واقعاً از یک LLM واقعی در دمو استفاده کرد.

پیاده‌سازی سوم اضافه شد: `OpenRouterClient` — از نظر ساختار تقریباً عین `OpenAIClient` است (چون Endpoint چت OpenRouter با استاندارد OpenAI سازگار است)؛ تفاوت واقعی فقط یک `$baseUrl` قابل‌تنظیم و دو هدر توصیه‌شده (`HTTP-Referer`/`X-Title`) است.

مدل پیش‌فرض: `meta-llama/llama-3.1-405b-instruct:free` — یعنی حتی با یک کلید بدون هیچ اعتبار مالی، باز هم کار می‌کند.

### یک تصمیم درست که «تأیید» شد نه «اجرا»

متن درخواست پیشنهاد کرده بود یک کلاس جدید `SimpleLLMClient` ساخته شود تا وقتی کلید API خالی است، جایگزین شود. این **عمداً ساخته نشد**. چرا؟ چون کنوانسیون واقعی این کدبیس از قبل این است: یک کلید خالی یا نامعتبر، همچنان یک کلاینت واقعی می‌سازد که فقط **در لحظه‌ی واقعی فراخوانی** شکست می‌خورد — و این شکست از قبل یک لایه بالاتر گرفته می‌شود (`LLMPlanner`→`DeterministicPlanner`، `LLMReasoningEngine`→`SimpleReasoningEngine`). یک لایه‌ی محافظتی دوم و اضافه، فقط تکرار همان تضمینی بود که از قبل وجود داشت.

با پایان این آماده‌سازی: ۱۰۷۸ تست، ۱۲۴ قابلیت (بدون تغییر — این یک ارائه‌دهنده‌ی جدید است، نه یک قابلیت جدید).

## جمع‌بندی

| موضوع | نکته‌ی کلیدی |
|---|---|
| بازتاب خود | توضیح می‌دهد، هرگز برنامه را عوض نمی‌کند |
| پیش‌فرض `reasoning.type` | `simple`، برای همان دلیل امنیتی `planner.type` |
| OpenRouter | دسترسی رایگان به LLM واقعی؛ بدون کلاینت جایگزین اضافه |

با تمام‌شدن این آماده‌سازی، همه‌چیز برای یک دموی زنده و قابل‌نمایش آماده بود. فایل بعدی دقیقاً همین دمو را باز می‌کند.
